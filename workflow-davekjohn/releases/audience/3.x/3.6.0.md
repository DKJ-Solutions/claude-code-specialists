# Release notes v3.6.0 🚀

**Date:** 2026-08-06  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

This release rebuilds how a change describes itself. Instead of being filed under a heading chosen from the
branch it arrived on, every change now states who it reaches and how much it weighs — and the release
documents order themselves by that. Alongside it, a branch keeps its plan in a file and has to finish it
before it can merge, the adoption documentation became two pages at new addresses, and a defect that could
delete work you had written is fixed.

**Three of the changes below need something from you.** They are first, and nothing else in this release
requires action.

## For consumers

### Do these after updating

#### 1. Take the scaffold marker off any lens you have filled in

If your repo was set up before this release, every specialist lens you have written still carries the
scaffold marker `(VUL-IN)` in its **title**, even though you replaced the slot below it. The teardown reads
that title and classifies the file as disposable scaffolding — so removing the system from your repo would
delete work you wrote. This was reported from outside and measured in a repo with 24 lenses: three filled
lenses holding 153 lines between them were all listed for removal.

The fix stops the marker being written into new titles, but it cannot reach a title already on disk. Search
your lens folder for `(VUL-IN)` and delete it from every `#` title whose lens you have actually filled in.
Leave it on the slot heading of lenses you have not filled — that is what marks them as still empty.

#### 2. Migrate your `CHANGELOG.md` if it still has section headings

The changelog is now an intro followed by one `##` per change, with no section headings at all. If yours
still carries `## Latest Release` or the three `## Tier N` sections, the tooling would read each of those
headings as a change: your release history would be published as if it were this release's work, and then
deleted from the file.

**It refuses instead of doing that**, and the refusal names the migration. So the action is required, but
you will not discover it by finding your history gone.

#### 3. Update any documentation links you have saved

The three consumer-facing pages became two, at new addresses: `plugins/INSTALL.md` and
`plugins/UNINSTALL.md`. Bookmarks to the old paths, and the links printed on the release cards shipped with
v3.5.0, now return 404. The repository's own `README.md` still routes readers to the right place, so this
is an inconvenience rather than a dead end.

### Every change now says who it is for, and the release notes order themselves by it

Each change declares two things: **how far it reaches** — only this repo's developers, the people working
on the project, or you as a consumer — and **how much it weighs** for that audience, scored 1 to 5 against
a written scale, where 5 means the reader has to act and 1 means nothing changes for them today.

The reach decides which document a change appears in; the weight decides where in it. Which is why the two
items you have to act on are at the top of this page rather than somewhere in the middle.

**What this replaces is worth saying, because it explains why the page you are reading looks different.**
Changes used to be grouped by the kind of branch they arrived on. Held against the previous release, that
grouping did not survive: the single most consequential change for consumers — one that broke every
existing installation — arrived on a branch labelled routine maintenance, and was filed below changes that
affected nobody. The branch a change arrives on turns out not to predict who notices it.

**And a release now has to earn its version number.** The tooling refuses to cut a release that reaches
nobody outside the repo, a feature release with nothing a consumer would notice, or a major release without
ten smaller ones behind it. In practice that means a page like this one always has something on it.

### A branch carries its plan, and has to finish it

Work now writes down its steps when it starts, in a file beside its changelog entry, and cannot open a pull
request or be merged while a step is still open.

**There is a third mark besides done and open**, for a step that turned out not to be needed, with the
reason kept on the line. That matters more than it sounds: without it, the only way past a step you decided
to drop is to tick it, and a check that teaches people to report work they did not do is worse than no
check. A branch with no step list at all is not refused — a one-commit typo fix should not need ceremony.

Both files live at fixed paths in a `branch/` folder, and the folder has a page explaining the convention.
Branches you have in flight keep working: the previous single-file form is still read.

### Fixes you get without doing anything

- **A skipped plugin now says why it was skipped** rather than reporting itself missing. Any plugin you
  enable that ships no agents used to produce the same misleading line at session start.
- **The fold no longer risks swallowing an entry.** A missing trailing newline in the changelog could make
  a merged change vanish from the release documents while the run still reported success.
- **Entries that quote the changelog format are read correctly.** Three separate defects came from readers
  disagreeing about where a quoted code block starts — including one that ordered entries by where a fence
  sat rather than by what they declared. There is one such reader now.
- **The link check reaches the documentation the plugins actually ship.** Thirty-nine files of prose had
  never been scanned; two agent definitions were pointing readers at the source repository's safety rules
  where they meant the reader's own.
- **Release documents no longer carry an empty section** where a change's audience table was removed
  before publication.

### What has not changed

Your installation, the marketplace name, the plugin names and the update commands are all unchanged. If you
are not writing changelog entries or lenses yourself, items 2 and 3 above are the only things this release
asks of you, and item 1 only if you have filled in lenses.

As always, refresh the marketplace before updating — an install compares against a cached copy, not against
what was just released:

```powershell
claude plugin marketplace update claude-code-specialists
```

## What it is worth

**The question of what matters most moved from a reader to the author, at the one moment it can be
answered cheaply.** Ranking twenty-two changes after the fact means re-reading twenty-two changes; the
person who wrote one knows what it was worth in the minute they wrote it. The scale is written down rather
than left to instinct, which is what makes the numbers comparable between releases instead of a mood.

**Three judgements that used to depend on someone remembering are now checked.** Whether a version number
is deserved, whether a branch finished what it set out to do, and whether a release document is ordered by
consequence -- each was a habit, and each is now refused when it is not met. The value is not the checking
itself but that the failure is loud: all three used to fail silently, which is the expensive kind.

**And the release process asks for approval one time fewer.** Cutting a release is still a deliberate
decision. The closing steps of a cut that was already asked for are no longer a second decision, because a
checkpoint that is always waved through trains people to stop reading the ones that are not.

## What was still open at this release

- The user-facing release document is still generated as a draft and rewritten by hand before publication.
  The selection of what belongs in it is now automatic; the prose is not, and was not intended to be.

- Two things surfaced while cutting this release and were recorded rather than repaired. A safety check
  cannot tell a quoted example from a real occurrence, and flagged a text that merely described the
  problem it looks for -- the fifth time this project has met that same shape. And seven of 326 dated
  entries in the published history disagree with the real date by a day or two; they were deliberately
  left alone, because they sit in records that have already gone out and moving them rewrites shipped
  history for nobody's benefit. Whether either becomes work sits with Dave.

- The empty-section defect this release nearly shipped was caught by the one step where a person looks at
  the assembled document before it is public. That step is optional in the tooling. Whether it should stay
  optional was not decided here.
