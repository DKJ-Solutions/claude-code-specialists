# Release notes v4.15.0 🚀

**Date:** 2026-08-20  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

A two-section branch entry, a live-theme guard for team-shopify, and a release-notes page you can scan

## For consumers

### If you run `team-shopify`, a guard now refuses a theme publish, a theme delete and an unauthorised live push -- and it arrives half-armed

`team-shopify` gains its first hook: a `PreToolUse` guard that blocks a theme **publish**, a theme
**delete**, and a push aimed at your **live theme** -- whatever shell wraps the command. Publishing and
deleting have no escape hatch and need no configuration. The third rule does, and it is the reason this item
is first on the page.

**The visible symptom of the half-armed state is a standing `[ERROR]` at every session start**, naming the
function to add. Until you add it, a push aimed at live **by theme id** goes through; `--allow-live` is still
blocked, and publish and delete are still blocked. A guard that is installed reads as protection, which is
why this state announces itself rather than sitting quietly.

**What to do:** answer `Get-ShopifyLiveThemeId` in your `scripts/repo-config.ps1` with your live theme's id.
Then, **if you already wrote your own guard, delete it** -- you are now running two. Your existing
authorisation marker keeps working: the shipped default accepts any marker *ending in*
`LIVE-PUSH-AUTHORIZED`, which is what both existing Shopify repos already write. `Get-ShopifyLivePushMarker`
narrows it to one spelling if you want that.

Liam, Sandra and Steven each named one specific store twice -- once in the `description:` your model reads
every turn, and once in the body line that tells the subagent who it is. They now read "for this repo's

### Delete `Get-ChangelogHeading` from your `scripts/repo-config.ps1` if it is there

That seam was retired on August 5, 2026. Nothing reads it. The bootstrap kept scaffolding it anyway, with a
comment arguing that you should fill it in -- so every repo bootstrapped since then carries a dead function
that asks for an answer.

**The bootstrap is fixed, and that does not reach you**: a scaffolded file is written once and never again,
so no release can correct a file you already have. **What to do:** delete the function and its backing
variable. Whatever value you gave it was never used, and if you have not filled it in, there is nothing to
decide -- `INSTALL.md` has always said it may be deleted.

### Your branch files are renamed, and the step list gains a fourth phase

`branch-cycle.md` carries the branch through **PLAN / CREATE / TEST / DEPLOY**; `branch-deployment.md` is the
part that travels to `main`. The old names said where a file ended up rather than what it held. The step list
loses its `### Steps` wrapper -- the phases are the sections now -- and **DEPLOY deliberately holds no
steps**, only a pointer to the other file.

Each end of a branch's life is now stamped in the document that owns it: the creation stamp sits in the cycle
file's heading, and the landing stamp on the entry's `Pull Request` heading, written from the pull request's
own merge time.

**No action needed, and nothing to migrate.** Both old filenames are still read, so a branch you have in
flight folds and resets in the files it already has. The one thing to expect: the file you open tomorrow has
a different name than the one you closed today.

### Your changelog entry is two sections, and neither names a tier number

`#### Tier 0` is gone -- the question the entry opens with *is* that section -- and `#### Higher than tier 0?`
now reads `#### What makes this change extra special`, nested inside it. Filling one in means answering two
questions rather than classifying two readers, and the guidance under the second one now names **your**
audience in words rather than describing subscribers a tier-1 repo does not have.

**No action needed.** Your next branch is scaffolded in the new shape and your `branch/templates/` is
rewritten to match; nothing you have already written has to change, and nothing about your release documents
changes. Seven older entry shapes are still read, which is what keeps every entry in your `CHANGELOG.md`
folding.

**If you have stated no audience tier, your tier headings do not change at all** -- you keep the numbered
sub-sections. Absent means unchanged.

**The visible symptom is an entry reporting `tier 0` when it declares more, or printing no tier line at all.**
On this repo's own pending work that difference was a **tier 2 at score 4** reported as a bare tier 0 -- the

same reader the fold and the release cut use, so the next rename cannot reopen it. `N/A` renders as `N/A`
instead of a zero, and a malformed section is surfaced instead of swallowed.

**No action needed.** **If you have stated an audience tier**, your reporter was wrong in exactly the way
this repo's was; **if you have stated none**, you keep the numbered headings the old pattern could read, and
this is the smaller half for you.

## What it is worth

**A guard now stands between a stray command and the theme customers see, and the gap it closes was open by
default.** Both Shopify repos serve real customers from a live theme and Shopify provides no lock, so the rule
against publishing was prose -- and prose does not stop a command. The mechanism worth understanding is *why*
a permission list could not do this job: a deny rule matches a command prefix, so it never sees the same
command wrapped in `powershell -Command "…"`. That is the ordinary state of a repo rather than a
misconfiguration, which means every repo enabling this team had the route open. It was also built twice
independently before it shipped here, which is the plainest evidence that it belonged in the product rather
than in each repo.

**The reduced dependence is on nobody re-deriving a written rule into a working one.** Two teams wrote the
same guard from the same paragraph, and one of them spent its first day discovering that matching the
forbidden words *anywhere* in a command blocks the very edit that writes the rule down. The shipped version
asks where the words sit rather than whether they occur, and every one of its three exemptions carries a
counter-case -- because an exemption without one is a hole with a comment on it. A guard that makes its own
rule impossible to write down is one somebody eventually switches off, which is worse than no guard.

**Four of this release's changes are the same defect: a shipped document naming something that does not
exist.** A path the bootstrap never creates, a script absent from the marketplace, a retired seam scaffolded
with a comment arguing for it, and a page describing an entry shape nothing accepts. None of them errored, and
that is the expense -- instruction text that is wrong does not fail, it gets followed. The organisational
point is that these reach every consumer through a plugin update rather than by anyone choosing them, so the
cost of a wrong instruction is paid once per reader rather than once.

**One of the four cannot be repaired for the people who already have it**, and it is the reason a scaffold
deserves more care than a script. `Get-ChangelogHeading` is written into a file exactly once, at bootstrap; no
later release can correct it. One repo paid for that in the way that is easiest to miss -- by doing the work
properly, reasoning at length about which of two false values was less harmful, and filing the reasoning as a
report. Both of its options were wrong, and so was the question.

**Cost to here: 5m 12s** from clock start to the tag being pushed. The legs, measured from timestamps rather
than reconciled to a total: reading the checklist, verifying the entry-section seams and both gates on the
release commit **4m 29s** (the 44 test suites were **151s** of that, the lint gate the rest), and the two
pushes **43s**. Nothing in that block waited on a person.

**The suites read 151s here and 888s earlier the same morning, on the same commits.** That is the same spread
v4.14.0's note recorded as an unexplained jump to 364s, and it has a plain cause: the earlier reading was
taken while the machine was running a full branch review. A stopwatch reading is a count, and a count taken
under load measures the load. The figure to carry forward is that this gate runs in about two and a half
minutes on an idle machine -- and that timing a gate while working the machine produces a number about the
machine.

**Cost of this release: 24m 34s** end to end, from clock start to both attachments verified on the published
Release. Added after the fact, because this document cannot time its own publication -- the four legs the
paragraph above could not see are writing this page, its own gates and commit **9m 37s** (the suites **148s**
of that), CI and the merge **8m 22s**, the fold **5s**, and the publish with its two uploads **1m 18s**.

**The head was 5m 12s of that -- 21%, the lowest of the four releases that have been timed.** `v4.12.0` came
to 24% of 20m 41s, `v4.13.0` to 30% of 20m 38s and `v4.14.0` to 32% of 26m 40s. Four readings are not a
distribution, but they keep saying the same thing: most of a release happens after the document describing it
is frozen, which is why the first pass is written before the tail rather than estimated afterwards.

**Two legs are the tail, and only one of them blocked a person.** Writing this page and waiting for CI came to
**18m 00s** between them — 73% of the release. The writing is the part a person does; CI is a machine running
behind you, and shortening it would buy almost nothing. That distinction matters more than the total: the
fixed cost of a release sits in the writing, and where a cost is fixed per event, releasing half as often
removes exactly as much of it as making it twice as fast.

## What was still open at this release

  document cannot time its own publication, so the total above was added afterwards in its own small edit. The
  attachment is deliberately not replaced -- an attachment is what was published at the moment it was
  published, and silently swapping it is the opposite of the record this document is for. **This page is the
  current version.**
- **The v4.15.0 tag holds a draft of this document.** The cut generates it and commits in one motion, so what
  the tag carries is the entries in the words their authors wrote for a diff reviewer. This page is the
  written version and lands afterwards, via its own pull request.
- **This release has not been published to the organisation.** Publishing is a decision separate from
  cutting and was not asked for. Until it is, colleagues installing internally remain on the four team
  plugins at **4.13.0** -- now two releases behind. Read at the target rather than carried forward:
  `BWJ-ecommerce/claude-plugins-bwj`, commit `9ea8dcf`, 2026-08-16T19:40:08Z, from the published
  `plugin.json` files themselves.
- **Two reports about the live-theme guard arrived before this release was cut and are not answered by it.**
  One says the guard lands with its id half inert because no install step seeds `Get-ShopifyLiveThemeId` --
  which is the first item on this page, stated as a session-start error rather than solved. The other says a
  consumer who built their own guard now runs two, with no convergence path. Both were filed by the
  consumers who wrote those guards, and both sit with the source.
- **`team-shopify` still ships no starter `.theme-check.yml` and no CI workflow**, the two "conveniences"
  of the report the guard answered. They need a delivery mechanism and a decision about which checks are on
  by default -- and that decision is real rather than a default: one of the two Shopify repos runs against
  1,504 pre-existing offences across 171 files, so a starter config assuming a clean theme is a starter
  nobody keeps. Asked on the report, unanswered.
- **Whether `team-shopify`'s `start-task` gets its missing script or moves to the workflow plugin is
  undecided.** The report offered three routes and declined to pick, correctly -- the choice is the source's.
  This release repaired the three verified defects and left the skill where its domain is.
- **The release-notes page still renders note bodies in the browser.** Going fully script-free would need a
  second markdown implementation beside the one in the template -- two renderers for one format -- so the
  index is static and the bodies are not. Without JavaScript a reader gets the complete index and empty
  notes, and the page says so.
- **Two layers of this repo speak Dutch where no rule in the tree can reach them** -- the public repository
  description and the `inbound` label description, both in repository settings. Unchanged since v4.14.0.
- **A second `Get-JsonField` remains, and 310 uses of "workshop" as a role word remain**, both deliberately
  and both unchanged. No live misbehaviour was found in the first; the second is not the retired framing, and
  sweeping it buys consistency at the price of worse sentences.
