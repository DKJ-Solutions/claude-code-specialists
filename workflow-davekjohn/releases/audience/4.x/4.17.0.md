# Release notes v4.17.0 🚀

**Date:** 2026-08-20  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

The Shopify floor gains its pre-task sync, and the branch-entry convention gains a shipped gate

## For consumers

### If you run `team-shopify`, stop hand-writing the sync that mirrors your live theme

`team-shopify` gains `sync-main`, a shipped script that pulls the live theme into your trunk **without
letting live overwrite what the trunk has done since**. The exclusion rule that decides which files live may
not touch ships beside it as its own tested lib, with 32 asserts across two suites.

**What to do**, if you are on `team-shopify`:

```powershell
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/adopt-shopify-floor.ps1" -StoreDomain <your-store>.myshopify.com
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/adopt-shopify-floor.ps1" -StoreDomain <your-store>.myshopify.com -LiveThemeId <id> -Apply
```

That writes the sync's seam answers into the same `scripts/repo-config.ps1` block the floor already appends,
so the sync is runnable in the move that arms the guard. Then:

```powershell
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/sync-main.ps1"
```

**Two of its seams are required and the script refuses to guess either**: `Get-ShopifyLiveThemeId` and
`Get-ShopifyStoreDomain`. The rest have defaults matching what both existing consumers already do --
`Get-ShopifySyncReferencePattern` (`^[Ss]ync`), `Get-ShopifySyncBranchPrefix` (`sync/live-`) and
`Get-ShopifySyncMerges` (`$false`: push the branch and stop, rather than merging for you). `-Store` overrides
the domain for a one-off against a second store.

**It never pushes to live, publishes a theme, or deletes one.** It reads from live and writes to git; the
`PreToolUse` guard covers those three acts independently and is not weakened here.

**If you already wrote your own sync, this is the one to converge onto.** Both consumers who had one wrote it
themselves and the first version destroyed work in both -- one of them recording the same procedure reverting
merged work three times in a single week. A live theme has no locking and no merge, so the obvious
implementation of "mirror live" is exactly the one that eats unpushed work. The failure is not exotic: the
case both hand-written versions got wrong is that **a deletion is also a touch**, and it is asserted directly
against fixture repositories here.

**One interaction to know if you also run this marketplace's changelog model:** the moment you adopt it,
"merged into the trunk but not live yet" becomes a *designed* state, so every entry sitting in your
`CHANGELOG.md` names work a naive sync would have reverted. Adopting one half of this marketplace makes the
other half more dangerous, and that sentence is now in Sandra's manual and on the skill page rather than only
in this note.

### The branch-entry gate is now something you run, not something you write

If you run `workflow-davekjohn`, the CI gate that holds every pull request to carrying a written changelog
entry now **ships**: `scripts/lint/check-branch-entry.ps1`, plus the six lines of workflow that call it.

**What to do:** run `adopt-workflow-folder`, which places `.github/workflows/branch-entry.yml` for you. It is
additive and a dry run until `-Apply`, like the other two `adopt-` commands.

```powershell
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/adopt-workflow-folder.ps1"
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/adopt-workflow-folder.ps1" -Apply
```

**If you wrote your own version of this gate, delete it and take this one.** Both consumers who had one wrote
it from scratch against a document whose function signatures they had to reverse-engineer, and **both got it
wrong in the same direction**: each refuses a merge over a missing significance score. That is stricter than
the convention actually is -- tier 0 owes nothing, and the score is asked for at the release cut, not at the
merge. The shipped gate reports it and names the cut instead of refusing, which is the load-bearing test in
its suite.

**It adds no rule of its own.** It calls the same two functions `open-pr` calls, so there is one definition of
"written" in the system rather than a second one per consumer.

**Two things it deliberately does not do**, so you are not waiting for them: it is not a job in your `ci.yml`
(that workflow also runs on `push: main`, where the entry sits in its reset state after every fold, so your
trunk would be red after every merge -- it gets its own `pull_request`-only file), and it does not make itself
a **required** check. That is a branch-protection setting and it stays yours.

One new seam comes with it, `Get-EntryGateExemptPrefixes`, defaulting to `sync` -- the prefixes that owe no
entry, because a mirror branch carries somebody else's work. An unknown prefix is **not** exempt, so a typo
cannot skip the gate silently.

### If you run `team-shopify`: read theme drift after `git add -A`, and do not pin `eol=lf`

The Shopify CLI writes each file with the line endings live holds, and live holds both. So a pull reports
files as modified with **zero changed lines** -- measured in a consumer's tree at 37 files out of 37.

**What to do:** run `git add -A` first, and read the drift off the staged diff rather than off the raw
`git status`.

**What not to do, and this is the half worth the section:** do not pin `eol=lf` in `.gitattributes`. It is the
fix that suggests itself and it makes the noise *permanent* -- the same files come back after every pull,
forever. That converts the one signal that spots a third party's in-flight edit into standing noise, and the
whole safety model of this team rests on that signal: after a pull, you look at the diff and judge whether it
is yours or somebody else's unsaved work. **A verification step that cries wolf every time is the step nobody
reads on the day it is right.**

The plugin deliberately does **not** place a `.gitattributes` for you. What it should carry is written down,
along with why it is not scaffolded: `* text=auto` dropped into a repo whose index already holds CRLF
renormalises the entire tree on the next `add`, which is a bad surprise to arrive by scaffold.

**How this reached you is worth one line:** both existing Shopify consumers hit it independently, and one hit
it *twice* -- filing `eol=lf` as an improvement and then inverting its own conclusion on re-measuring, because
the proposed remedy would have broken the check it was meant to help. You inherit the whole loop.

### If you adopted the workflow folder already, check its `releases/README.md`

`adopt-workflow-folder` used to contradict itself inside one command's output: it scaffolded
`workflow-davekjohn/releases/README.md` with a `## Release history` heading and a table promising the cut
would insert rows there, and then told you to leave `Get-ReleaseHistoryPath` at its repo-root default. Both
cannot be true.

**What to do:** if you adopted the folder before this release, the page in your repo carries a table nothing
will ever write to. The scaffolded page now states your repo's release *answers* and names where the list
actually lives, read through the seam rather than hardcoded -- so a repo that has repointed it is not sent to
a file that is not theirs.

**No new file is scaffolded for you, deliberately.** A root history file with a table but no `<major>.x`
heading reads as done to `cut-release`, which files the row while silently disabling the guardrail that
refuses a `v2` row under a `1.x` heading. The closing advice now prints the exact shape you owe, and the
warning you get if you forget: `<path> is missing -- row not added`, after which the cut proceeds.

### If you run `team-shopify` and throw away preview themes, you can now authorise a delete

`team-shopify`'s live-theme guard gains a third seam, `Get-ShopifyThemeDeleteMarker`. Rule 2 -- a theme delete
-- stops being absolute **for repos that ask for it**.

**No action needed, and doing nothing is a complete answer.** Take this update and change nothing and a theme
delete is refused exactly as before; no marker you could write would pass it. That is the deliberate opposite
of the push marker's default: an unstated seam has to mean unchanged, and unchanged for a delete is *always
denied*.

If you do want it, three bounds are worth knowing before you answer the seam:

1. **The live theme is refused even with the marker**, and that check runs before the authorisation path, so
   no marker reaches past it.
2. **A delete without the marker still blocks.** Answering the seam does not open deletes generally.
3. **One marker may not do two jobs.** Answer both seams with the same string and the delete capability stays
   **off** rather than being granted. A push marker gets written as routine -- it is in your own step list --
   so accepting it here would turn every documented live push into a standing authorisation to delete. It
   fails safe, and it is the bound most likely to surprise you.

**Why a marker rather than "allow anything that is not live"**, which was the simpler option and was declined:
a real Shopify estate is not the live theme plus this week's preview. Measured on the requesting store,
**nineteen themes, one of them a current preview** -- the rest dated backups, two named `DO NOT DELETE`, and
five `feat/*` themes from a previous agency. Being non-live is not enough to make a deletion deliberate.

### `ship-pr` now names the trap that makes a working merge look broken

If you run two sessions in one checkout, `ship-pr`'s step-list gate can refuse your merge over a step **you
never wrote**. The gate reads `branch-cycle.md` on disk, and nothing compares the branch you are standing on
against the branch whose pull request is being merged -- so if another session moved `HEAD` while yours waited
on CI, the gate reads the other branch's freshly scaffolded step list.

**No action needed, and nothing is damaged** -- re-running from the right branch picks up where it left off.
The reason it is here is that every instinct on meeting that refusal points at the step list rather than at
`git rev-parse`, and the page now answers it in one line.

**A guard was deliberately not built.** Comparing `HEAD` against the pull request's head ref is one line, but
it is a change on the merge path and one benign instance is not evidence for making it. The page also states
the wider rule none of these scripts can see: they assume **one working tree per session**, `/lock` is a note
rather than a claim on a checkout, and two things that genuinely run at once want a second clone or a
worktree.

## What it is worth

**The two most dangerous things a Shopify consumer does by hand are now shipped, and this release closes the
more expensive one.** v4.15.0 and v4.16.0 armed the guard that stops a wrong push; this one ships the
procedure that runs *before* every task. The distinction matters commercially: the guard prevents a bad act,
the sync prevents a good act from silently reverting somebody's finished work. Both consumers who wrote the
sync themselves destroyed work with the first version, and one of them did it three times in a week with the
same procedure -- that is not a skill gap, it is the obvious implementation being wrong. A live theme has no
locking and no merge, so "mirror live into the trunk" only has a safe form if somebody has already worked out
the exclusion rule. Shipping it with 32 asserts, including the exact case both hand-written versions got
wrong, means the next consumer inherits the answer instead of the accident. That consumer is the exposed one:
they have no sibling repo to copy from.

**The reduced dependence on a developer is the same pattern twice, and the second instance is the sharper
argument.** Two consumers independently wrote a branch-entry CI gate, from scratch, against a document whose
function signatures they had to reverse-engineer -- and **both got it wrong in the same direction**, each
enforcing a rule stricter than the convention, one of them recording that they had no way to verify their YAML
before it shipped. When two teams derive the same artefact from the same paragraph and make the same mistake,
the paragraph was doing a script's job. The plugin already shipped every *reader* of the entry format and
shipped nothing that *checked* it, so the machinery to enforce the convention was sitting there the whole
time. What shipped is not new logic; it is the existing functions called from CI, which is why it is simpler
than the hand-written gates it replaces rather than more complex.

**A convention that enforces nothing rots quietly, and this release stops that clock.** The source now runs
the shipped gate on its own pull requests, so it is exercised here every day rather than being unverified in
every repo that has a copy. That is the difference between owning a gate and running one.

**The install path was still costing a consumer a day, and this is the third round of closing it.** The
reporting consumer spent a second full day on follow-up rounds after adopting, each one triggered by a session
check naming something neither adoption page mentioned. None of it was discovery work -- all of it was
knowable up front, and none of it could be bridged in that consumer's own lens, because the audience for those
pages is a repo that has not adopted yet. Two documents that stop one step short of the finish line cost more
than the step would have.

**One design decision in here is worth repeating outside its own context: an unstated seam has to mean
unchanged.** The theme-delete marker defaults to *empty*, which switches the capability off, while the push
marker defaults to a permissive suffix. Those look inconsistent and are not: nobody has ever written a delete
marker, because until this release no marker could authorise a delete at all -- so a default here would hand
every consumer a new destructive capability on their next plugin update, silently. The same reasoning produced
the collision rule, where answering both seams with one string leaves the capability off rather than granting
it. A marker that gets written as routine cannot also be an authorisation, or the authorisation means nothing.

**The two reports worth carrying out of this release are both about scope rather than symptom.** The
line-endings report arrived with a figure that had already moved -- "over 712 tracked files", the tree now says
740 -- so the text carries the count that holds (37 files, zero changed lines) and drops the total. And the
release-history report asked for a second half that was deliberately not built, because the recount showed the
premise was wrong: the cut does not create an unannounced file, it warns and proceeds. Building the proposed
repair would have scaffolded a file that reads as done to the cut while disabling one of its guardrails. Both
are the same lesson the house rule already states -- verify the reason, not just the symptom -- and both cost
nothing this time because the recount happened before the work.

**Cost to here: 11m 12s** from the first command of the session to the moment this page was frozen for its own
pull request. Step 0a's baseline was taken before starting this time, so the legs are clock readings rather
than reconstructions: reading the repo's stand, the nine pending entries and the release seams, then running
the cut **5m 05s** (19:14:28 to 19:19:33, of which the **48 test suites were 184s** -- the gates are very
nearly the whole of that leg); inspecting the generated artefacts and pushing the commit and tag **36s**;
opening this branch and verifying every mechanism named above against the tree **2m 10s**; writing this page
**3m 21s**.

**Three legs are still running on this file as it is written** -- its local gates, its CI and merge, and the
publish -- so the total arrives in a second pass, as step 0a of the checklist asks. At the two releases before
this one the unmeasurable tail was the larger half: 9m 42s frozen against 28m 03s total at v4.4.0, and 7m 36s
against 25m 29s at v4.16.0. Expect the same shape here.
