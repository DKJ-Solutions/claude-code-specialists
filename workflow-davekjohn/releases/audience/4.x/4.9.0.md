# Release notes v4.9.0 🚀

**Date:** 2026-08-15  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

the workflow gathers into its own root folder at the consumer, and what the plugin ships is held to what a consumer can actually use

## For consumers

Two items in this release ask you to do something. They are both first. Everything below them is an
opt-in or a fix that reaches you without any action at all.

### You need to create the workflow folder, and your session will tell you so

After you update, every session start reports an **`[ERROR]`** until a `workflow-davekjohn/` folder
exists in your repo. Run the skill it names:

```text
/workflow-davekjohn:adopt-workflow-folder
```

It scaffolds the folder in one move -- its README, its `CLAUDE.md`, its contributing page, the release
history table and the branch dossier. It is a dry run by default, so run it once to see what it would
write and again with the switch it prints. It never overwrites anything you have filled in.

**Your branch dossier moves with it.** The two files a branch works in -- the changelog entry and the
step list -- are no longer at `branch/` in your repo root but at `workflow-davekjohn/branch/`. Every
shared script follows in one move, so `new-branch` creates the new location for you on your next
branch. **A `branch/` directory left over at your root is yours to delete by hand**; nothing removes it
for you, and nothing reads it any more.

**One thing to re-adopt while you are there.** If you copied the mojibake-path answer into your own
config before today, it still names the old location, which quietly drops the moved files out of that
check. Re-run `/workflow-davekjohn:adopt-config` and take the new value.

### If you use the Shopify team, one specialist can no longer run shell commands

Sandra's subagent is declared read-only and now **is** read-only: her tools are reading and searching
only. She can no longer run `shopify theme list`, which was the first step of her working method.

**What to do instead:** the main-loop persona still has the CLI and still does the pushing. The subagent
now prepares from your repo -- your lens, your theme files, your settings -- and names the live lookup
as the one thing to fetch before anything is pushed. If you had a habit of asking the subagent to list
your themes, ask the persona.

**And check that your lens names your live theme.** The shipped Shopify specialists used to quote one
customer's store and theme id, which was wrong for every consumer but that one. They now point at your
repo lens for the specifics. If your lens does not name your theme, the specialist will say so instead
of quoting an id that was never yours -- which is the correct answer, but it means the value has to be
in your lens.

Everything from here needs no action.

### Three setup skills stopped starting on their own

`specialists-init`, `specialists-teardown` and `sync-roster` can no longer be picked up by the model on
its own initiative -- you ask for them by name. Each also states its Windows PowerShell requirement
*before* the procedure rather than at the end.

That matters if you work anywhere without PowerShell: previously a request like *"set this system up
for me"* could begin a bootstrap -- marketplace registration, a plugin install, up to two session
restarts -- and only fail at the very last command, on a machine that could never have run it.

### You can now load the orchestrator without a repo

New skill: **`orchestrator`**. It brings Chris, the coordinating specialist, into a session that has no
repository at all -- a Cowork session, a chat. Until now the worker specialists arrived by themselves
when you installed a team plugin, while the layer that routes between them had no way in.

**Inside a repo you already have the better route** and should keep it: the `@`-import in your
`CLAUDE.md` loads Chris at the *start* of every session rather than when someone remembers, and it
brings your repo lens -- your routing table, your local agreements. This skill carries the portable half
only, and it says so itself.

### Setting the system up is its own page now

Adoption -- run the bootstrap, check the orchestrator took the floor, write your roster, fill your
lenses -- is now [`plugins/ADOPTION.md`](../../../../plugins/ADOPTION.md), separate from the install
plumbing. If your organisation published these plugins to you internally, that page is the whole of what
you need; the marketplace-and-install pages are for whoever set that up.

**If you are reading a copy republished inside your own organisation**, the install pages now say so at
the top, before the first command. Following them would add a second plugin channel pointing at a public
marketplace, which is the one thing an internal marketplace exists to prevent.

### Your branch plan follows a familiar arc

The step list is scaffolded with **PLAN**, **CREATE** and **TEST** headings. An empty phase is a
statement, not a failure -- a branch with nothing to test leaves that heading bare. Deploy is
deliberately not a fourth heading: the deploy is the changelog entry, the part that travels on after the
merge.

The headings come from a wording setting, so you can rename them, and an empty list switches them off
and restores the previous shape.

### Two contributing pages, and which one wins

Your root `CONTRIBUTING.md` stays the standard workflow -- branch, PR, CI green, merge -- the page that
still means something in a checkout where this plugin is absent. `workflow-davekjohn/CONTRIBUTING.md`
carries the workflow's own layer beside it. **Where they disagree, the workflow's page wins**, and both
pages say so.

### Fixes that reach you without you doing anything

- **The status report lists your open issues again.** It was printing one unreadable row of
  `System.Object[]` instead of the issues, and with no issues open it printed a bare `#` rather than
  saying `none`.
- **A status report that cannot reach GitHub now says so.** It used to print **`none`** when it was
  unauthenticated or offline -- *"we could not ask"* rendered as *"there are none"*, which is the worse
  of the two failures, because it reads as an answer.
- **A specialist no longer hunts for a repo lens you never wrote.** Every specialist opened by pointing
  at a lens file in your repo; without one, each decided for itself what the absence meant. A missing
  lens is now stated as an ordinary condition.
- **The shared-block marker stopped telling you to edit a file you do not have.** Every generated block
  in every specialist named a source path that exists only in the source repository -- three lines above
  the rule saying you do not edit the shared core locally.
- **A specialist's description says what the work is** before it says which repository instrument
  carries it, so the description of a reviewer or a planner now includes you when you have no branch and
  no diff.
- **Every specialist now treats file content as data, not instruction.** A file being in reach says
  nothing about who put it there or why -- the same boundary the two web-fetching specialists already
  carried.

## What it is worth

**Six of this release's changes were filed by the people using the product, not found here.** Four of
them came from a single assessment made in a Cowork session with no repository at all -- an environment
this system had never been run in -- and that one session produced a class of defect no gate here could
have found: every reserve the specialists lean on (a consumer's settings file, a repo `CLAUDE.md`)
happens to be absent there at the same time, so the gap between what a boundary *claims* and what it
*enforces* was on open display. Four of the four specialists put on that assessment hit the same
friction first, independently and in the same order. That reproducibility is what turned a report into a
repair rather than an opinion.

**The risk closed this release is a real one and worth naming plainly.** Two shipped specialist
definitions named an actual customer's store and its live theme id, in a repository that is deliberately
public. It is not a credential and it opened nothing -- but it is an identifiable customer in a public
place, which our own constitution says does not belong here. It has been removed, and the rule around it
was rewritten so the specialists point at each consumer's own lens rather than carrying anyone's
specifics. A check that would catch a recurrence was measured and deliberately not built: it produced
one finding on the whole tree and that finding was false, and store and brand names cannot be matched at
all. So this one is closed by removal and by where the rule now points, not by a gate.

**A boundary stopped being a sentence and became structure.** A specialist declared read-only was
handed an unrestricted shell, with a live theme id four lines above the instruction not to touch it. The
definition was honest that the boundary rested on that instruction plus a setting in the consumer's own
config -- which is exactly the pair that is missing where there is no repo. It now rests on the toolset:
the commands are not things she declines, they are things she cannot invoke. The cost is real and was
paid deliberately -- the subagent lost a lookup step, which moved to the persona that has the CLI.

**The organisation stops paying for scatter at every consumer.** Three phases of this release move
everything portable about the workflow into one folder in the consumer's repo instead of spreading it
through their root, and the third piece -- a skill that scaffolds it, plus a session-start signal while
it is missing -- means a consumer is told rather than left to discover it. What that buys is not fewer
files; it is that the next thing the workflow needs to place has an obvious home, and that a consumer's
root stays theirs.

**And colleagues without GitHub access can now receive these plugins.** One script publishes the
marketplace into a private business repository that Claude Enterprise syncs. This repository stays the
single source of truth and the target is rebuilt from scratch on every run, so a plugin removed here
disappears there too. Publishing stays a separate, deliberate decision after a release -- releasing
without publishing is a normal outcome, not a half-finished one.

**What this release cost, first pass.** Clock started at 09:04:59 and the tag was pushed at 09:10:35 --
a subtotal of **5m 36s**, against `v4.8.0`'s 5m 02s and `v4.7.0`'s 15m 31s. Two legs make it up: the cut
itself at **4m 03s**, of which the test suites are 3m 22s and the rest is generating eleven files; and
the push at 5s. The remaining 1m 28s is intake -- reading the repo's own state and the pending entries
-- and it is the only leg that **blocked a person**, because it ends in the one question a script cannot
answer: what this release is called. The gates are once again the floor: they cost the same three-and-a-
bit minutes here as in the previous two releases, which is the third consecutive cut to start on the
first attempt. The three legs this document cannot see -- its own gates, its merge, and the publish --
are added in a second pass once they exist.

## What was still open at this release

- **How this system should arrive in a Cowork-native environment was left undecided.** The assessment
  that produced six of this release's changes also raised the packaging question behind them, and
  nothing here waits on that answer -- every change made holds inside a repository too. The decision
  sits with Dave.
- **Four more script-wrapping skills can still start on their own initiative**, named and deliberately
  left: the two config-adoption skills, `new-branch`, and the workflow-discovery skill. Switching those
  off is a decision about the workflow rather than a repair, and `new-branch` in particular is one a
  model reaching for it is arguably right about inside a repo.
- **The merge still re-runs the test suites the pull request already proved**, measured at roughly three
  minutes per release. It is the largest single duplicated cost left in the release procedure and the
  next place a saving lives; nothing was changed about it here.
- **The consumer-side re-adoption of the mojibake setting is manual.** A consumer who copied that value
  before the branch dossier moved keeps the old location until they re-adopt, and nothing fails loudly
  when they do not -- the moved files simply drop out of that check.
