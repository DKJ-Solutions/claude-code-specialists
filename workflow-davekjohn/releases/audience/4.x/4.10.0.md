# Release notes v4.10.0 🚀

**Date:** 2026-08-15  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

The Claude App marketplace publishes a chosen subset, and an inbound report's subject is verified before it is routed

## For consumers

**Nothing in this release asks you to do anything.** There is one exception, and it belongs to the
previous release rather than to this one -- it is first.

### If you are updating from 4.8.0 or earlier, v4.9.0's two actions still apply

Updating straight to 4.10.0 does not carry you past them. After the update your session start reports
an **`[ERROR]`** until a `workflow-davekjohn/` folder exists in your repo, and the two files a branch
works in have moved out of your repo root.

Both are closed by one skill, and a leftover `branch/` directory at your root is yours to delete by
hand -- nothing removes it for you. If you use the Shopify team there is a third item: check that your
repo lens names your live theme, or the specialist will refuse the question rather than answer it with
an id that was never yours.

**[The full v4.9.0 notes are here](4.9.0.md)**, with the skill to run and what each item means. That
document is also complete now: it carries its end-to-end cost, where it previously showed only the part
measurable before publication.

Everything from here needs no action.

### If you receive these plugins through your organisation, the list is shorter and everything on it works

Where an organisation republishes this marketplace internally -- so colleagues without GitHub access can
install from it -- the two **workflow** plugins are no longer offered there. They were never usable in
that setting: every skill in a workflow plugin ends in a script run against a repository checkout, and a
Claude App session has no checkout, so both could only ever fail at their last step.

**Nothing you already have breaks.** The marketplace keeps its name, so every plugin you have enabled
still resolves. The four team plugins are unchanged and travel exactly as before.

If you are installing from GitHub, this does not reach you at all -- your marketplace is the whole
repository and always was.

### Chris checks that a report is about something real before working on it

The intake route already asked three questions about an incoming report: is the **symptom** still there,
does the **reason** given for it hold, and does the **repair** it proposes name things that exist. There
is now a fourth, underneath all three -- does the **subject** exist at all.

This matters for the reports you did not write yourself. When an idea is mentioned in passing and filed
by a session so it is not forgotten, it arrives under your name, in your house style, naming a project or
a tool nobody has ever checked. Each of the other three questions can pass on its own terms while the
item as a whole is about nothing.

**What you will see:** a name that appears nowhere except inside the report that names it is now raised
as a question to you at pickup, before anything is designed. The check is one search, and *"I cannot see
it from here"* is explicitly not the same answer as *"it is not there"* -- reading the first as the
second is what this is written against.

## What it is worth

**A publication set that is now a decision rather than a side effect.** Publishing the marketplace to
the organisation used to mean publishing whatever happened to be in the tree. It is now a named list
with three refusals around it, each guarding a failure that is otherwise silent: a name the manifest
does not have (a typo would quietly drop the plugin it meant to keep, and report success), a list that
keeps nothing (an empty marketplace rather than a subset), and a plugin folder that travels while the
rebuilt manifest never names it -- that last one produces no error anywhere, it simply means the plugin
is never offered while the manifest reads as complete. The alternative on the table was a per-entry hide
flag, which would have required Claude to honour it; not travelling needs nobody's cooperation.

**One measured waste, and the check that closes it.** Issue #660 asked for a project board for a tool
that does not exist -- no file, no repository, no other mention anywhere. Two work pickups answered its
design questions, measured two genuine blockers, and produced a coherent design; the second also
required an authorisation-scope change requested from Dave. All of it was correct, and all of it was
about nothing. The cost was two pickups and one permission request; the check that would have stopped it
is a single search at intake. The first pickup did run that search, found nothing, and recorded it as
*"not visible from here"* -- so what was bought here is a reading, not a tool.

**Where the work came from.** Two of this release's four changes are the previous release's own
documents; one closes an issue filed by someone using the product (#683), and one closes the issue above.
Half of the substantive work in this release therefore arrived from outside the team rather than from a
plan, which is the pattern the inbound route exists to serve -- and the reason a check at its front is
worth more than its size suggests.

**What the release itself cost: 25m 02s** from clock start to a published Release with its attachments.
The cut to the pushed tag was **5m 12s** of that -- roughly 41 seconds of which was a person deciding what
the release is called, the rest being the gates and the generation running on their own. That head is in
line with the two releases before it (5m 36s and 5m 02s) and confirms the gates as the floor.

The remaining **19m 50s** is the tail: writing this document (3m 24s), its own gates (4m 08s), CI (7m 55s),
the merge with the fold (4m 02s) and the publish (21s). **That is the fourth consecutive tail inside a
seventy-second band** -- 19m 26s, 18m 47s, 19m 55s, 19m 50s -- while the head over the same span moved
from 15m 31s to about five minutes and stayed there. The tail is made of fixed legs and barely moves, so
the rising *share* it takes of the total is the head having been fixed rather than the tail getting worse.
Both series are given here for that reason; the percentage on its own would read as a regression.

Only about 4m 05s of the 25m blocked a person at all. The rest ran unattended, which is the number that
matters when deciding whether this is worth shortening.

## What was still open at this release

- **The merge re-runs the tests the pull request already proved.** Measured at roughly 3m 27s, 3m 18s
  and about three minutes across the previous three releases, and inside a 4m 02s merge leg here --
  consistent enough to be the largest single saving left in the release procedure. Named for the fourth
  release running and deliberately not acted on here. The next step sits with whoever picks up the
  release-procedure work.
- **Two specialists are *degraded* rather than excluded in the Claude App setting.** The map that decided
  what publishes found two agent definitions that name a script in one step of one procedure. Excluding
  them would lose a whole specialist over one line; publishing them silently hands a user a step that
  cannot run. They travel with that step named in their own description, which is a mitigation rather
  than a fix.
- **This release has not been published to the organisation.** Publishing is a separate decision from
  cutting, and it has not been asked for. Until it is, colleagues installing internally remain on the
  previously published set.
- **The copy attached to the GitHub Release is the version published at the moment of publication**, so
  it carries the head only -- the total above was added afterwards, in its own small edit, because a
  release note cannot time its own publication. The attachment is deliberately not replaced: an
  attachment is what was published when it was published, and silently swapping it is the opposite of
  the record this document is for. This page is the current version.
