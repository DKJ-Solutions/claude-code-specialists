# Release notes v4.18.0 🚀

**Date:** 2026-08-21  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

Consumer-reported repairs across the sync, the cut and the branch files, plus a shared Shopify preview push

## What changed

### If you run `team-shopify`, update before your next sync -- the version you have can revert merged work

**This is the one item in the release with a deadline.** v4.17.0 shipped the pre-task sync; this release
repairs it **four times**, and every repair is about the same thing: the sync overwriting work your trunk had
already merged. Nothing warns you. The run finishes green, prints a reference point that looks found, and
quietly reverts files.

**What to do**, and the dry run is new precisely so you can do it in this order:

```powershell
claude plugin marketplace update claude-code-specialists
claude plugin update team-shopify@claude-code-specialists --scope project
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/sync-main.ps1" -DryRun
```

`-DryRun` prints every file's verdict and writes nothing, and it is allowed on a dirty tree -- that being
exactly when you want to ask what a sync would do to it.

The four repairs, in the order they bite:

- **The rule now asks whose content live is holding, not when your trunk last touched the file.** The old
  question could not be answered correctly: nothing pushes your trunk *to* live except the per-file release
  step, so your trunk's changes are permanently invisible to live and sink out of the window as soon as one
  more sync lands. From then on every sync tried to overwrite them again, forever. Measured against a real
  store: 31 differing files, of which the old rule captured **all 31** and was about to revert three merged
  pull requests; the new rule correctly captures **zero**.
- **The floor is read off the commit subject.** A commit that merely *mentions* a sync in its body used to be
  able to become the reference point -- in one repo a `fix:` commit whose body read `sync-main.tests.ps1 goes
  from 20 to 32 asserts` became the floor, and eight commits of merged trunk work fell below it.
- **A merge commit can no longer become the floor.** If your repo answers `Get-ShopifySyncMerges = $true`,
  that is the path which produced it: right after a sync pull request landed, the floor became `HEAD` and
  **every** file on live won.
- **A theme filename with an accent in it is judged the same way on every machine.** Paths are read off git's
  wire format instead of off whatever console code page the run inherited. On an ordinary Windows OEM console
  `sections/café.liquid` decoded to two wrong characters, and live's identical file then read as content your
  trunk had never held -- foreign, taken, your version overwritten. Verified green at cp850, cp1252 and
  cp65001, and red at cp850 before the change.

**Three things the sync now refuses to do at all**, worth knowing before you point it at a store: it pulls
live into a mirror **outside** your repo and writes your working tree only for the files it decided live wins;
it **never deletes** (a path you have and live does not is reported, not acted on); and it decides the branch
name before the pull, so a collision stops the run while your tree is still clean.

**One flag is gone.** `-SkipPull` meant "run the rule over the working tree", which cannot mean anything now.
It is still accepted, so the refusal can tell you what replaced it.

### If you run `team-shopify`, you no longer need your own preview-push script

`push-preview` ships, so pushing a branch to its own unpublished preview theme is one command instead of a
script each repo wrote for itself.

```powershell
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/push-preview.ps1"
```

It resolves the target in four steps -- an explicit id, the id remembered in the branch's git config, a name
lookup, and only then creating the theme -- refuses the trunk, refuses live, and prints the preview URL.

**Preview themes are created lazily now, which is the part to notice if you create one per branch.** A Shopify
store has a hard ceiling of **20 themes**. Measured on one store the day the rule was made: 49 themes, 47
unpublished, and of the 12 real branch previews **6 belonged to branches that never needed one**. A preview
theme is a consequence of wanting to show something, not of starting work. `start-task` opens the branch and
leaves the theme to this script.

**One optional answer is worth writing**: `Get-ShopifyPreviewUrls`, if your store spans markets. That table is
genuinely per-store -- one consumer runs a single domain with locale-prefixed paths, another runs five separate
domains -- so nothing shared could fill it. Without it you still get one working URL rather than none, and it
already carries `_ab=0&_fd=0&_sc=1`, which a preview link needs in order to survive the first internal click.
Without those you are looking at live while believing you are looking at the preview; that cost a consumer a
whole review.

`Get-ShopifyLiveThemeId` is **recommended, not required** here -- unlike for `sync-main`, which cannot work
without it. This script warns and continues rather than blocking a preview.

### Your next release cut may refuse, and stating the type is the way through

`cut-release.ps1` now cross-checks the version it is bumping **from** against your release overview, and
refuses where the two disagree. **No action unless it refuses** -- and if it does, the refusal names both
numbers and where each came from:

```powershell
# only where the baseline and the overview genuinely differ -- tags used for something other than
# releases, per-component tags in a monorepo, imported history
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/release/cut-release.ps1" -Version 2.4.1 -Type patch
```

**`-Type` is deliberately not a `-Skip` switch.** A bypass would hand you back the very label the check just
caught; stating the type produces a correct release instead.

**Why this earns a refusal.** The baseline is taken from the highest `v*` tag, so **one stray tag** -- a
mistyped `v99.0.0`, a per-component tag, imported history -- silently relabels every later release, with no
policy decision by anyone. It is wrong in four places at once: the `**Type:**` line in the notes, the `Type`
cell in the overview, the question the bump gate answers, and whether a hand-written document is drafted at
all. The last two are the ones you cannot see. The consumer who reported this had to unpick a cut by hand
afterwards -- delete a document that should never have been drafted, correct `Minor` to `Patch` in two files,
and repoint an overview cell whose dead link would otherwise have failed their own lint.

`-NoPush` now also prints the baseline in its closing line (`4.17.0 -> 4.18.0, Minor`). The flag whose whole
purpose is reading a release before it is public was the one path that hid the number every label hangs on.

### Your next `open-pr` may refuse a dead link in a changelog entry

You write an entry in `workflow-davekjohn/branch/branch-deployment.md`, two directories down, and the fold
copies that text **verbatim** into `CHANGELOG.md` at your repo root. So a relative link in an entry has to be
written **root-relative** -- which looks wrong in the file you are editing and only becomes right after it
moves. Nothing said so, and the natural instinct produces the broken form.

**What to do: write entry links as if from the repo root.** `open-pr` now refuses to push while one is dead,
and the message prints the **root-relative form** rather than only telling you the link does not exist -- a
finding that says merely "does not exist" sends you to add another `../`, which breaks a link that was right.
The rule is also stated in the guidance block above the entry itself, so it reaches you before the gate does.
`branch-cycle.md` is deliberately exempt: that file never travels, so `../` is correct there.

### You can reap merged branches without writing the script yourself

`prune-merged` ships, for the local clone:

```powershell
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/prune-merged.ps1" -DryRun
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/prune-merged.ps1"
```

**It deletes only on proof** -- either the branch is an ancestor of your trunk, or a merged pull request proves
a squash. Anything with neither proof (unfinished work, a parked branch, a branch pushed from another machine)
is **kept, with the reason printed**. It refuses on a dirty tree before touching anything, fast-forwards the
trunk and never merges into it, and **touches no remote branch at all** -- that last one being a tested
property rather than a promise in a header.

**And `ship-pr` now tells you when your repo setting is off.** Where `delete_branch_on_merge` is `false`, you
learn it straight after a merge that has just left a branch standing, with the one-line fix:

```powershell
gh api -X PATCH repos/OWNER/REPO -F delete_branch_on_merge=true
```

That is a read, never a write, and it stays silent when the answer is already yes. **The merge itself is
deliberately not given `--delete-branch`**: the flag covers only the route it is passed on while the setting
covers every route, and it was measured leaving the checkout *on* the merged branch -- with `ship-pr`'s very
next act being the fold.

### If you host the release-notes page, rebuild it -- most of this pass was subtractive

The page had its second editorial round, driven by four reports from somebody reading the deployed page and
eight rounds of reading the built result. **No action beyond a rebuild and your own redeploy**, which stays
your decision because it is outward-facing.

What your reader gets: a row carrying only what differs between releases; `Version 4.17` instead of `v4.17`,
because a lone `v` is developer shorthand and this page's reader has no reason to know it; a chip only where a
row is **unusual** (measured here: 27 chips became 2); a masthead where each line says one thing; a summary
that stays in reach while they scroll a long note, so the control that closes it is never several screens away;
and closing a note puts them **back on the row they opened** instead of dropping them into the middle of a
suddenly shorter list. A note also stops restating the row it sits inside -- forty duplicated headings and a
rocket, gone on render rather than in your files, so it reaches notes **already published** too.

**`Get-ReleasePageMasthead`** is the new seam if you want your own wordmark above the title. Data-URIs and
base64 only, because a request to a third party leaks who is reading the page. Two marks, 32 KB each, 64 KB in
total -- each a warning, never a build failure. Two rather than five is a measurement: five read as a page
about the brands rather than about the releases.

### No action needed on these three

- **That `Error writing file` on a branch file is a harness guard, not a broken tool.** `new-branch` and the
  fold are the only writers that rewrite `branch/`'s pair out from under a session -- twice per cycle -- so
  both scripts now say, at the moment they print those paths, that the files must be re-read. One read
  re-syncs it and nothing is ever lost. Measured over three full cycles: 2 refused writes, 3 stale notices,
  and **0** cases of anything clobbered. Deliberately **not** suppressed: the refusal is what stops a session
  overwriting a change it never saw.
- **The entry form now says who its audience section is about, and that a short "not applicable" is a whole
  answer.** The heading `What makes this change extra special` named no reader, so it read as a general
  *anything else notable* slot. Measured in one repo in a single afternoon: two entries of 240 and 192 words
  under it, both scored `N/A`, against that repo's own norm of 28 to 78 words. The significance rubric's
  docstring now also states what a reworded band must not lose -- every built-in band is about **reach**
  ("they notice within a day"), and a repo that had retuned one into a statement about the diff duly produced
  a `4` at a tier whose reader cannot see the change at all.
- **A test-harness fragility that has nothing to do with your repo.** One assert in `prune-merged`'s suite was
  green in CI and red on a developer machine, because a console wrap could split the phrase it matched on. The
  script was correct in both places. It is named here only because `prune-merged` is new in your payload and
  this is its suite.

## What it is worth

**The commercial content of this release is one thing repeated four times: a script that reverts finished work
reports nothing.** v4.17.0 shipped the Shopify pre-task sync as the answer to two consumers having
hand-written one and destroyed work with it. This release repairs that shipped answer four separate times, and
every repair has the same signature -- no error, no warning, no slowdown, a green run, and files quietly
returned to an older state. That signature is why the four are worth a release rather than a footnote: the
failure cannot be noticed by the person running it, so the only protection is the version they have. Two
consumers are running the unrepaired one right now, and one of them carries a temporary hook routing its own
sessions away from the shipped skill -- a workaround whose stated removal condition is this release.

**The measurement that justifies a redesign rather than a fifth flag is the one that came back zero.** The old
rule was not buggy; it was asking the wrong question, and a wrong question cannot be repaired by fixing its
floor. Against a real store the old rule captured 31 files and was about to revert three merged pull requests,
while the new rule captured **zero** and was right to. A rule that is safe by capturing nothing would be
useless, so the same replay was run over every past case of real drift: **10 of 11** still come back and are
caught. That pair -- zero false positives, ten of eleven true positives -- is what a redesign has to show
before it is worth the disruption.

**Four of the consumer-facing items here were reported by consumers, and three of those reports were wrong
about something load-bearing.** One proposed refusing a cut only on the `-Version` route, when `-Bump` is the
more dangerous of the two. One claimed a consumer-side linter structurally could not check entry links, which
this repo's own lint has done since August 6. One concluded a flaky test was "not correctness", when underneath
it sat a production data-loss path on any theme file with an accent in its name. Each was caught by
re-measuring the report before building from it, and in each case the correct repair differed from the proposed
one. The reduced dependence on a developer is not that reports arrive -- it is that the house rule about
verifying a reason before repairing a symptom paid three times inside one release.

**The pattern worth carrying outside its own context: a guard whose failure mode is a green run has to be
tested from the failing side.** The sync's floor lookup had a suite, six asserts, and a docstring naming which
direction loses work -- and shipped with a hole, because every case asked what the lookup *finds* and none
asked what it must *not* find. The same shape produced the release page's chip rule, built as "render it where
the type varies", which answered *varies*, changed nothing, and was caught only when somebody asked why a
label was still there. Both are tests that confirm an intent instead of excluding a failure.

**One item is the opposite of a repair: it is the cost of a copy per consumer.** `push-preview` existed in
every Shopify repo as its own script, and the report behind this one came from a create path spelling a flag
the Shopify CLI has never had -- `--theme-name`. It failed the *first* time anybody needed a theme created,
written one day and reached the next. Nothing was wrong with the reasoning; the code had simply never run, and
a per-consumer copy means every consumer discovers that independently. The whitelist that ships with it earned
its place on its first run, by refusing the library's **own** call.

**Cost to here: 43m 55s** from the first command of the session to the moment this page was frozen for its own
pull request. Step 0a's baseline was taken before starting, so the legs are clock readings rather than
reconstructions: reading the repo's stand, the fourteen pending entries and the release seams, then the first
cut attempt and diagnosing the red gate through to opening its repair **22m 57s**; that repair's CI, merge and
fold **8m 53s**; the cut itself, including confirming the fold had landed, **4m 08s** (19:41:25 to 19:45:33);
inspecting the generated artefacts and pushing the commit and tag **39s**; and reading the 1,100-line draft,
re-reading each mechanism it names at its source, and writing this page **7m 18s**.

**The finding of this release's timing is that 73% of it was spent on a defect that had nothing to do with the
release.** The cut refused at its first command: one assert in `prune-merged`'s suite was red on this machine
and green in CI, and the local test gate is the only gate a release meets. Diagnosing it, repairing it and
shipping that repair came to **31m 50s** of the 43m 55s above -- before the cut ran at all. Two things follow,
and only one of them is about speed. The escape valve existed (`-SkipTests` would have cut in seconds) and was
the wrong answer, because the same gate blocks every pull request on this machine, so skipping it would have
moved the cost rather than paid it. And the wrong inference was cheap only because it was checked: the first
explanation of the failure was wrong, and building the repair on it would have shipped a second broken
normalisation on top of the first.

**What blocked a person, separated from what ran behind them**, since shortening the second is worth close to
nothing. Blocking: **35m 02s** -- the diagnosis, the repair, the cut, the inspection and the writing. Running
behind: **8m 53s** of CI on the repair, and that one is not really behind either, since the cut could not start
until it merged. This release had no idle leg to trim, which is itself the answer to "where did the time go".

**Three legs were still running on this file as it was written** -- its own local gates, its CI and merge, and
the publish -- so the total follows in the second pass step 0a asks for, once the number exists.

**Cost of this release: 63m 33s**, end to end, 19:09:35 to the Release published at 20:13:08. The three legs
the first pass could not see, all of them running on this file as it was written: this note's own local gates
and push **4m 37s**, its CI and merge **14m 19s**, and the fold plus the publish **42s**. The run was
continuous, so the wall clock and the working time are the same number.

**This is the longest release recorded here, at nearly double the previous longest, and the reason is not its
size.** 24m 34s for v4.15.0's thirteen entries, 25m 29s for v4.16.0's four, 32m 19s for v4.17.0's nine, and
63m 33s for this one's fifteen. The spread has never tracked the entry count and still does not: what made this
release expensive is that it needed **two** pull requests instead of one. A release normally ships one -- the
note -- and this one had to ship a repair first, because the cut refused on a red test gate. Two pull requests
means two full CI cycles, and CI is the single largest cost in here: **23m 12s** of the 63m 33s, or **37%**,
across the two.

**The head is 58% of this release, which inverts the claim the last six readings supported.** Clock start to
the tag being pushed came to **36m 37s** -- against 18% at v4.17.0, 21% at v4.15.0, 24% at v4.12.0, 26% at
v4.16.0, 30% at v4.13.0 and 32% at v4.14.0. Every one of those readings said most of a release happens after
the version number exists. This one says the opposite, and the mechanism is worth keeping rather than the
number: **a blocked cut moves work into the head.** The 31m 50s spent diagnosing and shipping the unrelated
test-gate repair all fell before the tag, because nothing downstream of the cut could start until it was done.
So the head/tail split measures where the obstacles were, not where the effort inherently is.

**The frozen subtotal was 43m 55s of 63m 33s, so the part this document could not measure about itself was
31%** -- far below 65% at v4.17.0, 66% at v4.4.0 and 70% at v4.16.0, and for the same reason. The unmeasurable
tail is roughly constant per release; it looks small here only because the head was abnormally large.

**And the reading the first pass got wrong is the one about which check governs the merge, so it is corrected
rather than confirmed.** That pass had only the repair's pull request to go on, where `lint-en-tests` (the one
required check) took 8m 37s against `claude-review`'s 3m 02s, and concluded the ordering had reversed from
v4.17.0. This note's own pull request says otherwise: `claude-review` **14m 05s**, `lint-en-tests` **9m 58s**
-- the non-required check governing again, exactly as at v4.17.0. So the honest tally across three readings is
**two to one** for the non-required check governing the wait, not the even split the first pass implied. The
variance is in `claude-review`, which ran 3m 02s and 14m 05s on two pull requests forty minutes apart, so what
is unstable is that check's own duration rather than the ordering. Still named and not repaired -- but the
direction of the evidence has changed, and a first pass that reported an even split on one data point is the
thing being corrected here.

## What was still open at this release

**The copy attached to the GitHub Release carries the frozen subtotal only, and stays frozen.** This document
cannot time its own publication, so the total above was added afterwards in its own small pull request, per the
two-pass rule -- and that same pass corrected the note's reading about which check governs the merge wait. The
attachment is deliberately not replaced: an attachment is what was published at the moment it was published,
and silently swapping it is the opposite of the record this document is for. **This page is the current
version**, and it is the one to read for the total and for the corrected check reading rather than the 43m 55s
the attachment stops at.

**The v4.18.0 tag holds a draft of this document.** The cut generates it from the entries in the words their
authors wrote for a diff reviewer, and commits it inside the tagged release commit. This page is the written
version and landed via its own pull request before the Release was published, so the attachment is this
document rather than the draft.

**Five sibling test suites carry the same harness fragility that was repaired in one.** `park-branch`,
`session-status`, `new-branch`, `find-specialist-mentions` and `shared-scripts` all render a captured child
refusal through `Out-String` before matching on it. They are green, so they were named rather than repaired,
under the rule that a risk which has not bitten gets written down. They have diverged on the part that does not
matter -- three different normalisations between them -- and agree on the part that does.

**Three follow-ups were measured and deliberately declined**, each with its measurement rather than a shrug:
per-process console isolation for the test suites, which would change how every child is created for a hazard
now a few lines wide; a `--grep` prefilter on the sync floor, which would put two regex engines in the
correctness path for a **46 ms** saving, on a pattern a consumer supplies; and an optional contract check for a
retuned significance band, declined on the reporter's own reasoning that flagging a band with no reader pronoun
is a heuristic.

**One test gap is declared rather than papered over.** `ship-pr`'s new setting check has no suite: it runs only
after a real merge, and splitting it into its own script is not worth it for one read and one printed line.

**Whether `ship-pr` should wait on the required check alone stays open, and this release supplies two readings
rather than one.** At v4.17.0 a non-required `claude-review` took 15m 09s and governed a merge whose required
gate finished in 9m 29s -- 48% of that release. This release's two pull requests disagree with each other: on
the repair, `lint-en-tests` (required) took **8m 37s** against `claude-review`'s **3m 02s**, so the required
gate governed; on this note, `claude-review` took **14m 05s** against `lint-en-tests`'s **9m 58s**, so it did
not. Across three readings that is **two to one** for the non-required check governing the wait, and the
unstable quantity is `claude-review`'s own duration -- 3m 02s and 14m 05s on two pull requests forty minutes
apart -- rather than the ordering. Still named and not repaired: the case for changing what the merge path
waits on is stronger than it looked an hour ago, and a check whose runtime varies fourfold is the thing to
understand first.

**This release had not been published to the organisation.** Publishing is a decision separate from cutting and
was not asked for. Read at the target rather than carried forward: `BWJ-ecommerce/claude-plugins-bwj`, commit
`84e6316`, 2026-08-20T12:19:05Z, all four team plugins at **4.16.0** from their own `plugin.json` files -- now
two releases behind.

**Every registered consumer is one release behind as of this cut**, which is the definition of having cut
rather than a finding: all four were on v4.17.0 and current until this moment. That is a consumer-side
`claude plugin update`, which the source cannot run for them, and the session check reports it on their own
machine. The refresh is the safe first step, because `plugin install` does **not** advance a `github`
marketplace's cached clone:

```powershell
claude plugin marketplace update claude-code-specialists
```

**Nothing was open as an issue at the moment of the cut**, on either the inbound queue or this repo's own:
`gh issue list --state open` returned empty. Every report answered in this release arrived and closed inside
the same working period.
