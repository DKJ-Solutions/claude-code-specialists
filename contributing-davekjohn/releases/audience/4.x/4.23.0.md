# Release notes v4.23.0 🚀

**Date:** 2026-08-29  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

the first full adoption test run's findings, repaired -- the fresh-repo path and the shipping cycle

## What changed

**This release came out of one exercise: adopting this family on a brand-new repository and walking the
whole contribution cycle on it, from `gh repo create` to a published Release, using only the shipped
documentation.** Everything below is what that run hit, plus the shipping-cycle repairs that landed
alongside it.

Two items ask something of you: **1** is a file to delete, **2** is a seam to check. **3 to 6** are
behaviour changes you will meet on your next branch -- two of them are new refusals. **7 to 10** matter
on the day you adopt this on a fresh repo. **11 onward** arrive on their own and ask nothing.

### 1. If you ever adopted `/lock` and `/handover`, delete `.claude/handover.md` -- act on this

Those two commands were retired in `v4.21.0`, and **no release note told you**, because the entry that
retired them was scored as not reaching you. Nothing you have written stops working. But if you adopted
the convention while it existed, a `.claude/handover.md` is still sitting in your repo, and **nothing in
a plugin update reaches into your tree to remove it** -- so it is dead weight that still reads as live
session context.

Measured on the consumer side two days after the removal: exactly that file was read as live context in
a session and then updated, because it was still there and nothing said the mechanism was gone.

The rule that let it pass is repaired: the audience-tier question now states that an entry retiring
something an earlier note told you to adopt is **never** "not applicable" for you. The next retirement
announces itself.

### 2. If your repo never answered `Get-ReleaseConsumerBumps`, your releases write no note for you -- act on this

Two shipped pages said that seam defaults to `('minor','major')`. **It defaults to `@()` -- the consumer
tier switched off.** So a repo that never answered it drafts this hand-written note for *no* bump at all,
while the `cut-release` page you read while cutting told you your minors and majors already produce a
draft. `('minor','major')` is this source repo's own answer, promoted into two texts as though it were
the shipped fallback.

**Anyone on `4.22.0` reading that page is reading it wrong today.** Check `Get-ReleaseConsumerBumps` in
your `scripts/repo-config.ps1`: if it is not there, answer it. Nothing computes differently -- the
fallback and the functions are unchanged, and an unanswered seam has to keep meaning what it meant
yesterday. What changed is the wording, so the page stops describing a document your repo does not
produce.

Nothing was going to catch this for you: `check-script-contract` reports a missing optional seam
together with its declared fallback and never judges whether that fallback suits your repo, so it
printed the correct text while the page said the opposite.

### 3. A backgrounded ship gives your checkout back before it waits -- no action

`ship-pr` merges and folds on the trunk, and it did not go there until after the CI wait. Backgrounding
the run is the default, so the ordinary shape of a shipping session was: work finished, pull request
open, the session reported as clear -- and the tree still standing on the branch.

**Step 2b now hands the trunk back the moment the pull request exists.** It costs nothing, because
nothing after that point reads the working tree. Three conditions guard it and none of them refuses a
ship: the primary checkout only, nobody else holding the trunk, and a clean tree. A tree that cannot go
home stays where it is and says which of the three it was.

`prune-merged` had the same shape and is repaired with it: it borrows the checkout for its fast-forward
and now **gives it back**. It used to switch to the trunk and stay there -- silently, with a clean tree
and nothing in `git status` to show for it, so the next commit of that session landed directly on
`main`. Two starts cannot be returned to, and each says so while naming the sha it left.

### 4. A finished lane hands the trunk back, and `ship-pr` refuses before the merge instead of after -- act if you use worktree lanes

`ship-pr`'s fold step checks `main` out in whatever tree it runs in. In your primary checkout that is
deliberate. **In a worktree lane it took a lock that is global to your clone** -- git allows one worktree
per branch -- and nothing warned you: the bill was paid later, by an unrelated branch, at the moment it
costs most. Measured once as the exact half-state the fold exists to prevent, with the merge already
irreversible and the changelog unfolded.

Three changes, in the order they fire. A **step 0** asks whether another worktree holds `main` and
refuses there -- before any gate runs and before anything is pushed or merged -- naming the directory
and the commands that release it. The fold's in-place arm now carries the same hand-fold instruction its
worktree arm always had. And **step 5b** returns a lane to its own branch once the fold succeeds, which
is where the lock was being created.

`prune-merged` -- unavailable in exactly the situation that produces stray branches -- now names the
worktree holding the trunk instead of relaying git's message.

**You may meet a refusal where the command used to run.** That is the repair. If you do not use lanes,
nothing changes for you.

### 5. The fold refuses a second entry for a branch that already has one, and a re-run `ship-pr` says the work has landed -- act on this if you re-run ship-pr

Re-running `ship-pr` on a branch that had already shipped used to end in a PowerShell error naming your
`gh` authentication -- on a finished branch, in a run where `gh` had just listed PRs, pushed and read
issues. **An already-merged PR is now its own outcome**, reported with its number and url, exiting 0
before the gates, the push and the create. Where a create does still fail, the message carries gh's own
reason instead of a fixed guess.

The route that closed had a second end, now guarded: the fold would write a **second** entry for a
branch the changelog already carried, and report both runs as a success -- measured in a consumer as two
entries, same branch, same text, two PR numbers. Nothing downstream refused them, so a release counted
the duplicate twice and printed it twice in the published note. The fold now refuses, naming the PR of
the entry already there, leaves your entry file on disk and exits non-zero. **`-Force` folds anyway.**

Refusing is safe here for a reason that does not generalise: an entry refused for a missing score leaves
merged work with no record, while a duplicate refused leaves the record already standing.

### 6. `new-branch` warns when the base you are cutting from is behind `origin`, and the step-list gate names the act each finding needs -- no action

`new-branch` now measures the base it is about to cut from and **warns** when it is behind
`origin/<trunk>`, naming the count. It warns rather than refusing, and says it twice -- once before the
checkout, once as the last line, because the scaffold, the commit and the push all print in between. A
repo with no `origin/<trunk>` is neither asked nor warned, which keeps the script usable offline.

What it prevents was measured, not imagined: a branch cut from a trunk 17 commits behind `origin/main`,
to fix an issue another session had closed by a merged PR four minutes earlier -- producing a complete
duplicate of already-merged work, branch, commit, PR, every gate green on both.

Separately, the **step-list gate** stops repeating advice that cannot work. It refuses on two different
findings and printed one remedy for both -- *resolve each step, `- [x]` or `- [~]`* -- which is the whole
answer for an open step and no answer at all for a line still carrying the scaffolder's placeholder: a
placeholder is resolved by replacing its text, and a mark cannot do it. Follow that advice on the second
finding and you were refused again by the same four lines. Each finding now carries the act that clears
it. The gate itself is unchanged, and there is still no `-Force`.

### 7. The adoption hands you an `allow` half, not only a `deny` half -- act on this when you adopt

`specialists-init`'s `settings.suggested.jsonc` carried `deny` alone, so following the adoption to the
letter produced a repo that **forbids the five things the workflow must never do and permits nothing it
must do**. You are the only one who can widen a permissions file -- a session cannot and must not -- and
until now nothing handed you the lines to paste.

The `allow` half now carries your workflow's three entry points (`new-branch`, `open-pr`, `ship-pr`, in
both tool shapes) plus the single `gh repo edit --delete-branch-on-merge` the workflow assumes.
`cut-release` is deliberately absent: a release is worth a prompt. Enable no workflow and the half is
emitted **empty and says why**.

**The paths in those rules are wildcarded on purpose -- do not "fix" them into absolute paths.** The
plugin root resolves to the version-pinned install, so a rule carrying today's path stops matching at
your next plugin update, silently, while still reading as covered.

### 8. Enabling a plugin is not installing it, and the adoption now says so -- act on this when you adopt

`INSTALL.md` and `ADOPTION.md` now say plainly that a repo can look **completely adopted** and carry no
plugin surface at all: the `enabledPlugins` key is yours, the install record is the machine's, and
setting the first without the second leaves a session with no skills, no subagents and no hooks while
every visible surface says the adoption is done. Measured on a repo that ran that way for a full working
day, two merged PRs and a release.

Both pages name the check, and both name it as the **slash-command menu** rather than anything the
session says about itself: several skills ship `disable-model-invocation: true` on purpose, so a healthy
session lists *fewer* skills than the plugins ship and a count read off that listing means nothing.
`INSTALL.md` points at a query that needs no plugin at all.

And both now say the part that makes this recur: **all four checks that report this state ship inside
the plugin that is not installed**, so the one repo they were written for is the one repo they cannot
speak in. Their silence is the symptom, not an all-clear.

### 9. The adoption commit lands on the trunk, and the pages say so -- no action

Your first commit -- the seam, the lenses, the script scaffolds, the workflow folder -- **cannot** travel
through the cycle it is installing, and that is not a preference: `new-branch` refuses without
`scripts/lib/branch-info.ps1`, which is one of the files that commit puts down, and the lint, test and CI
gates are all downstream of it too.

Worth writing down because the documents you are handed the same day say the opposite as a rule. It is
one exception, it is spent by using it, and it is now stated at the bootstrap step of `ADOPTION.md` and
beside the rule in `CONTRIBUTING-portable.md` -- so your own contributors find it a year later without
reading the adoption page.

### 10. What the cycle does in a repo that cannot have a required check -- no action

A private repository on the GitHub Free plan cannot have branch protection, and that is the shape most
new repos start in. The contributing page described the merge as waiting on "whatever status check your
branch protection requires" and stopped there, so the first reader on a fresh repo met a mechanism they
had no way to switch on.

What happens instead is good news, now written down: the wait covers **every** check the PR has rather
than only required ones, so it works with no ruleset at all; and where nothing is required, the merge
verdict cannot tell *"this repo requires nothing"* from *"the required checks have not reported yet"*, so
it **refuses on a red check** rather than proceeding. A repo without a ruleset is guarded conservatively
rather than left open.

One output line changed with it: the fallback that read *"which check governed could not be read"* --
reported as sounding like a fault -- now reads *"no readable check facts, so nothing to report about the
wait"*, which is the condition it actually fires on.

### 11. Seventeen relative links in your installed copies were dead, and a gate now stops the next one -- no action

The lint gate could not see the one class of dead link that reaches you. Links were resolved against
this source tree -- the single tree where they are guaranteed to work -- while you read the same file
from the plugin cache, where the `plugins/` level, the family level and every sibling plugin are gone.

**Measured on arrival: 17 escapes in 5 files, all dead in the copies installed today, all repaired
here.** They sit in payload you read -- the `specialists-init` and `specialists-teardown` skills, the
workflow's README and scripts README, and the `cut-release` skill. `specialists-init` alone had 8 of its
9 relative links landing on nothing. They work from this release onward.

A new check holds the boundary at the **plugin root** rather than at `plugins/` -- the difference is the
whole check, because the weaker rule passes a link into a sibling plugin, which is equally dead.

### 12. Relative links in your changelog entries survive the release cut -- no action

If your changelog sits in `contributing-davekjohn/` rather than at your repo root, **no relative markdown
link in an entry could survive both hops it has to make.** The link gate judged a link from the
changelog's own directory -- correctly, since the fold copies the entry text there verbatim -- while the
release cut rebased it as though it had been written against the repo root, one directory too far. The
form the gate demanded landed in the tagged release record pointing at nothing; the form that survived
the cut was refused before the PR could open. The measured workaround was to write no relative links at
all.

The cut now measures from the changelog, and `../` is rewritten with everything else -- it had been
exempt since the rewriter existed, on the reasoning that a link climbing out of a directory had been
aimed by hand. With an isolated changelog that stopped being true: `../` is the ordinary form, and the
one the gate hands you when it refuses something. The cut was skipping exactly the links the gate had
just dictated.

**A repo whose changelog is still at the root gets the old answer byte for byte.**

And a link written inside a code fence, an inline code span or an HTML comment is now left exactly as
written -- it is an illustration of a link, not a link, and the cut used to rebase it into a tagged,
immutable document with an extra `../../../` on the front.

### 13. `ship-pr` tells a stalled Actions run apart from a check that went red -- no action

When a workflow run fails to *start*, `ship-pr` now says **"CI never RAN"** instead of reporting a check
that went red. Measured in a consumer repo: Actions stopped starting jobs because an account payment had
failed; every run ended in about four seconds with zero steps, no logs, and no annotation on the
ordinary run page. The old message pointed the reader at their own code for a state no branch can repair
and no re-run will change -- and one PR was merged by hand as a result, the habit this workflow exists
to prevent.

**The merge decision does not move.** Refusing on an unreadable required-check list is the conservative
half and it still refuses, on exactly the same payload. What changed is the sentence you read beside the
refusal, and it names the single command that prints the reason.

### 14. `prune-merged -IncludeRemote` classifies the heads it used to only name -- no action

`git ls-remote --heads` is the only read that surfaces a **parked** branch, and in it a merged leftover
and live parked work look identical. Telling them apart was four commands per head, redone every time.
Measured three times in two days; twice the session also had to hand-write a *don't sweep this one*
warning about somebody else's live head.

Every head that is not the trunk now goes through the two proofs the script already computed for local
branches, and prints one of two things: the paste-ready delete command for a head it can prove is
merged, or `Kept origin/<branch> -- live work` for one it cannot. **It runs neither** -- what was
declined was *executing* a remote delete, and handing the command over paste-ready is what that decision
says should happen instead.

### 15. Smaller corrections to pages you read -- no action

- **The `new-branch` skill page** promised a version-suffix scan "checked against the branches that exist
  locally and on the remote". It does not do that and never has: it appends `-v1`, full stop. Worse, its
  stated consequence was the reverse of the real behaviour -- a second run on the same name **resumes**
  the `-v1` branch rather than making a `-v2`. You have the mirror and that page, not the source tree, so
  for you the false statement was the only statement.
- **`DEVELOPMENT-portable.md`** no longer tells you to report the standing gates as an *outcome* in TEST
  -- which could only be answered by hand-running the very suites your push is about to run. The example
  now cites them as **coverage**. `- [~]` still means "no suite", never "no verification".
- **The `v4.22.0` note** has a correction section. Its claim that the test suites cost 443s, and its
  attribution of a red gate run to who invoked it, were both falsified hours after publication -- the
  gate costs about 200s on that tree, and no caller axis ever existed. The timing row itself is frozen
  and untouched, because it was true when typed; the two sentences built on top of it are marked
  corrected.
- **The connector-register block** `specialists-init` prints now carries a row for **every** enabled
  plugin of this marketplace, not only the ones shipping an `agents/` directory. If you pasted that
  block before, the workflow plugin was silently missing from your manifest -- and an absent row looks
  exactly like a plugin you never enabled, so the version-gap warning could not fire for it.

## What it is worth

**The measurable win is the first day on a new repository.** The exercise behind this release was a full
adoption on a virgin repo, and the run before it cost a working day that produced two merged PRs and
almost nothing else -- the time went on blockades, not on the repo. Every one of those blockades is
either repaired here or written down: the permissions block now hands over lines a person can paste, the
adoption says which of its two acts can silently be missing, and the one commit that cannot follow the
rules says so instead of leaving the reader to choose between two wrong exits.

**The second win is smaller per occurrence and constant.** Three separate scripts used to leave a
checkout somewhere other than where the session reported it: a backgrounded ship stood on the branch, a
`prune-merged` silently kept the trunk, and a finished lane held `main` for the whole clone. None of them
errored. Each one cost a session that had been told it was finished -- and in one case produced a
half-merged state that had to be repaired by hand. They all end on the trunk now, and the one case that
cannot says which of three reasons it was.

**And one class of failure moved from invisible to gated.** Seventeen relative links in the payload
consumers install were dead in every copy shipped so far, discoverable only by a reader clicking one.
That is now a lint check, so the eighteenth is caught before it is published rather than after.

Cost of the release itself: 30 changes folded, cut end to end in a single session while a second session
worked the same board in parallel.

## What was still open at this release

**The adoption test run has not been repeated yet** -- that is
[#1079](https://github.com/DaveKJohn/claude-code-specialists/issues/1079), and it is the only issue left
open on this repo at the time of writing. Its exit criterion is a complete run on a **fresh** repository
that files nothing; the run behind this release filed five findings, all of which are repaired above.
The next run starts on a new `ccs-testrun-<n>`, never on a repo a previous run touched, because the state
that broke the last run is exactly what a repeat would inherit.

**A fix does not need a release to reach that run.** The marketplace clone tracks `main`, so a merged
repair arrives after a marketplace update -- this release is not a prerequisite for the next test run,
and cutting one per iteration is deliberately not part of that loop.

**One deliberate leftover on the maintainer's side:** `ccs-testrun-1` is left standing with `v0.1.0`
published and a duplicated changelog entry **not** repaired -- it was the evidence for the
duplicate-fold guard shipped in item 5 above. It can be deleted now that the guard is in.
