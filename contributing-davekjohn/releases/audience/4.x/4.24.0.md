# Release notes v4.24.0 🚀

**Date:** 2026-08-29\
**Type:** Minor\
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

A fresh repo can walk the adoption path from install to its first release

## What changed

**This release closes the second full adoption test run.** A brand-new repository was taken from
`gh repo create` to a published Release using only the shipped documentation, and everything that
stopped or misdirected that run is repaired here -- together with the reporting repairs that landed
alongside it.

**Two items ask something of you: 1 and 2.** Both are one check on a repo you have already adopted, and
both are quick. **3 to 6** are what you meet on the day you adopt this on a fresh repo, and they are the
bulk of the release. **7 onward** arrive on their own and ask nothing.

### 1. If you filled `settings.json` from the suggested file, confirm it parses -- act on this

The instruction that tells you to copy the desired parts of `.claude/settings.suggested.jsonc` into
`.claude/settings.json` did not warn you that the `//` comment lines have to go. `settings.json` is
strict JSON, and Claude Code discards the **whole file** when it fails to parse.

**That is the part worth acting on.** If your `settings.json` was filled that way and carries a comment,
then `deny` (`git push --force`, `git reset --hard`, `rm -rf`), `allow`, `enabledPlugins` and
`extraKnownMarketplaces` have **never been in force** -- behind one startup line that says *malformed
JSON* rather than *your safety rules are off*. Open the file, check it parses, strip any `//` lines.

The instruction now says so where you read it.

### 2. If a session-start line ever told you to "re-install at project scope", you did not have to -- act on this

`[RECORD-SHAPE]`'s pathless line fired at every session start, in every repo, for a shape that is
usually deliberate: a plugin you installed machine-wide, in a repo that never project-installed it. It
read that as a demotion and closed by telling you to convert it into a per-repo install.

**If you followed that instruction, you now have a project-scope record you did not want**, and your
deliberate machine-wide install was converted. Nothing is broken; you may simply want it back the way
you had it.

No predicate can separate the two states -- a demotion writes `scope=user` and drops `projectPath`,
which is byte-for-byte an ordinary user install. So the line still fires, because a genuinely lost
record must not go back to being unreported, but it now states what it can see and asks you the one
question the register cannot answer, with both answers written out including the one where nothing
needs doing.

### 3. Adoption no longer requires guessing who runs the bootstrap -- adoption day

Four places told the reader to run `specialists-init`. That reader is usually the model, and
`disable-model-invocation` structurally forbids it -- while the same flag hides the page that documents
the route, so the session could not even learn the skill exists. A fresh session was told to act, with
nothing it could act on, one absolute path away from running the bootstrap itself: exactly the
substitution the refusal exists to prevent.

All four sites now name the command **and who types it**. The flag stays, deliberately -- dropping it
would load that skill's description into every session of every consumer forever, for something that
happens once per repo -- and that decision is now written on the skill page instead of left implicit.

### 4. A session can reach the orchestrator *during* adoption, not one restart after it -- adoption day

The `orchestrator` skill is the route to Chris wherever the `@`-import cannot reach, but its description
offered three situations and a repo mid-adoption was in none of them: it has a repo, it has a
`CLAUDE.md`, and its specialists did not arrive in an app. The one channel that is always in context
before the bootstrap was telling the one session that needs it that it is for somebody else.

It now names that repo, and says in a clause what is missing until the bootstrap runs. The page gained a
closing section for the same reader, stating that the handover to `/team-alpha:specialists-init` is
still the whole move -- the bootstrap writes **your** `CLAUDE.md` and is yours to authorise.

### 5. Your session is told, before the bootstrap, that filing what it finds needs no permission -- adoption day

Everything a session finds while adopting -- the moment it is least equipped and has the most worth
reporting -- reached this repo only if that session knew filing an inbound issue needs nobody's
permission. That rule lived in the orchestrator's body and the agent-def bodies, and neither reaches a
pre-bootstrap main loop.

Worse, our own `CLAUDE.md` listed *"issues on other repos"* among the acts needing explicit permission,
with no carve-out -- and the bootstrap tells you to model your governance on that file. Two of our
statements disagreed about the same act.

`ADOPTION.md` now states all three rules a session needs before it has Chris, says out loud that they
are not in session context yet, and tells you to check your own safety rules for the same
contradiction. `CLAUDE.md` names the carve-out.

### 6. Cutting your first release stops tripping over your own repo -- first-release day

Three defects, all in the layer a fresh consumer meets first, and two of them arrive on that one
command:

- **The cut no longer reads an ordinary root document as an unfolded changelog entry.** Its branch-name
  test scanned *every* heading, so a single backticked word anywhere below the title declared a branch
  and stopped the release -- close to unavoidable in a technical repo. It now reads only the opening
  heading, which is where a real entry declares itself. And when it does refuse, it names
  `Get-ReservedRootMd` beside the fold, because *"fold them first"* is the right remedy for one of the
  two ways that gate fires and a **destructive** one for the other.
- **The release documents no longer carry trailing whitespace**, so your trunk is not left failing its
  own lint gate on files the release just wrote -- at the one moment the tree is least inspectable. The
  cut runs its gate before those documents exist, so it could never catch its own output.
- **The `CHANGELOG.md` that `adopt-workflow-folder` scaffolds now states the heading level the fold
  actually writes**, composed from the constant so the sentence cannot drift from it again.

### 7. A red check that does not block your merge now tells you why -- no action

`ship-pr` reads a failing check's annotations and prints the sentence that workflow wrote about itself.
A red `claude-review` arrives as *"out of quota -- the review did not run ... resets Aug 31, 7am (UTC)"*
instead of as a red mark with a log to hunt through.

The rule is generic: a failure annotation **carrying a title** was written by a workflow author, while
the runner emits its own untitled *"Process completed with exit code 1"*. Nothing is keyed on a check
name, so your own workflows get the same relay.

This was the eighth thread about the same red check -- one of which concluded a secret needed rotating,
against a log already reading `429`. The reason had been printed since an earlier release; what was
missing was a reader standing where it was printed.

### 8. The quota headline no longer vouches for when work resumes -- no action

It still tells you the account is out of quota and which limit it hit. It no longer tells you **when**,
because that half is upstream's and has been measured wrong by 2.5 days. The headline names the
discrepancy and attributes the time to upstream, so nobody writes off three days that turn out to be
forty minutes.

The repair went into the workflow that writes the sentence, not the relay that carries it: the relay is
generic on purpose and cannot know which authors are reliable, so a caveat there would caveat every
workflow in every consuming repo.

### 9. Nothing in a plugin now tells you to run a skill you are barred from running -- no action

The lint gate refuses a printed instruction naming a skill whose frontmatter carries
`disable-model-invocation: true`. Seven sites carried a bare imperative and are repaired. The rule is
frontmatter-driven rather than a phrasing convention, which is what lets an unflagged skill go on being
named the same way.

It was offered as optional a month ago and deliberately not built, under the rule that a risk which has
not bitten gets named rather than repaired. It is built now because it bit twice, a month apart, with
nothing connecting the two.

### 10 to 13. Reporting and housekeeping -- no action

- **The two caps bounding a red review's explanation now carry the arithmetic that relates them**, and a
  test that fails the day either moves. Neither number changed, and that is the finding: the tighter cap
  hands the reader the identical text, drops the `...` marking the loss, and spends a second reader's
  margin.
- **The roster hook's handover speaks to you in your own voice** -- *"that command must be TYPED by the
  repo owner"* rather than *"ask the repo owner to type"*. You are not a third party to yourself, and a
  SessionStart hook is the first thing in context on a fresh consumer.
- **The one `.ps1` in the tree carrying a byte-order mark loses it.** Nothing was broken and no gate
  changed; the odd file out is back in line.
- **The internal note's `Date:` and `Type:` labels render as three lines** rather than one, completing a
  repair that had reached the other three release documents.

## What it is worth

**The adoption of this way of working on a new repository stops being a developer-shaped task.**

That is the whole of it, and it is measurable in the two runs behind this release. The first full test
run reached a published Release but needed five repairs and a bridge placed by hand. The second reached
it needing three, and both of its bridges were one line. What is left in this release is the third
attempt at the same question: whether somebody can take a repository they have just created and be
working inside the agreed process the same afternoon, without a developer sitting beside them to
interpret a refusal.

**The risk being removed is the silent kind.** Two items in this release are cases where something read
as working and was not: a `settings.json` whose safety rules were never in force because a comment line
made the file unparseable, and a session-start line that told every consumer with a machine-wide install
to undo it. Neither produced an error anybody could act on. Both were found by walking the path as a
newcomer rather than by reading the code, which is why the test run exists and why it is repeated on a
fresh repository each time rather than on the one that was already fixed.

**The dependence being reduced is on the person who wrote it.** Every defect in this release was
reported from inside a consuming repository by a session that had no access to this codebase. That only
works if such a session knows it may file what it finds without asking -- which, until this release, our
own governance file contradicted. Items 3, 4 and 5 are all one thing: the reporting channel now works
before the tooling that describes it has been installed.

## What was still open at this release

**A snapshot at the moment of the cut, not a claim about the present.**

- **The third adoption test run is planned but not yet run.** Its runbook is written and posted on
  [#1079](https://github.com/DaveKJohn/claude-code-specialists/issues/1079), with every correction from
  runs 1 and 2 folded in, and it sits with `davekokbwj`. The exit criterion is unchanged and has not yet
  been met: a run passes when it files nothing.
- **One known trap remains unmeasured after two runs, and run 3 is the first to test it on purpose.**
  Both previous runs kept a healthy install record throughout, so what a session does *when that record
  is missing while the plugins are enabled* is untested rather than disproved. Run 3 enters that state
  deliberately and restores it afterwards.
- **`ccs-testrun-1` and `ccs-testrun-2` are still standing** as the evidence behind their findings, and
  neither is registered as a connector -- a throwaway repository in the register would add a permanent
  row to every session check here.
- **Nothing else was deliberately left.** The issue tracker was empty of everything but #1079 at the
  moment this release was cut.
