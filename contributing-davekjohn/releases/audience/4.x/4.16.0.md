# Release notes v4.16.0 🚀

**Date:** 2026-08-20  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

The Shopify floor gains the install path it shipped without

## For consumers

### If you run `team-shopify`, one command now places the floor -- and arms the guard v4.15.0 left half-armed

`team-shopify` gains an `adopt-shopify-floor` skill. It writes the three things the plugin could not: the
Shopify seam block appended to your `scripts/repo-config.ps1`, a starter `.theme-check.yml`, and
`.github/workflows/theme-check.yml`. It is additive and a **dry run by default**, like `adopt-config` and
`adopt-workflow-folder` -- it prints the plan and touches nothing until you add `-Apply`.

**What to do**, if you saw the standing `[ERROR]` at session start after v4.15.0:

```powershell
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/adopt-shopify-floor.ps1"
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/task/adopt-shopify-floor.ps1" -LiveThemeId <id> -Apply
```

Your live theme's id is the one marked `[live]` in `shopify theme list --store <your-store>.myshopify.com`.
Give it and the guard's third rule -- a push aimed at the live theme **by id** -- starts firing; omit it and
the block lands commented out, and the session check keeps reporting. That is deliberate: a placeholder in
this seam would silence the report without arming anything, because the check reads any non-empty answer as
answered. Both the guard and the check now reject a **non-numeric** id, so a half-answer cannot pass either.

**Nothing about the other two rules changed.** A theme publish and a theme delete were refused before this
release and are refused after it, with or without the seam.

**If you wrote your own live-theme guard, you are now running two**, and the session check says so once per
session. A `PreToolUse` command in your own settings naming this guard is by construction a second one, and
two guards block every command twice. The README gained a *Converging off a hand-written guard* section
saying what to delete and what to keep.

**Your starter `.theme-check.yml` is `extends: nothing` plus two syntax checks** -- Liquid that does not
parse, JSON that does not parse -- and the CI workflow runs at `--fail-level error`. That is not a loosened
gate; it is exactly the two checks the config declares, at the severity it declares them. It is deliberately
green on a real theme rather than on an ideal one: the recommended set reports over 1,500 offences on one
existing theme and roughly 58,000 on another, and a gate that is red the day it arrives is a gate you switch
off in week one. Turn more on when you want them.

### `/handover` no longer reports a stale lock as work you need to do

If a `/handover` pickup finds that your locked topic has been overtaken, it tells you -- and some sessions
carried that further, putting "the lock is stale" at the top of the answer as the thing most needing action.
Step 3 now says where that stops: **a spent lock is spent, not broken.** Naming the change is the whole of
it. Your pickup will not offer to clear the lock, propose re-locking it, or list it among what is still open.

**No action needed**, and nothing about `/lock` or the file it writes changes. What changes is the first
paragraph you read after a `/handover`, which stops spending itself on a mechanism that was working.

### The v4.15.0 release note you received is the written version, not the draft

The document attached to v4.15.0's Release is the rewritten one: twelve of that release's thirteen entries
reached you, ordered so the three items carrying an action open the page, with every remaining item saying
**no action needed** rather than leaving you to infer it.

**No action needed.** It is named here because the draft and the written version are two different documents,
and it is the written one you want if you are deciding whether to take v4.15.0.

### That note now carries what the release cost, end to end

**24m 34s**, of which writing the page was 9m 37s and waiting for CI and the merge 8m 22s. If you run this
workflow, that page is your worked example of the two-pass timing the checklist asks for: a subtotal frozen
when the document is written, and the total added afterwards, because a document cannot time its own
publication.

**No action needed.**

## What it is worth

**A guard that reads as protection while one of its rules cannot fire was the default on install, and this
closes it at the only place it could be closed.** v4.15.0 shipped the live-theme guard and it worked
immediately for publish and delete; the third rule needed the consumer to name their live theme, and no step
in any install path owned that answer. An install writes nothing into a repo, so every consumer who refreshed
met the same standing error. Asking each of them to notice and repair it individually is the arrangement that
does not scale -- one command that places all three files does, and it is the same shape as the two `adopt-`
commands already in the workflow, so nobody has to learn a new one.

**The reduced dependence is on nobody hand-writing operational floor twice.** Before this shipped, both
Shopify repos had independently written their own theme-check config, and both had arrived at the same two
checks over `extends: nothing`, with the same exemption for the same false positive. That is the plainest
possible evidence that the content belonged in the product: when two teams derive an identical artefact from
the same paragraph, the paragraph was doing a script's job. What each repo still owns is the one answer only
it has -- which theme is live.

**The finding worth carrying out of this release is about a proposed repair, not about the defect.** The
report that named the problem also named the cure: scaffold the seam with a `VUL-IN` placeholder, the way
every other seam in this system is scaffolded. It reads as obviously right, and it would have made things
worse. The convention works elsewhere *because* those seams have documented fallbacks -- absence means "use
the fallback", so a placeholder reads as a question waiting for an answer. This seam has no fallback, and the
check reads any non-empty answer as answered. A placeholder there does not prompt the question; it cancels
it, and leaves a hole with a comment on it. The block therefore lands commented out, and both readers now
reject a non-numeric id, so the counter-case is asserted from both sides. The reporter was right about the
symptom, right about the cause, and wrong about the lever -- which is the third of the three things a report
can get wrong, and the most expensive, because a wrong lever ships as instruction.

**A green-on-arrival default was chosen deliberately over a correct-in-principle one.** The recommended
theme-check set reports over 1,500 offences on one live theme and roughly 58,000 on another. A gate that
fails the day it is installed is bypassed the day after, and then the repo has neither the gate nor the
honesty of not having one. Shipping the two checks that pass, at the severity they declare, buys a gate that
is still running in a month.

**The loop from report to answer closed inside one day.** Three consumer reports arrived within nine hours of
v4.15.0 being cut, and all three are answered here -- two repaired, one closed as already answered, with the
evidence, rather than being repaired twice. The organisational point is that the reports came from the
consumers who had already built the thing by hand: a system that receives that kind of report and answers it
the same day is one people keep reporting to.

**Cost to here: 7m 36s** from the first command of the session to both attachments verified on the published
Release. The legs, from timestamps rather than reconciled to a total: verifying the locked topic against the
repo and running the cut with both gates **6m 34s** (the 45 test suites were **154s** of that, the lint gate
the rest), then the tag to the published Release **1m 02s**. One caveat that belongs on the figure rather
than beside it: that first leg contains the requester's own decision point, so it is not all machine time,
and it cannot be split after the fact.

**The baseline for this release was not noted before starting**, which is step 0a's one instruction and the
one thing it says cannot be recovered afterwards. The figures above are reconstructed from file and commit
timestamps, which is weaker evidence than a clock reading and is stated as such. It is a small number to have
got loosely, and the reason to record the miss is that the step exists precisely because this is what happens
without it.

**Cost of this release: 25m 29s** of working time, added after the fact because this document cannot time its
own publication. The legs the first pass could not see: writing this page **5m 45s**, its local gates and the
push **2m 57s**, CI and the merge **9m 07s**, and the fold **4s**.

**A separate 58m 53s sat between the published Release and the start of this page**, and it is excluded from
the total above rather than folded into it. That gap is the requester deciding to ask for the document, not
the procedure running -- and a release measured with it included would report an hour and a half for work
that took twenty-five minutes. Stating it beside the total rather than inside it is the only reading that
survives being compared with another release. End to end, wall clock, the whole thing spans **1h 24m 22s**.

**Two readings the first pass could not produce.** The head -- clock start to the tag being pushed -- came to
**6m 34s**, or **26%** of the working total, which sits mid-range against the four releases timed before it
(`v4.15.0` 21%, `v4.12.0` 24%, `v4.13.0` 30%, `v4.14.0` 32%). That is now a fifth reading for the claim that
most of a release happens after the moment the version number exists. And the two heaviest legs are **14m
52s** between them, **58%** of the working total -- but only the 5m 45s of writing is a person's time, the
9m 07s of CI being a machine nobody waits on deliberately. The comparison with v4.15.0 is the one worth
keeping: **24m 34s** there against **25m 29s** here, for a release with a quarter of the entries. The cost of
a release is mostly fixed per event rather than per change, and two consecutive measurements now say so.

## What was still open at this release

**The Release was published one step early, and its `notes-for-users` attachment is the generated draft.**
The checklist puts the written document before the publish, for exactly this reason, and it names publishing
early as the first wrong idea that suggests itself. v4.15.0 followed the order -- its document merged at
07:20:20Z and the Release was published at 07:21:20Z. This one was created and published in the same motion
as the cut, so what a reader downloaded before this document landed was the tier-2 entries in the words their
authors wrote for a diff reviewer, with two empty organisation headings. Whether the attachment is replaced
or left frozen sat with the requester at the moment this was written.

**This release had not been published to the organisation.** Publishing is a decision separate from cutting
and was not asked for. Read at the target rather than carried forward: `BWJ-ecommerce/claude-plugins-bwj`,
commit `9ea8dcf`, 2026-08-16T19:40:08Z, all four team plugins at **4.13.0** from their own `plugin.json`
files -- three releases behind as of this cut.

**Each `team-shopify` consumer still owns the one answer nobody can ship them.** The floor now places the
seam block, but the live theme's id is a fact about their store. A consumer who runs the command without
`-LiveThemeId` gets the block commented out and keeps the session-start report, by design.

**Whether `team-shopify`'s `start-task` gets its missing script or moves to the workflow plugin was still
undecided.** The report offered three routes and correctly declined to pick; the choice is the source's, and
this release did not make it.

**The release-notes page still rendered note bodies in the browser.** Going fully script-free would need a
second markdown implementation beside the one in the template -- two renderers for one format -- so the index
is static and the bodies are not, and the page says so.

**Two items from v4.15.0's list had closed and are named so nobody inherits them.** The public repository
description and the `inbound` label description are English, verified by reading the repository settings and
the label rather than any document.

**Three things remained deliberately unchanged**, all of them measured and none of them a defect anybody has
reported hitting: a second `Get-JsonField`, 310 uses of "workshop" as a role word (not the retired framing --
sweeping them buys consistency at the price of worse sentences), and a dash-matching regex in
`pr-issues-lib.ps1` whose risk is written up rather than repaired, under the rule that a risk which has not
bitten gets named and left.
