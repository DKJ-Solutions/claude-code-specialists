# Release notes v4.27.0 🚀

**Date:** 2026-08-30\
**Type:** Minor\
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

prune-merged leaves the checkout alone, and the consumer-facing messages name the seam

## What changed

**No action needed.** Nothing here is breaking, no convention is retired, and nothing you have
configured stops working. Update the plugin and everything below applies on its own.

### Your gates stop going red for a reason that was never in your code

`prune-merged` used to step the checkout onto the trunk and hand it back within the second. That is
still a working tree moving under whatever else is running in the same clone -- and the workflow tells
your session to run it mid-assignment while a `ship-pr` runs in the background. The symptom to
recognise, if you have seen it: a test suite failing on a file that exists on your branch and not on
the trunk, which passes when you re-run it. It now advances the trunk with a `git fetch` refspec, which
writes a ref your `HEAD` is not on and touches no file at all.

The same run also stops refusing outright when a second worktree has the trunk checked out. It reports
the lane, skips the fast-forward, and carries on classifying your branches -- so the script is
available in exactly the situation that produces stray branches in the first place.

### Adopting the workflow folder now leaves your release notes where the folder says they are

If you run `/adopt-workflow-folder` in a fresh repo, it now resolves the release note root through the
seam and writes that answer into your `scripts/repo-config.ps1` -- but only where the file exists,
defines no answer of its own, and you have no hand-written note sitting at the shared fallback. Your
first release note then lands inside the folder the adoption just built, instead of at `releases/notes/`
in the repo root with the history table linking back out to it.

If you already answered `Get-ReleaseNoteRoot`, or already have notes on disk, nothing changes: your
answer wins and no file is ever moved.

### The two messages you meet when you cut your first major now say the right thing

Cutting `X.0.0` stops and asks you to open that major's section by hand. If your line has had fewer
minors than the threshold, the refusal now names `Get-ReleaseMajorMinMinors` and the file to set it in
-- previously it offered only `-SkipTierGate`, which overrules a judgement that was usually correct
instead of pointing at the one value that makes the release correct.

And the advice that prints the heading to add no longer counts an edit you may not have. It says the
test pin has to be repointed *if your repo has one*, and its closing sentence now agrees with that
condition instead of asserting two edits. Verified on the documented path in a fresh repo: adding the
section alone -- one edit, no pin -- cuts `v1.0.0` cleanly.

## What it is worth

**A class of false failure disappears from the working day.** The checkout collision cost time twice
over: once when a green gate came back red, and again in working out that the cause was not in the
change under test. That is the most expensive kind of defect to sit with, because the natural response
is to go looking in the code -- and the answer was never there. It is gone at the source rather than
documented as a quirk to recognise.

**The two refusal messages reduce dependence on whoever knows this system.** Both were points where a
person met a hard stop and had to ask someone -- or reach for a bypass that produces a subtly wrong
release. Each message now carries its own remedy, so the person meeting it can act on it alone. That
matters most at a major cut, which by definition nobody in a repo has done recently.

**The adoption fix removes a discrepancy that only surfaces later.** The folder and the release both
behaved as documented; they simply disagreed with each other, and the disagreement showed up at the
first release rather than at adoption. Found by running the documented path literally, which is what
the test rounds are for.

**What this release cost:** 6m 09s end-to-end, from the first state check to the last attachment
landing on the GitHub Release. Three legs, and only the first two blocked a person: the cut itself
2m 56s (of which the 55 test suites were 76s), writing and gating the hand-written note 3m 02s (76s
of it the same suites, run a second time before the release-notes commit), and the publish plus both
attachments 11s. The gates are two thirds of the release, run twice by design -- once by the cut and
once before the commit that follows it -- which is the cost the two-commit shape buys, and the tail
is now small enough that where it ends stopped being ambiguous.
