# Release notes v4.2.0 🚀

**Date:** 2026-08-10  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

The document you are reading is now named after you, and has a written norm behind it. Two more failures
that produced no error message are caught.

## For consumers

### Two things to check in your own repo

Both are about state that may **already** be wrong in your repo rather than about anything this release
changes underneath you. Neither takes more than a minute.

#### 1. Do your branch types include anything outside `Feat` / `Fix` / `Docs` / `Chore`?

If your branch table produces a fifth type — a `style/` or `liquid/` prefix, say — you may have a seam
function that is present, correct, and **never loaded**. A contract record makes two claims: that the
function lives in a particular file, and that a given script calls it. Only the first was ever checked. A
file the calling script never loads is not in scope at runtime, however present it is, so the script quietly
used its own built-in fallback of the four canonical types.

**What you would have seen**, both without a word of explanation: on `v4.0.0` every folded changelog entry
came out with no type at all; on `v4.1.0` the fold refuses outright. The contract check reported `[OK]`
throughout, because the function really was there.

Run the contract check. It now emits an `[INFO]` for every declared function whose file is never reached by
the script that needs it — directly or through any file that script loads:

```powershell
powershell -NoProfile -File scripts\lint\check-script-contract.ps1
```

If your function is listed, the repair is to load its file from somewhere the script already loads.
`Get-BranchTypes` is also a declared optional record now, and its entry states what the fallback **costs**
you — a refused fold, not a degraded one — instead of leaving you to find that out at the fold.

It stays `[INFO]` and never an error, deliberately: every function reached this way is probed before use, so
the fallback is a designed state. If your branch types *are* the canonical four, it is also the right one.
What was missing was any way to learn which of the two answers you were getting, before the fold rather
than at it.

#### 2. Was the `adopt-config` skill missing from your skill list?

It was, and not because of anything you did. The file shipped with three invisible bytes in front of its
opening `---`, so every parser that expects `---` at the very start read it as having no frontmatter — and a
skill with no name registers under none. **The symptom was pure absence**: the page was simply not in the
listing, with no error raised anywhere, in any log. Of the model-invocable skills in the two shipped plugins
it was the only one to go missing.

Update and it appears. Nothing on your side needs repairing.

Worth knowing why it lasted: the bytes are invisible in every editor you would open the file in, *and*
invisible to our own quality gate, because every reader in it discarded them before any check could look. A
byte-level check on every shipped document with frontmatter now closes that. It was found by a consuming
repo comparing first bytes, which is the only way it could have been found.

### One rename, and it takes nothing from you

The release document written for you was called **highlights** — the directory, the seam function and the
renderer. That named the form, a selection of the nice bits, while the documents either side of it are named
after their reader. It is `releases/consumer/` now, and the seam is `Get-ReleaseConsumerBumps`.

**If you define the old seam name, it keeps working.** `Get-ReleaseHighlightsBumps` is read as a fallback,
and that is not politeness: an unrecognised seam falls back to "this tier is switched off", so a repo still
carrying the old name would cut a minor, write no document for the very reader it was cut for, and report
success. You receive a rename through a plugin update rather than by choosing to, so the old name is
recognised for as long as it needs to be.

**Your own directory is not renamed for you**, and nothing will complain. If you want to follow, rename the
directory and the seam function in the same change — either name alone works, so a half-done rename is not
detectable by anything.

### What is new

#### The document written for you now has a norm you can hold it to

Seven tests, in the [`cut-release` skill](../../../../plugins/workflows/contributing-davekjohn/skills/cut-release/SKILL.md):
open every item with what you can now do, order by urgency, say plainly whether you must act, give a silent
failure its visible symptom, stay short and link out, and never hand you a document written for somebody
else. Each one is carried by what a named product actually does rather than by taste — Linear, Stripe,
Vercel, Raycast and GitHub were read before the list was written.

**If you adopt this, adopt the measurement with it, not the conclusion.** Only one of the seven is
automated here, and which one was decided by running three candidate rules over eleven existing documents:
one found two real problems, the other two found seven between them and every single one was false. Run the
seven over your own last few release documents before deciding which part your repo can afford to automate.
Your answer may not be ours.

#### A gate against being sent into a document written for our developers

The one automated test refuses a release document for you that links into the per-PR record or the internal
summary. It reads the **link target** only — a tier named in prose is someone writing about the model, which
is a different thing entirely. The two real cases it found had both been inviting a paying reader into our
own engineering notes; both are gone.

#### The v4.0.0 page was rewritten for its reader

If you are still coming from `3.x`, re-read [that page](4.0.0.md). Every factual claim it made is unchanged
— what moved is the order and the address. The three migration sections were at the bottom behind an
instruction to scroll; they are now first and run in version order, so you walk forward from wherever you
are instead of jumping backwards. Both breaking changes now name what you will actually *see*, since "it
fails in silence" is a category and not something you can check.

#### Two records are cited where they actually live

Looking up the `Get-LiveStage` record sent you to a file that has not held one since it moved on August 8.
The `cut-release` skill now names the right file. This one ships to you, which is why it is here; the other
was in our own README.

### Nothing here requires an update to keep working

Every existing installation keeps functioning on the previous version. The two checks at the top are about
state that may already be wrong in your repo, and the rename recognises both names. Update the usual way:

```powershell
claude plugin marketplace update claude-code-specialists
claude plugin update <plugin>@claude-code-specialists --scope project
```

## What it is worth

> Most of this release asks nothing of you. **One item does**, and it applies to any repo whose branch
> types are not the four this product ships with: a setting that used to be answered wrongly in silence
> now says which of the two answers you are getting.

**The theme is audience: which document is for whom, and what it costs when that slips.** Four of the
seven changes here are about the release documentation itself, and the failure they address is not
sloppiness but drift -- whoever edits the outward-facing page has been writing for colleagues all week and
keeps doing it. That is invisible from the inside and obvious to the reader, which is exactly the kind of
problem a norm fixes and good intentions do not. The value is that this now transfers: a new person can
execute the seven tests, and one of them holds without anyone remembering it.

**The second half continues the previous release's theme, and it is the more expensive one.** A capability
we ship was simply not there, for days, with no error anywhere -- and our own quality gate could not have
found it, because every reader in it discarded the offending bytes before any check could look. That is
worth stating plainly: the gate was not weak, it was blind by construction. Both of this release's silent
failures were reported from outside, by people measuring what we cannot feel from in here, and both are now
checked at the moment they would occur.

**And the principle from last release held up under a second test: what travels is the measurement, not
the answer.** Before automating any of the seven writing tests, three candidate rules were run over the
eleven existing documents. One found two real problems and was built. The other two found seven between
them, all false, every one of them a release whose subject *was* the document format and which therefore
quoted the shape it was announcing. Both would have shipped needing an exception list on day one. Declining
them is cheaper than maintaining them, and the count is why we know that rather than suspect it.

## What was still open at this release

- **Two of the seven writing tests were deliberately left as prose after being measured**, with the numbers
  recorded: nothing automatic separates a document quoting an example from one leaking internal detail, and
  a rule that needs an exception list on the day it lands has been a reliable mistake here.
- **A consuming repo's own outward-facing release document is checked by nothing.** The new gate runs in
  this repo. What reaches a consumer is the norm, the measurement behind it, and the request to run that
  measurement over their own documents before deciding which part they can afford to automate.
- **One check that was declined a day earlier was re-measured at this release rather than left as a
  memory**, and declined again on the same grounds: it would guard six places, all of which are currently
  correct. It is written down as measured-and-not-built, with the count, so the next person spends a minute
  instead of an afternoon.
- Nothing else was left half-done; every change in this release merged with its gates green.
