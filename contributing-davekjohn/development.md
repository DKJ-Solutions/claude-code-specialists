#### The reason in the report did not survive the check, and the repair still stands

The report's stake was *"the internal note is published output -- it is the GitHub Release body"*. It is
not. `cut-release.ps1` passes `releases/github/<dir>/<X.Y.Z>.md` to `gh release create --notes-file`, and
that document is generated by `Build-GitHubReleaseBody` -- which already carries the break. The internal
note is the tier-1 document for colleagues and management, and since the one-document reorganisation
(Dave, August 10-12, 2026) nothing in the cut calls the script that writes it.

The claim was not invented by the report. `internal-note.tests.ps1` carried it in a comment
(*"this document is the published GitHub Release body"*), stale since that same reorganisation, and this
branch corrects it there so the next reader does not repeat it.

**The symptom stands on its other leg**, which is why the repair is unchanged: three documents of one
release should not differ in shape -- the sentence `new-internal-note.ps1` already carries four lines
above the block that breaks it.

#### And the choice the report left open was already made

The report offered two repairs and called the choice Dave's. It is not open: `release-lib.ps1` states in
its own comment, written in the #1100 repair a day earlier, that *"removing the two spaces renders the
two labels on one line rather than two"* and that the break is **deliberately KEPT**. The internal note
simply never received the same treatment. This is the completion of #1100, not a new decision.
