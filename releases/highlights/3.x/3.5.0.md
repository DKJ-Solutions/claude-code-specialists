# Release notes v3.5.0 🚀

**Date:** 2026-08-05  
**Type:** Minor

Your changelog can now say **who notices each change**, and a release has to earn its version number.
The shared release workflow also stopped assuming it was running in the repository it was written in --
which, if you had adopted it, cost you a safety check you thought you had.

## Your changelog gets three sections instead of one

Every change now declares **how far it reaches** while it is still on its branch: only your own
developers notice it, a colleague on the project gets something out of it, or someone using your
product notices. That single answer files it under the matching section of your changelog and decides
which release document it appears in.

You get three documents per release instead of one, each written for its own reader:

| for | what it answers | when |
|---|---|---|
| your users | what they notice | minor and major releases |
| your colleagues and management | what the organisation got out of it | every release, patches included |
| your developers | the complete per-change record | every release |

Only the middle one is written by hand. The other two are generated from what the changes declared.

**A release now has to earn its bump**, checked before a single file is written. A release with nothing
in it for anyone outside your own repo has nobody to announce it to, so it is refused; a minor needs at
least one change your users notice; a major has to recap enough minors behind it. When the cut refuses,
it names the version the pending work *does* earn, so the usual answer is to take that one.

**If you have not adopted any of this, nothing changes.** A repository that declares one changelog
section simply travels the same path with one tier, and the bump gate reports itself inactive rather
than refusing your releases. That is how the code is built, not a compatibility layer bolted on.

## If you adopted the shared release script, four things were quietly wrong

The first repository to cut a release on it found all four, and this release closes them.

**Your lint gate was not running.** The release route resolved it by a path that only exists in the
repository the script is maintained in, so in yours it was skipped -- with a warning, not a failure.
That route is the one that never passes through a pull request, so it was also the only gate it had.
It now uses the same setting your pull-request route already uses, and **refuses to release** if the
gate it is told to run is not there.

**The checklist's first command did not exist in your repository.** It pointed at a local copy of the
script that you deliberately do not keep. It now points at the plugin.

**The reminder to write the internal note never appeared for you** -- the one tier that is written at
*every* release, including patches, and the only one nothing else would remind you about. It now
appears, and prints a command you can paste rather than a path you have to translate.

**Your changelog was written in English whether or not your repository is.** The four sentences a
release writes into it are now yours to set, the same way the entry templates and the category labels
already were.

## Two workflow scripts resume instead of failing

**Shipping a branch whose pull request is already open used to stop at the first step** -- and take the
CI wait, the merge, the changelog fold and the issue check down with it. Precisely the branch you most
want the script for. It now picks up where it was, running every gate against the new commits and
skipping only the part that is already done.

**And a resumed pull request can have its description refreshed from the changelog entry.** On a branch
that keeps growing, the description used to describe an earlier version of the work while the entry that
ends up in the release notes carried the new one -- so the two disagreed exactly where people go looking.
It is opt-in, so a description you edited by hand is never overwritten unasked.
