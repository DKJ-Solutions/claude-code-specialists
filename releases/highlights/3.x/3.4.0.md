# Release notes v3.4.0 🚀

**Date:** 2026-08-04 · **Type:** Minor

**Nothing requires action before you update.** Two things get quieter on their own, one piece of manual
work disappears, and there is one thing worth reading if you have been folding changelog entries by hand.

---

## What you can do now

### Ship a finished branch with one command

`ship-pr` opens the PR, waits for CI, merges, folds the changelog entry, and checks that the issues the PR
said it closes really are closed. You have had the script since v3.3.0 — **what was missing was the page
telling you it exists.** The `cut-release` page was already sending readers to "the normal
`new-branch` → `ship-pr` route", a route nothing described.

It stops at the first failure and never forces: a failing gate means nothing is pushed, a red CI means
nothing is merged, and there is no `--admin` anywhere in it.

### Repair mangled characters without writing your own tool

`fix-mojibake` repairs text that was read once as Windows-1252 and saved as UTF-8 again — the damage that
turns a middot into two characters while the file stays perfectly valid. Run it with `-Check` as a gate.

**Three repos had each written their own copy of this before it was shared.** That is why it now has a
page: three people needed it and none of them had anything to read.

### Stop committing the changelog fold by hand

`fold-changelog` gained `-Commit` and `-Push` in v3.3.0. **Its page did not say so, so the instructions
you were following still told you to make that commit yourself.** If you have been doing that, you can
stop:

```powershell
powershell -NoProfile -File "${CLAUDE_PLUGIN_ROOT}/scripts/release/fold-changelog-entry.ps1" -Branch <prefix>/<name> -Push
```

That gap prompted a new check across every shared script, which found three more parameters missing from
their pages — including `cut-release`'s `-NoPush`, the one inspection step before a release goes public.

## What gets quieter

### Two errors disappear if you use the scripts without the specialists system

`Get-RosterPath` and `Get-RosterIgnoredIds` are now **optional**. If you installed this plugin only for
the shared workflow scripts, your session start stops reporting them as missing.

They were the only two required entries you could not opt out of: every other one serves a script you
choose to run, while these two served a check that runs from a hook. And that check never needed them —
it defaults the roster to `CLAUDE.md` and runs fine without either.

### The roster check reports the version you are actually running

If more than one repo on your machine uses this plugin, the shared cache holds several versions. The check
used to read the newest one present; it now reads your install record. Nothing looked wrong before — those
versions happened to ship the same specialists — but as soon as two differ, it would have told you a
specialist was present that your session does not have.

## What you can turn on

### Let your changelog lead with the release instead of archiving them all

Set `Get-ReleaseHistoryMode` to `'latest'` in your `scripts/repo-config.ps1`, and `Get-ReleaseHistoryPath`
to wherever you keep your release list. Your changelog then keeps **one** release block and points at that
file for the rest.

**Only do this once every release really is listed somewhere else** — from that point the other file is
the sole record. Here the accumulating section had grown to 434 of 1,062 lines while duplicating, more
poorly, an overview that already existed.

Both settings are optional and default to what you have today: change nothing and your changelog comes out
byte-for-byte as before. The release section may also sit **above** `## Pull Requests` now, and a cut keeps
whichever order your document already has.

## Worth knowing

**Two release attachments cannot share a filename.** All three note tiers call their file `<X.Y.Z>.md`,
and a GitHub asset's name is its basename — so uploading two straight from `releases/` makes the second
fail with a `404`. Copy them to distinct names first; the `cut-release` checklist now says so.

**The internal note's "still open" section is a snapshot.** It is the Release body, so whatever it says
about open work is published and then goes stale in place. Write it as "open at the time of this release",
not as a live list.
