# Internal summary v4.0.0

**Date:** 2026-08-09
**Type:** Major
**For whom:** colleagues and management -- what the organisation gets out of this release

## What is different now

**The major bump is a milestone, not a change of direction.** It closes the third chapter of this product
— twenty-one releases and fifty-one pull requests in ten days, which took the specialists from a plugin you
could install to a family whose every member says whether it is a *team* (who the colleagues are) or a
*workflow* (how work moves through the repo they land in). The release notes open with that recap.

**The release itself is the documentation catching up with the product, and it was done by measuring
rather than by reading.** Chapter 3 moved a great deal of structure; the sentences describing that
structure stayed where they were. Held against the code and the directory tree instead of proofread:

- **The page that explains how to run a release was wrong on five load-bearing points**, all in the half
  that travels to any organisation adopting this way of working. It described release rules **stricter
  than the ones the software enforces** — so an adopting team would have believed it was not allowed to
  publish work it was entitled to publish.
- **Four separate claims were contradicted by the thing they described.** The clearest: an overview that
  called itself the complete list of shared components listed **nine of twenty-three**.
- **Three directories had never been described at all** — including the one a maintainer actually edits,
  whose read-only copy had carried a page for months.

**A pull request became a document a reviewer can read.** It used to open with four lines of branch
bookkeeping — a title repeated from the heading above it, a creation timestamp, a type already shown as a
label — before the first sentence saying what the change does. That sentence is now the first thing on the
page.

**A check was reporting correct configuration as broken.** Four errors were being raised every session
against two consuming repositories that were registered exactly as intended. The rule the check enforced
and the written policy contradicted each other; the policy was right, and the check now distinguishes *not
yet migrated* from *invalid*.

**And one proposed safeguard was measured and turned down.** A plausible new check was built five ways and
run over a hundred and twenty documents; the narrowest version produced a hundred and twenty-four alerts
and **not one of them was a real problem**. The reasoning was written into the record rather than
discarded.

## What it is worth

**The instructions we hand other teams now match the software they describe.** This is the item with real
exposure: a set of release rules that is stricter than reality does not fail loudly — it quietly stops
someone from shipping, and they have no way to know the document is the thing that is wrong. That class of
error was found in the one document written to be copied by others.

**Review time moved from bookkeeping to substance.** Every pull request from here starts at the argument
instead of at metadata the page around it was already showing. Small per review, and it applies to all of
them.

**A recurring session-level false alarm is gone.** A check that cries wolf every session against a correct
setup is worse than no check, because it teaches the team to scroll past the place real problems appear.

**The habit is the durable part, and it now runs in both directions.** Documentation here is increasingly
verified against the system rather than re-read — which is how a "complete" list turned out to be
nine-of-twenty-three. The same discipline is what allowed a well-intentioned new safeguard to be refused on
evidence, and the refusal to be written down so the next person does not spend the same afternoon
rediscovering it. Saying no with numbers is cheaper than maintaining a check that is wrong a hundred and
twenty-four times.

## What was still open at this release

**A snapshot, at the moment of the cut.** The consumer-facing highlights and this summary were the two
documents the release tooling deliberately leaves to a person; both were written after the version was
tagged and shipped together through the normal review route, with the public release page published after
they landed. Nothing else was left open, and no decision was waiting on anyone outside the team.
