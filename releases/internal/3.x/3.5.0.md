# Internal summary v3.5.0

**Date:** 2026-08-05
**Type:** Minor
**For whom:** colleagues and management -- what the organisation gets out of this release

## What is different now

- Every change now states, while it is still being made, **who notices it**: only our own developers,
  a colleague on the project, or someone using the product. That single answer decides which of the
  three release documents it appears in.
- **A release has to earn its version number.** The cut refuses a number the pending work does not
  justify, and says which number the work *does* earn.
- **Another repository can now run this whole release process without keeping its own copy of it.**
  The first one to try found four places where the shared machinery still assumed it was running in
  the repository it was written in; all four are closed.
- **Interrupted work resumes instead of being redone.** Two steps that previously had to be started
  over now pick up where they were left.

## What it is worth

**The version number stopped being a matter of taste.** It used to be decided at the moment of
release by whoever was cutting it, working from a list of changes written for developers. It is now
decided by what the changes themselves declare, before anyone gets to the release. The practical
effect is that "is this worth a release, and who for" is answered once, by the person who actually
knows, instead of reconstructed later by someone reading titles.

**Three audiences stopped sharing one document.** Management, colleagues and users of the product
were all being handed the same per-change developer record, which serves none of them well. Each now
has a document written for them, assembled automatically from what the changes declared -- so the
cost of producing three is roughly the cost of producing one, and this note is the only part still
written by hand.

**And a gate we believed was running turned out not to be.** The check that stops broken links and
bad configuration from reaching the main branch was silently skipped on the release route in any
repository other than this one -- reporting a warning, not a failure. Nothing had gone wrong yet, but
that was luck rather than a control: the one previous time this check was missing, two broken links
reached a main branch and would have blocked every subsequent change until someone traced it. It now
runs, and refuses to release if it cannot.

**The direct saving is duplication.** A second repository adopting this workflow used to mean keeping
and maintaining its own copy of the scripts, which then drifted from ours. It now points at one
shared copy and states the handful of things that genuinely differ for it -- its own language among
them, which this release made configurable for the last piece that was not.

## What was still open at this release

**The repository that reported the four faults still carries notes telling its readers to run the
missing gate by hand.** Those instructions are now wrong rather than merely redundant, and removing
them is work on that side, not this one.

**Four ideas are recorded and none are scheduled**, the most substantial being a proposal to score
each change by how pleased its reader would be and to order these documents by that score -- which
would finish what the tier model started, since knowing *who* a change is for still says nothing
about *how much* it gives them.
