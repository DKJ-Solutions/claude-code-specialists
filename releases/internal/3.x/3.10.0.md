# Internal summary v3.10.0

**Date:** 2026-08-09
**Type:** Minor
**For whom:** colleagues and management -- what the organisation gets out of this release

## What is different now

- **Every plugin is now either a team or a workflow, and its name says which.** Four teams
  (`team-alpha` and three add-ons) answer *who the specialists are*; two workflows answer *how work
  moves through the repo*. Teams stack; exactly one workflow may be enabled at a time.
- **Every existing installation has to be reinstalled.** The five old plugin names no longer exist, so
  each connected repo swaps its ids once. A migration page walks through it.
- **A repo that has not chosen a way of working now has one to enable.** `workflow-default` imposes
  nothing: the specialists follow the conventions the repo already has, and a skill reads those
  conventions out of the repo -- its documents, its CI, its branch names -- and records them, naming
  the questions the repo has never answered instead of filling them in.
- **A misconfiguration that used to be invisible now announces itself.** Two conflicting ways of
  working could be switched on at once with no error and no symptom beyond specialists behaving
  inconsistently. That is reported at session start now, naming which settings file to open.

## What it is worth

**The naming was costing a decision every time somebody added to this product.** One prefix covered two
unrelated kinds of thing, so "what is this new plugin?" had to be looked up rather than reasoned about,
and the answer lived in a table that went stale. It is now a question with two answers, and the answer
picks the name. That is the durable half.

**The reinstall is a one-off cost, paid once per connected repo, and it buys the rest.** Three repos are
connected today; a fourth would have paid the same cost later at a worse moment, because this kind of
rename gets more expensive with every consumer added, never less.

**The largest reduction in dependence on a developer is the one that is easiest to miss.** Five scripts
each kept their own answer to "which plugins exist and where do their folders sit", each encoding the
directory layout. Adding or moving a plugin meant finding all five and hoping. They now read one source,
which is why the directory reorganisation in this same release needed **no production script change at
all** -- measured: the move produced 45 findings, every one a dead link in a document.

**And a class of defect that used to reach consumers is now stopped before it ships.** A skill page that
printed the author's own disk path went out in two consecutive releases; the page was the instance, and
this release added the gate that refuses the class.

## What was still open at this release

*A snapshot of 2026-08-09, not a claim about the present.*

- **The three connected consumer repos had not migrated yet**, and their register entries still name the
  old plugin ids on purpose -- the register records what a consumer has, so writing the new id early
  would report a real migration as missing. The next step sits with whoever runs each of those repos.
- **A second checkout of this repo, on another machine, was still on the old plugin ids** at the moment
  this was cut. Its owner does that migration when it suits them.
- **One caveat is documented rather than repaired**: a consumer whose repo lenses still sit on the older
  of the two supported locations has the plugin name inside that path, so their lenses go unseen after
  reinstalling under the new name. No connected repo is confirmed to be in that state, and the fix is
  renaming one directory. It is written down in the migration page rather than pre-empted in code.
- **This release is `3.10.0` and not `4.0.0`, and that was decided rather than defaulted.** The rule here
  is that a major *recaps* ten minors; this line had nine. The work is breaking for consumers, which is
  the usual argument for a major, so the rule and the instinct genuinely pointed different ways. The
  rule won, and the next release can be the major without overruling anything.
