# Internal summary v3.4.0

**Date:** 2026-08-04
**Type:** Minor
**For whom:** colleagues and management -- what the organisation gets out of this release

## What is different now

- Every tool the team shares now has a written page. The last four were undocumented; that count is
  down to one, and that one is a script nobody invokes by hand.
- Two recurring pieces of manual work disappeared: shipping a finished branch is one command instead
  of five steps, and repairing mangled text no longer means writing your own tool first.
- The changelog answers "where do we stand" at a glance. It went from over a thousand lines to
  twenty-one, with the full release history moved to its own page.
- Two warnings that fired at every session start, in a repo that was configured correctly, are gone.
- A check that reported on the wrong version now reports on the one actually in use.

## What it is worth

**The undocumented tools were costing real work, and we can name the instance.** One shared script
gained two flags that make a routine step automatic. Because its page was not updated, everyone kept
doing that step by hand for two days -- including on other projects, which had no way of knowing the
shortcut existed. A new check now refuses to ship a script whose documented options do not match the
real ones, so this class of loss cannot recur silently. It found three more cases the same day,
including the one inspection step that stands between a release and the public.

**The largest saving is that a release now takes a fraction of the attention.** Shipping a branch was
five manual steps, each with a way to go wrong in a place nothing reports. It is one command that stops
at the first failure. Cutting this release surfaced two defects before anything was published, purely
because the process has a deliberate inspection point.

**The reduced dependence is the part that compounds.** Three separate projects had each written their
own copy of the same repair tool -- three people solving one problem, and three versions that drift
apart. There is now one, with a page. The same pattern is why documentation gaps get treated as
defects here rather than as tidiness.

**And the working method proved itself in a way worth stating.** An improvement request came in from
another project, carefully argued. Checking its premise showed the situation had reversed within the
hour, by the requester's own hand -- so the work it asked for would have solved a problem nobody had.
What was built instead was the one measured issue underneath it. That is a day of avoided work, found
by verifying a report rather than acting on it.

## What was still open at this release

- The **public release page** for this version is not yet published; that is the closing step for
  whoever finishes the release.
- A **proposal to let other projects adopt this changelog workflow automatically** was assessed and
  found largely feasible, but is not built. The next step sits with Dave: deciding which parts of the
  configuration are meant to travel and which belong to this project alone.
- Two smaller items were deliberately left: an issue awaiting reproduction, and two older versions
  without a public page, both consciously not backfilled.
