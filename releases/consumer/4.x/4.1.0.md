# Release notes v4.1.0 🚀

**Date:** 2026-08-10
**Type:** Minor

The workflow's portable half: a consumer can copy the PR template and the contribution cycle, and three
seams stop failing quietly.

---

## Three things to check in your own repo

This release is mostly about failures that produce **no error message**, so the useful part of this page
is at the top rather than the bottom. None of the three takes more than a minute.

### 1. Does your PR template's placeholder still match? (most likely to already be costing you something)

`open-pr` fills your PR body's description by comparing each line of `.github/pull_request_template.md`,
**whole and exact**, against a list of known placeholder strings. A template one word away from one of
them matches nothing — and until this release the run said nothing either. You get a PR body that looks
structurally correct and is empty exactly where it matters.

This was measured, not imagined: one consumer had
`<!-- Beschrijf kort wat er verandert en waarom. -->` where the recognised string is
`<!-- Korte beschrijving van wat er verandert en waarom. -->`, and **12 of their last 60 merged PRs have
no description at all**. Nobody noticed for months.

**From this release the run warns**, naming your file, the strings it compared against, and the seam that
overrides them. Open a PR and see whether the warning appears. If it does, either paste one of the named
strings into your template verbatim, or declare your own line:

```powershell
# scripts/repo-config.ps1
function Get-PrDescriptionPlaceholder { return @('<!-- your own placeholder line -->') }
```

### 2. If you ran `adopt-config`, check `Get-ReleaseNotesGrouping`

That record used to be marked `copy`, so `adopt-config` wrote **this** repo's answer (`'major'`) into
your seam without asking. If your `releases/development/` tree is foldered per **minor**, your next cut
would quietly start a *second* tree beside your existing one and write an overview row pointing at a path
holding none of your history. Nothing fails at adoption, and the contract check reports `[OK]` afterwards,
because `'major'` is a perfectly valid answer — just not yours.

It is a `decide` record now, so `adopt-config` asks instead. The answer is a lookup rather than a
judgement: a directory named `3.x` means `major`, one named `2.13` means `minor`.

### 3. Coming from v3.x? The rename has a migration path now

`v4.0.0` renamed the plugins *and* moved them in the tree, and two things break **inside your repo**
without any error: the `@`-import of the orchestrator's body (Claude Code drops an unresolvable import
silently, so your session starts looking normal with no ritual behind it), and every `<plugin>:<name>` id
in your roster. `plugins/INSTALL.md` now carries a before/after for both, plus the reason neither
`specialists-init` nor `sync-roster` repairs them for you — neither overwrites what you already have.

## What is new

### The PR template's shape now ships with the plugin

`.github/pull_request_template.md` is the one file in this whole cycle that cannot live in the plugin —
GitHub reads it only from that path in your own repo — so unlike everything else it has to be **copied**.
That is exactly what made it drift-prone, and there was nothing to drift *from*. There is now:

```text
${CLAUDE_PLUGIN_ROOT}/templates/pull_request_template.md
```

The whole interface is two lines: a **first heading** at any level (which is what `-RefreshBody` replaces
the description under) and a **placeholder line** the script recognises verbatim. Everything else in the
file is yours — add sections and checklists freely; the script leaves them alone.

**Read the reasoning behind the two-line default before you copy it.** This family's own template lost its
"Type of change" block and its checklist after counting 60 PRs, and the rule that survived is *keep what
is neither restated by the changelog entry nor proven by a gate*. That **nothing** survived it here is a
fact about this repo, not about the form. The consumer who prompted this ran the same count over their own
60 PRs and found one box of eight that genuinely varied — a preview-URL approval, on a repo whose result
has to be judged by eye and which no gate can prove. They kept it, correctly. **The measurement travels;
the answer does not.**

### The contribution cycle travels too

[`CONTRIBUTING-portable.md`](../../../plugins/workflows/workflow-davekjohn/CONTRIBUTING-portable.md) is the
cycle in prose — branch, two files, PR, gates, merge, fold — written to be read in **any** repo that
enables this workflow. It names the *seam* wherever a repo owns the answer instead of stating one repo's
answer as the rule. Your own `CONTRIBUTING.md` can shrink to a `## Specific to this repo` section holding
just your answers.

Four statements that used to read as universal rules are gone, each measurably false outside the source
repo: that there are three branch prefixes and no `chore/`, that the lint gate is a particular script,
that the merge waits on a check with a particular name, and that tier 1 earns a minor — which is the
shared gate's **floor**, not your policy.

### The fold commit is typed `fold:`

```text
fold: feat/your-branch changelog (#42)          one entry
fold: 3 changelogs: a (#1), b (#2), c (#3)      a fold-all run
```

It read `chore: fold changelog entry <branch> (#NN)` before. Folding is a named act with its own script
and its own exception to "never commit directly on the trunk", while `chore` said only "housekeeping".
It now pairs field for field with the `merge:` commit one line below it.

**Nothing parses this subject**, which was checked rather than assumed — so every `chore: fold ...`
already in your log stays exactly as valid as it was. There is nothing to migrate.

### The fold refuses a pre-flat changelog instead of writing into the wrong place

If your `CHANGELOG.md` still carries section headings (`## Pull Requests`, `## Releases`), the fold used
to insert your entry **above the first of them** — outside the section you keep entries in — and report
success. Exit 0, no warning, a document that stays well-formed. The only way to see it was to open the
file afterwards, which nobody does after a green fold.

It refuses now, in a pre-pass before the first write, with the migration advice in the refusal text. The
cut has refused over that same assumption since August 5; the fold made it and never checked.

### The trunk warning is translatable from its first word

`TrunkWarningLead` joins the wording knobs, so the opening sentence of the trunk warning in
`branch/branch-changelog.md` and `branch/branch-progress.md` is repo-owned prose like the rest of it. A
consumer who had translated everything else was left with one English sentence at the very top of the
document and no way out but forking the script. `{0}` in your own text is replaced by your trunk name,
and is optional.

## Nothing here requires an update to keep working

Every existing installation keeps functioning on the previous version; the three checks at the top are
about state that may **already** be wrong in your repo, not about anything this release changes underneath
you. Update the usual way:

```powershell
claude plugin marketplace update claude-code-specialists
claude plugin update <plugin>@claude-code-specialists --scope project
```
