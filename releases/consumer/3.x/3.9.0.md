# Release v3.9.0 🚀

**Date:** 2026-08-09
**Type:** Minor

**Our workflow config stops being something you have to reverse-engineer.**

If you run the workflow plugin, one command now sets up the settings its scripts read — placing the
answers that are genuinely shared, and writing you a proposal for the ones only you can answer.
Nothing in this release breaks anything, and nothing here is required.

---

## If you are updating from before v3.8.0, read that release first

**[v3.8.0](3.8.0.md) has the one change in recent history that needs a decision from you**, and
skipping straight to this version does not skip past it. In short: if you use `new-branch`, `open-pr`,
`ship-pr`, `fold-changelog` or `cut-release`, those moved into a separate opt-in plugin and your update
takes them away unless you enable it.

```powershell
claude plugin marketplace update claude-code-specialists
claude plugin install specialists-workflow-davekjohn@claude-code-specialists --scope project
```

If you never used those skills, do nothing — that is the point of that change.

## Adopt our workflow config with one command

**The scripts always travelled to you. The answers they read never did.**

The shared workflow scripts read about twenty settings from two files in *your* repo. Until now you
were told which ones were missing and what the script would fall back to — but never what we chose, or
why. So adopting the workflow meant deriving twenty answers by hand, or quietly leaving them.

Ask your Claude for the **`adopt-config`** skill from your repo root — it knows where the plugin lives
on your machine, which a command typed by hand does not.

**It is a dry run by default.** The first run prints exactly what it would change and touches nothing.
Say `-Apply` when you are happy with what it says.

**It splits the settings into two kinds, and the split is the useful part:**

- **Twelve are placed for you.** These state the shared way of working and assert nothing about your
  repo — so you get our function *as we wrote it*, comments and reasoning included, not a bare value
  stripped of the thinking behind it.
- **Ten are proposed, never placed.** These state what your repo *is* — its name, whether it publishes
  plugins, which branch prefixes it accepts. Copying our answer would assert something about your repo
  that is probably false, so they go into a proposal document with our answer and the reason it is
  ours, for a person to decide on.

**Nothing is ever overwritten.** A setting you have already answered is left exactly as it is, whatever
we chose. That makes the command safe to re-run — a second run finds nothing to do.

**Why the ten are not filled in with placeholders.** A placeholder is worse than an absent setting: an
absent one falls back to something documented and often correct, while a placeholder overrides that
with a value nothing checks. So the command cannot place them, rather than choosing not to.

**If your repo has no workflow config files at all**, this is not the command to start with — it points
you at the `specialists-init` skill instead of half-creating them.

## Before you update

A `github` marketplace source is a cached clone, and an install compares against that cache rather
than against what we just tagged. One idempotent command first, always:

```powershell
claude plugin marketplace update claude-code-specialists
```
