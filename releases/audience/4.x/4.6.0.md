# Release notes v4.6.0 🚀

**Date:** 2026-08-12  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

One audience tier per repo, and releases/ reduced to three reader-named roots

## For consumers

**Nothing in this release breaks anything you have configured, and no migration is required.** Every new
setting below falls back to exactly what it did in `4.5.0` when you leave it alone. Update with:

```powershell
claude plugin marketplace update claude-code-specialists
claude plugin update <your-plugins> --scope project
```

The refresh on the first line is the safe first step: `install` compares against a cached clone of this
repo rather than against the tag, so without it you can install the previous version and see nothing
unusual in the output.

### You can now decide which audience your repo writes release notes for

Answer `Get-ReleaseAudienceTier` in `scripts\repo-config.ps1` with `1` or `2`. Tier 1 is management and
whoever commissions or pays for the work -- the audience of a repo that *delivers* something, or that sells
a product whose buyers never read a release note. Tier 2 is the subscriber of a service, who reads your
notes to decide whether to upgrade. **Your repo has one of these, not both.**

Until now the two were rungs of a ladder: claiming tier 2 obliged you to write a tier 1 section as well. If
your repo only ever has one of the two audiences, that second section was the same reach argued twice for a
reader who is the same person. Set the knob and `new-branch` scaffolds that tier alone.

**No action needed to keep working.** Leave it unset and every tier is asked about, exactly as before.

### You can now put your release notes where they actually live

`Get-ReleaseNoteRoot` says which directory the hand-written release note is written into and read back
from. The default is `releases/notes`, unchanged.

This matters if you had wanted to switch the hand-written note on and found you could not: naming your bumps
in `Get-ReleaseConsumerBumps` used to point the release cut at `releases/notes/` whether or not that is
where your notes are, so the only safe answer was to leave the tier switched off. Repoint the root, then
name the bumps.

### Two new commands survive a cleared context: `/lock` and `/continue`

`/lock "<the next subject>"` records what you agreed to do next. After `/clear`, `/continue` reads it back
**and** re-reads the repo -- your branch and tree, recent commits, parked branches on the remote, open
issues, pending changelog entries, the last tag, and what the previous release left open.

The lock is recorded intent, not a rule: if the work has been overtaken while you were away, `/continue`
shows you the disagreement instead of following a stale note. It only reads -- it never commits, pushes or
edits -- so both commands are safe on a dirty tree mid-branch.

### A stacked branch no longer starts out claiming another branch's work

If you created a branch off a branch whose changelog entry was written but not yet folded, `new-branch`
skipped writing the new branch's files and told you `Branch files already written for 'feat/child' -
nothing done.` Nothing had been written for it. The files still held the **parent** branch's entry, heading
and all, and the message named the child -- so the new branch silently inherited a description of somebody
else's change.

**The symptom to look for**, if you have stacked branches in flight right now: open `branch/branch-changelog.md`
and check that the heading names the branch you are on. Fixed automatically from this version; no action
needed for new branches.

### "What the last release left open" now reports the release it says it does

`/continue` picks the newest release note by version number instead of by file modification time. Git does
not preserve modification times, so in any freshly cloned repo that choice was effectively arbitrary --
measured on a clean clone, fifteen notes carried two distinct timestamps between them. The block was always
populated, so it read as correct while describing the wrong release.

If you have been reading that section, treat what it told you before this version as unverified.

### Running a shared script from the wrong place now stops instead of quietly doing the wrong thing

Eleven of the shared entry points refuse to run, with a message naming the local path to use, when they are
executed from a copy outside the repo being operated on **while that repo holds its own copy**. This cannot
trigger for you as a consumer -- you have no such copy, so you are never refused. It is here because the
three failures it prevents were all silent ones: a changelog entry scaffolded in a retired shape, and a
status report with one section quietly empty.

### If you are still migrating off the old plugin names

The migration section in `plugins/INSTALL.md` described one **before** layout. There were two in the field,
and the documented one was the further of the two from where most migrations start. It now tests by shape --
any `@`-import whose path does not contain `plugins/teams/<team>/` or `plugins/workflows/<workflow>/` is
stale, whatever it contains instead -- with both real forms quoted underneath and the version range each
belongs to.

It also says what to do when neither quoted line matches yours, which is the failure that section exists to
prevent: searching for a literal, finding nothing, and reasonably concluding the change is not yours to make
leaves your orchestrator running without a body, with no error to tell you.

## What it is worth

**The release inspection paid for itself on this release, in the one way that is hard to argue with.** The
cut is run with `-NoPush` so that a person reads the assembled artefacts before anything is public. That
step is easy to treat as ceremony -- it has found nothing for several releases, and it costs a full
re-run of the gates when it does find something. This time it caught a generated dead link in the release
overview: the row for `v4.6.0` pointed at a document the same run had written somewhere else. Nothing
errored, no gate saw it, and every neighbouring row was correct, so it would have shipped inside a tag and
been found by whoever next clicked it. The release was undone locally, the generator was fixed, and the cut
was re-run. **The cost was about twenty minutes; the alternative was a permanent wrong link in a published
record and a repair that could only ever paper over it.**

**Three of this release's defects share one shape, and it is worth naming as a class rather than three
fixes.** A hardcoded path where a configurable one existed; a test that checked for the fully-qualified form
of that path while the real escape was the short form; a file-selection rule that sorted by a property git
does not preserve. None of the three failed loudly. Each produced a result that looked finished -- a
populated section, a plausible link, a passing test -- which is the expensive kind, because the moment of
discovery belongs to whoever trips over it rather than to whoever caused it. The guard added here is not
another gate but a habit: **when a check and the thing it checks disagree about wording, the check is the
one that is wrong.**

**The dependence on a developer went down in two concrete places.** Deciding who your release notes are for
is now one line in a config file instead of a property of the tooling you would have to change code to
escape; and a cleared context no longer loses the one thing the repo cannot reconstruct, so picking work
back up stops depending on whoever remembers what was agreed.

**And a measured cost worth putting in front of the organisation rather than hiding:** shipping one
three-line fix through the full workflow ran the same 32 test suites **four times** -- twice locally
(opening the pull request, then shipping it) and twice in CI -- for a total of roughly 27 minutes of the
release's wall clock. The suites are what make an unreviewed direct-to-trunk release safe, so this is the
price of that safety rather than waste, but it is the largest single line in the bill and nobody had
counted it before.

### What this release cost, end to end

Step 0a of the release checklist asks for the clock, because a release is the most-repeated expensive
procedure here and had never been measured in its own unit.

**Clock start: 23:09:07.** Measured legs, from timestamps rather than estimated:

| leg | time | blocked a person? |
|---|---|---|
| first cut: lint + 32 suites, commit, tag | 8m 25s | yes |
| reading the artefacts and finding the dead row | ~6m | yes |
| undo, fix both copies, write the test, verify it red then green | ~3m | yes |
| the fix's own gates before the pull request (lint + 32 suites) | 7m 07s | yes |
| CI on the pull request -- the required check that blocks the merge | 5m 26s | yes |
| merge + fold, which re-runs the same 32 suites | 7m 37s | yes |
| the re-cut: lint + 32 suites, commit, tag, push | 8m 33s | yes |
| CI on the merge and fold commits | 6m 20s / 7m 05s | no -- ran behind |

**Subtotal at the moment this document was frozen: 46m 05s** (23:09:07 to 23:55:12, the tag push). Every
measured leg blocked a person, which is the number that matters: the two CI runs that did not are excluded
rather than added, since shortening those buys nothing.

**Three legs cannot be measured from here, and this is why the checklist asks for two passes:** this
document's own CI gate, its merge, and publishing the GitHub Release are all still running on the file being
written. At the previous release that tail was two thirds of the total, so treat the subtotal above as most
of a lower bound rather than nearly the answer. The total is added in a follow-up once it exists.

## What was still open at this release

- **A machine-local PowerShell cache is tracked in this repository, and it blocked this release twice.**
  `Microsoft/Windows/PowerShell/ModuleAnalysisCache` was committed by accident in `65902dd`. PowerShell
  rewrites it in place, so it dirties the working tree, and the release cut refuses to run on a dirty tree
  -- it was restored by hand twice during this release to get the cut to start. It was deliberately **not**
  repaired here: untracking it is a repo-hygiene change with nothing to do with a release, and folding it
  into a release-blocking fix would have put two unrelated changes in one pull request. It sits with Dave
  for its own branch, and until then anyone cutting a release here will meet it.
- **Two entry points deliberately do not carry the new source-repo guard.** `check-roster-sync.ps1` and
  `check-script-contract.ps1` are invoked by the SessionStart hooks from the plugin cache by design, so
  refusing there would fail every session start in this repo. Closing it needs the hooks to pass an
  explicit bypass, which was judged more surface than the defect warrants.
- **The consumer-facing half of the audience decision is unproven in the field.** This repo answers tier 2
  and the webshop that asked for the change answers tier 1, so both branches of the new knob have one
  real user each -- but no consumer has yet cut a release under it. The failure that would be worth
  hearing about is a release document going out with a section its reader cannot use.
- **The timing above is the second release measured under step 0a, so there is still no trend.** The
  previous release came to 28m 03s with a much smaller change set; this one to at least 46m with a
  mid-release repair. Two points is not a baseline, and the next release is the one that makes the figure
  worth acting on.
