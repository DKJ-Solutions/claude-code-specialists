# Release notes v4.4.0 🚀

**Date:** 2026-08-11  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

Your release checklist now tells you to time the release, and the single-document release note has run
once end to end.

## For consumers

**Nothing you have breaks, and there is one new thing to do.** No command changes, no file moves, and
no seam function is renamed. One step is added to a checklist and one rule to a manual.

### 1. Time your own release — step 0a of the `cut-release` checklist

Note the clock **before** you cut, note it again when the Release is published, and write the duration
into the release note's organisational section. The
[checklist](../../../plugins/workflows/workflow-davekjohn/skills/cut-release/SKILL.md) now opens with it,
and it asks for two splits alongside the total, because one figure hides both:

- **what blocked you** (a gate you waited on, the writing) versus **what ran behind you** (a CI run on a
  push nobody is waiting for). Making the second one faster is worth close to nothing;
- **the fixed cost per release** versus **how often you release**. Where the cost is per event, releasing
  half as often removes exactly as much of it as making it twice as fast — and needs no code.

**No action needed to keep cutting releases.** This is a convention, not a gate: nothing refuses a
release over a missing timestamp. What you get for following it is the one number you cannot recover
afterwards — a baseline cannot be taken retroactively.

### 2. Ask "how long does this take" and get minutes back

Your performance engineer carries a new rule: **report in the unit the question was asked in — a proxy
is not the measurement.** Two halves, and only one of them can be done afterwards. Capture the baseline
in the asked-for unit *before* the change; when reporting, name the unit in the same breath as the
number, and say plainly where the asked-for unit has no post-change figure. It is in
[his manual](../../../plugins/teams/team-alpha/manuals/06-25-manual.md), so it applies to every cost
question you put to him, not only to releases.

The failure it is written against is reaching for the count that is easy instead of the one that was
asked for. If you have ever received a percentage when you asked for minutes, this is that.

### 3. The one-document release note has now run for real

You were told last release that two hand-written documents became one, with a named section per reader.
This is the confirmation that it works outside the test suite: the [v4.3.0 note](4.3.0.md) was drafted by
the cut, every one of the seven strings that should not survive the strip appeared **zero** times, and
the release-history row pointed at the right document on the first write.

**Nothing to do.** If you kept the two-document flow, `new-internal-note.ps1` still ships and still works.

## What it is worth

**This is the first release this repo has timed.** The clock started at **10:24:11**, before the cut,
exactly as step 0a now asks. Measured from git timestamps rather than remembered:

| leg | measured | blocking? |
|---|---|---|
| verifying the repo state and walking the checklist, then the whole cut — lint gate, **30 test suites in 231s**, the writes, the commit, the tag | **5m 07s** | blocking |
| pushing `main` and the tag, inspecting the generated artefacts, branching, and writing this document | **4m 35s** | blocking |
| **subtotal, clock start to the moment this document was frozen** | **9m 42s** | |
| CI `lint-en-tests` on the release commit's own push to `main` | ~9m, in parallel with the above | **not** blocking — nobody waits on it |

**The legs after this line are the ones a document cannot contain**, because the clock is still running on
the document itself: the pull request's CI gate, the merge, and the publish. They are measured in the
closing report rather than estimated here. What can be said about them from this repo's own record is that
`lint-en-tests` has run at **8m 41s to 9m 20s** across the four most recent runs, and it blocks the merge —
so it is the single largest thing a person waits on in a release, larger than the cut it follows.

**What the breakdown buys is a decision that was previously argued from feel.** The gates are the release:
231s of suites inside the cut, another local run of the same 30 suites when the pull request opens, and ~9m
of CI on top of that. The same 30 suites run **three times** for one release-with-a-document, which is deliberate
— the release commit travels via no pull request and therefore meets no CI, so the cut runs them itself —
and it is also where any real reduction would have to come from. Two of the three runs are blocking.

**And a warning against the wrong conclusion, which is the reason to write the caveat down rather than the
number alone.** This release carried **two** entries; `v4.2.0` carried seven. Less to read is less to
write, so nothing here shows that the merged-document model is faster than the two-document one it
replaced — that is a different variable, and this release does not isolate it. The comparison worth making
is between releases of similar size, and this repo does not have that pair yet.

**The cadence point is the one this release actively worked against, deliberately.** Cutting again this
soon adds another instance of the fixed gate cost to a repo that had already paid it sixteen times in ten
days — which is exactly the lever the performance engineer named as needing no code. It was accepted here
because the alternative was another release with no figure at all, and the figure cannot be captured
retroactively. Paying it once to end the guessing is a trade; paying it every day is the thing the cadence
question is about.

## What was still open at this release

- **Two of the three numbers the last release asked for were still unanswered.** Which of the 30 suites can
  change behaviour on a markdown-only diff — the answer decides whether the second local run of the suites
  has any room in it — and the release cadence against the fixed gate cost. Both are counting jobs, both
  sit with the performance engineer, and neither is a gate.
- **The draft still carried one line of branch language per change**: `#### What does the change on this
  branch bring to main?`, inside the section written for a consumer. Reported at `v4.3.0` and still not
  repaired, on purpose — it is draft noise the writer deletes in the same pass that rewrites the prose, and
  closing it properly needs a heading-only remover that nobody has asked for.
- **The release overview's own tier table had gone stale.** [`releases/README.md`](../../../releases/README.md)
  still named `consumer/<dir>` and `internal/<dir>` as the tier-2 and tier-1 documents, four days after the
  two were merged into `notes/`. Found while walking this checklist; no gate sees it, because a directory
  named in a table cell is prose rather than a link. It sits with the technical writer.
- **The timing convention had run exactly once when this was written**, which is enough to prove it can be
  followed and not enough to compare anything. The second data point is what makes the first one useful.
