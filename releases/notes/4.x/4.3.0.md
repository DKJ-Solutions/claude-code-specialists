# Release notes v4.3.0 🚀

**Date:** 2026-08-11  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

One hand-written release note per release instead of two, a Release page that lists every change, and the
performance engineer now owns how long your gates take.

## For consumers

**Nothing you have breaks, and there is one thing to look at.** Your next cut writes its release documents
into a different place. Every existing file stays exactly where it is, every seam function you have defined
keeps working, and no command you run changes.

### 1. Your next cut writes one hand-written document, in a new directory

You used to get two drafts per release and write both: an organisational note and a consumer document. You
now get **one**, at `releases/notes/<dir>/<X.Y.Z>.md`, with a named section per reader:

| section | for | how it arrives |
|---|---|---|
| *For consumers* | whoever decides whether to update | pre-filled with your tier-2 entries — rewrite it |
| *What it is worth* | your organisation | empty; it cannot be generated |
| *What was still open at this release* | your organisation | empty |

**What to expect the first time.** A `releases/notes/` directory appears; `releases/consumer/` stops being
written to and keeps everything already in it. Your release-history row points at the new document instead
of at the development notes, and it is correct on the first write — nothing repoints it afterwards.

**A patch now writes no hand-written document at all.** If you cut patches and were writing an
organisational note for each one, that stops. The release is still announced, by the page below.

**If you prefer the two-document flow, keep it.** `new-internal-note.ps1` still ships and still works,
including `-Force` and `-RepoRoot`. Nothing calls it for you any more, so running it is now a choice.

### 2. Your GitHub Release page is written for you

`cut-release.ps1` writes the Release body: your title, a pointer at the attached notes, and one linked line
per change that landed. Point `gh` at it — the cut prints the exact command at the end of its run.

Two things this fixes rather than improves. The body could previously exceed **125,000 characters** and the
publish failed outright with an HTTP 422; a title and a list cannot. And a patch used to have no body at
all unless you wrote a document for it, which is why writing one was mandatory.

### 3. Your release document no longer carries our branch administration

The generated draft used to repeat, per change, the branch title, the branch id, the branch prefix and the
pull-request link — measured at **125 of 396 lines, a third of the file**, with the branch title printed
directly under the heading it had just become. Those are gone from the draft, so what you read before
writing is the substance.

### 4. The specialist who measures cost now owns wall-clock too

The performance engineer covered token and context budget. He now covers **what your work costs to run** —
test suites, lint gates, CI, a script every branch invokes — with three counting rules that are the
transferable part:

- **count the invocations, not the run.** A gate that runs locally, again on the way out, and again in CI
  costs three times per unit of work;
- **separate what blocks a person from what does not.** Eight minutes of CI you wait on is not the same
  cost as eight minutes running behind you;
- **name the fixed cost and the frequency separately.** Halving how often a fixed cost is paid is as real a
  lever as making it faster, and needs no code.

And one prohibition worth adopting with them: **a skipped check is not a saving.** The fastest way to
shorten any gate is to stop running it, which trades coverage for time. That is a decision for whoever owns
your safety rules, quantified on both sides — never presented as a number that went down.

## What it is worth

**The theme is that a second copy is a liability, and the value is in what stopped being written twice.**
Two documents were produced at all twelve releases since the organisational tier existed, about the same
changes, and 38% of the organisational note was material the consumer document already carried in a
different register. That was found by measuring rather than by noticing: the same question — *does this
describe our effort or their outcome* — that decides how the outward document is written also decides how
much of the two overlapped. One document with a named section per reader keeps both registers intact and
writes the overlap once.

**The second half is the thirty-minute release, and this is the first release where anybody owned that
number.** A release took about half an hour, roughly seventeen minutes of it waiting on gates and the rest
writing. Both halves came down this cycle: one document instead of two, and a third less to read before
writing it. Neither was achieved by removing a check — every gate that ran before still runs, and two of
this cycle's changes were caught by those gates rather than by review.

**And a structural point about how these decisions were made, because it is the reusable part.** Four times
this cycle a change was measured before it was built, and twice the measurement reversed the plan: a blended
release document was refused on a word count, and two candidate lint rules were declined at seven findings
between them, all false. The cost of measuring first is minutes; the cost of shipping a rule that needs an
exemption list on day one is permanent.

## What was still open at this release

- **The first cut under the new model is this one, and it worked** — the document was produced by a real
  run, every one of the seven strings that should not appear in it appeared zero times, and the history row
  pointed at the right file on the first write. Before this release that was proven only by the test suite.
- **One wart survives in the generated draft**: each change still carries the heading *"What does the
  change on this branch bring to main?"*, which is branch language in a section written for a consumer. It
  cannot be stripped the way the other administration was, because the remover that drops a section takes
  its body with it and that body is the substance. It is draft noise the writer deletes; closing it
  properly needs a heading-only remover, which nobody has asked for.
- **Two measurements were named and deliberately not acted on.** Which of the thirty test suites can change
  behaviour on a markdown-only diff — the answer decides whether the second local run of the suites has any
  room in it. And the release cadence: sixteen releases in the ten days to August 10, each carrying the same
  fixed gate time, which makes batching a lever that needs no code. Both are cost questions and both now
  have an owner.
- **The archived documents were not migrated and will not be.** The eleven files in `releases/consumer/` and
  the twelve organisational notes are published records; they stay where they were written.
