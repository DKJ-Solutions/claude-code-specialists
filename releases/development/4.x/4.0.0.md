# Release notes v4.0.0

**Date:** 2026-08-09  
**Type:** Major

Chapter 3 consolidated (v3.0.0 -> v3.10.0)

## Milestone — closing chapter 3 (v3.0.0 → v3.10.0)

`v4.0.0` is a **consolidation milestone**, the same shape `v2.0.0` and `v3.0.0` used to close chapters 1
and 2. It carries its own merged changes below, but its purpose is to draw a line under the third chapter
— **21 releases and 51 pull requests in ten days**, from a plugin you could install to a family whose every
member says what it is for.

**Nothing in this release breaks anything.** The major bump marks a moment, not an incompatibility: the
changes below it are documentation and pull-request body fixes, and your next update takes them silently.

**Chapter 3 as a whole is a different matter, and it is worth being blunt about it.** Twice in ten days
this family renamed something every installation names back — the marketplace in `v3.2.0`, every plugin id
in `v3.10.0` — and **neither failure announces itself**. A session whose marketplace or plugin id no longer
resolves does not error; it loads no specialists at all and starts normally. If you are updating across
either of those versions, the highlights for
[v3.2.0](../../../contributing-davekjohn/releases/audience/3.x/3.2.0.md) and [v3.10.0](../../../contributing-davekjohn/releases/audience/3.x/3.10.0.md) are the two documents
to read before running a command, and `v3.8.0` carries the one decision the renames cannot make for you:
whether you want a workflow at all.

### The story of 3.x

- **The chapter opened with eleven patches, and that was the point.** `v3.0.1` through `v3.1.2` — nine of
  them in the first three days — were almost entirely findings from adoption rounds v8 to v12 run against
  real consuming repos: the install, update and uninstall commands measured against what the CLI actually
  does rather than what the documentation said; the enable state read from the whole settings chain instead
  of one file; the install record reporting what you are really running; and a crafted plugin id that could
  forge a line in a session check. The recurring move is visible from the release titles alone — each one
  closes **the class behind the finding**, not the finding. Chapter 2 made the product installable and
  uninstallable; chapter 3 began by proving it, and paying for the differences.

- **One product, one marketplace** (`v3.2.0`). `davekjohns-workshop` became **`claude-code-specialists`**,
  matching the repository, and the plugin tree flattened from two levels to one. The second level had been
  holding a place for a family that was never coming: the release train is repo-wide, so one changelog and
  one tag cannot honestly span two unrelated products. The next product gets its own repository instead.
  This is also the first of the chapter's two silent breakages.

- **A release learned to write for three readers** (`v3.3.0`, `v3.4.0`). One set of notes became three
  documents — for consumers, for colleagues on the project, and the complete developer record — and every
  shared script got a page of its own. The changelog stopped archiving its releases and started leading
  with them.

- **A change learned to declare its own reach** (`v3.5.0`, `v3.6.0`). The tier model: while a change is
  still on its branch, its author answers how far it reaches and how much it weighs for each audience, and
  that answer decides which release document it appears in and where in that document it sits. A release
  now has to **earn** its bump, checked before a single file is written. The reason this replaced grouping
  by branch prefix is a measurement rather than a preference: held against the 19 entries pending at
  `v3.2.0`, the single most consequential change for a consumer — the marketplace rename, which broke every
  install — had arrived on a `chore/` branch and would have been filed below the fold. Alongside it, a
  branch began keeping its plan in a file and had to finish it before it could merge.

- **The branch became two files with a designed shape** (`v3.7.0`). The changelog entry turned into the
  branch's own dossier, folded into the changelog verbatim; the step list holds the plan and nothing else;
  and the guidance that used to fill both moved beside them into `branch/templates/`, so what you type into
  is the questions and your answers.

- **The workflow became opt-in, and this is the chapter's largest idea** (`v3.8.0`). The specialists
  stopped bringing a way of working with them. What forced it was a count, not an argument: of what the
  core plugin was actually sending a consumer, **9% described a craft and 47% was machinery implementing
  one particular workflow.** Most of what a repo received was a method it never chose. So the method left
  for a plugin of its own, named after whose method it is. The same release gave the product **one**
  changelog: the per-plugin copies and release cards were 11,684 duplicated lines, free to disagree with
  the original, in a repository a consumer already clones whole.

- **Adopting the config stopped being reverse-engineering** (`v3.9.0`), and then **every plugin became a
  team or a workflow** (`v3.10.0`). A team is who the specialists are; a workflow is how work moves through
  the repo they land in. Teams stack, and you enable exactly one workflow — with `workflow-default` added
  for the repo that wants the deliberate absence of a method rather than a gap to fill. The names now say
  what the plugins had already become, at the cost of the chapter's second silent breakage.

### What chapter 3 was actually about

**Separability.** Chapter 2 asked whether a consumer could install this and get rid of it again. Chapter 3
asked a harder question — *which parts of it are even yours?* — and answered it three times over: a team is
separable from a workflow, a change's reach is separable from the branch it arrived on, and a rule that
belongs to this repo is separable from one that travels. Every one of those splits started as a measurement
of something that had been asserted for weeks.

**And the measuring cuts both ways, which is the habit worth keeping.** The chapter closes with a check
that was proposed, built as five candidate rules, measured over 120 documents, and **declined** — the
narrowest of them produced 124 findings and not one was real. The entry recording that decision is in the
notes below. A repository that only writes down what it built loses the more expensive half of what it
learned.

### Where chapter 4 starts

With the family named and split, the questions left are no longer about what the product *is*. They are
about the distance between what its documents claim and what its code does — which is what most of the
changes in this release are, and where the next chapter is likely to spend its patches.

#### What does the change on this branch bring to main?

`releases/README.md`'s portable half — everything above the mirroring rule, so everything that travels to a
repo adopting this workflow — described the changelog model as it stood before August 6, 2026. Measured
against `release-lib.ps1` and `cut-release.ps1` rather than read, it was wrong on five load-bearing points at
once:

- **The bump table refused what the code permits.** It required a tier-1 entry for *any* release and a
  tier-2 entry for a **minor**. `Test-ReleaseBumpEarned` requires nothing for a patch (a tier-0-only release
  is what a patch is for, Dave, August 7) and tier **1** for a minor. A reader following the page would have
  believed a legitimate release could not be cut.
- **It named a retired script as the writer.** `new-changelog-entry.ps1` was retired on August 7 and folded
  into `new-branch.ps1`; the page still had it writing `Tier: 0` into the entry.
- **It described the fold as rewriting the entry** — filing it under a section and stripping the tier line.
  The fold does neither: it folds **verbatim**, and `fold-changelog-entry.ps1:50` keeps the legacy
  `Tier: N` line deliberately.
- **It described the entry's retired shape**: an "impact table" and `#### What does this change do?`, both
  replaced by `### Significance` with one `#### Tier N` sub-section per reach.
- **It stated the gate's off-switch as a section count**, the exact test that became a landmine when the
  changelog went flat and which was replaced by counting declarations.

Two further claims were corrected against what was measured rather than against `CLAUDE.md`, which
summarises this one step too loosely. The highlights document is written when the bump is one the seam names
**and** a tier-2 entry is pending — both conditions, not either — and that second one only became
load-bearing when a minor stopped requiring tier 2. And the development note's structure is now stated as
what it is: the one document that still groups by tier, carrying each entry whole with its six `####`
sections, rather than "structured the way `CHANGELOG.md` itself is".

Alongside it, the root `README.md` claimed `cut-release.ps1` "stays repo-only and is deliberately not
mirrored" and cited `check-script-contract.ps1` for it — a file which opens that very record with
*"cut-release.ps1 USED TO BE OUT OF SCOPE HERE"*. The script has been shared and mirrored since #417; the
paragraph now separates the shared **script** from the portable **skill** instead of resting on a
distinction that dissolved.

#### Significance

##### Tier 0

The page is what a maintainer here reads before cutting, and it disagreed with the gate they were about to
meet. The `new-changelog-entry.ps1` reference in particular sends a reader looking for a file that is not
there.

##### Tier 1

**Score:** 3

### `fix/pr-body-heading-levels` changelog

#### Branch title

The PR body headings start at H1

#### Branch ID

20260809-131332

#### Branch type

fix

#### What does the change on this branch bring to main?

A PR body is now a document in its own right rather than a fragment of one. The entry's levels are
shifted up by one at the single point where the copy is made:

| in the entry and `CHANGELOG.md` | in a PR body |
|---|---|
| `## ` + the branch name | *(the PR title, not part of the body)* |
| `### What does the change on this branch bring to main?` | `# What does the change on this branch bring to main?` |
| `### Significance` | `## Significance` |
| `#### Tier 0` | `### Tier 0` |

**Why the levels differed in the first place, so nobody "corrects" them back.** In `CHANGELOG.md` an
entry is one `##` block among many, so its sections are `###` and its tiers `####`. That is right
there and wrong in a PR, where the entry is the whole document and its title is printed above the body
by GitHub. Carrying the levels across unchanged produced a body that opened at H2 with sub-sub-headings
at H4 — the typography of an excerpt. `CHANGELOG.md` and the release documents are untouched.

**One thing this could not be done without, and it is not cosmetic.** `-RefreshBody` replaces the
description by scanning forward to the next heading **at its level or shallower**. Promote the
description to H1 and leave `## Resolved issues` where it was, and that block is no longer a sibling of
the description but a child of it — so the next refresh deletes it along with the text it replaces,
GitHub closes nothing at the merge, and [the #341–#343 failure](https://github.com/DaveKJohn/claude-code-specialists/pull/343)
walks back in through the door built to stop it. `New-ResolvesBlock` therefore takes a level, and
`Add-ResolvesBlock` **derives** it from the body it is appending to rather than making a caller
remember: this repo's template is H1, a consumer's is still H2, and a hand-written `-Body` is whatever
