# Release notes v5.0.0 🚀

**Date:** 2026-09-11\
**Type:** Major\
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

The marketplace is dkj-claude-plugins -- every existing install must be re-installed under the new name

## What changed

### You must act now: the marketplace has been renamed

This marketplace is `dkj-claude-plugins` now (it was `claude-code-specialists`). An `enabledPlugins`
key is `<plugin>@<marketplace-name>`, and unlike a git repository slug there is no redirect for a
marketplace name -- so every id you have enabled today matches nothing after this release, and the
plugin it names **silently stops loading**. Nothing on screen tells you this happened: no error, no
warning, just a specialist, a skill or a hook that quietly is not there any more.

The fix has to run on every machine, and separately for every checkout on it, because your install
record is keyed on the folder path you installed from. **`INSTALL.md`'s migration sections carry the
exact command sequence and are the canonical copy of it** -- which section applies depends on which
plugin ids you are currently on, so read the one that matches you rather than retyping this from
memory.

One thing you do not have to touch: if you scaffolded a CI runner from this workflow before today, it
keeps working unchanged. It names this repository by its git slug, not by the marketplace name, and a
slug does carry a redirect.

### Worth knowing, no action needed: four plugins install again

If you tried to install `dkj-subagents-alpha`, `dkj-subagents-ecomm`, `dkj-subagents-lifehub` or
`dkj-subagents-shopify` on `v4.33.0`, the install refused outright with `agents: Invalid input` -- all
four shipped a manifest shape the installer does not accept, so nobody could install any of them for a
whole release, even though this repo's own checks reported them clean the entire time. That is fixed
here. Once you are on this version -- a `claude plugin marketplace update` away, which is part of the
migration above if you are migrating today -- the four install normally again. Nothing else about them
changed: same directory names, same specialists.

### Nothing to do: these arrive on the update

- **Session start tells you more about your own plugin state.** Where a plugin you enabled turns out
  not to be installed for this checkout at all, or is registered under a name this marketplace has
  retired, session start now says so as an error you can act on, instead of staying quiet or filing it
  next to an ordinary stale-cache notice.
- **A printed path or command can no longer paste into the wrong answer.** A folder path containing a
  space or an apostrophe, or a plugin id that is not a valid slug, used to produce a paste-ready line
  that was silently wrong in some shells or unsafe to run. Every script that prints one now builds it
  the same way, and where it cannot build a safe one it says why instead of guessing.
- **The `dkj-policy/README.md` section this plugin owns can be kept current with one command.**
  Re-running the adoption skill's first step refreshes that one fenced block -- what this workflow is,
  which pages exist, how to check your version -- without touching anything you wrote around it.
  Nothing changes unless you choose to re-run it.
- **A lost race between two changelog folds no longer turns your CI red.** Where two branches merge
  close enough together that the automatic fold runs twice, the second run now recognises its own work
  is already done and stands down quietly instead of failing the check.
- **If you keep a checkout of this marketplace's source next to your own repo,** it now also tells you
  when a plugin you have enabled is missing from its own bookkeeping, and it can be asked to check a
  connector you have not checked out locally at all. Neither is visible if you do not keep that
  checkout, and neither needs a command from you to take effect.
- **If you have read the `check-policy-drift` skill page and gone looking for the two hook names it
  used to cite,** they were retired before either ever shipped; the page now names the one hook that
  actually exists.

### A process note, if you run your own releases through this workflow

Since `v4.33.0` a release here is titled `Release version X.Y.Z` rather than a forced one-sentence
summary that a large, multi-theme cut makes meaningless. The sentence in the `cut-release` skill that
names a stable title as legitimate -- not something to apologise for -- is now part of what you
receive too. Nothing to do; it changes no command you run.

## What it is worth

- **The migration is the one-time cost of a name finally matching reality, and it cannot be adopted
  passively.** A marketplace name carries no redirect, so unlike an ordinary update this release needs
  the sequence in `INSTALL.md` run by hand, once per machine and per checkout. That cost was bounded
  deliberately: the five consumer repositories were prepared on their own branches ahead of time and
  merge alongside this one, so the window in which any of them is dark is as short as the re-installs
  take.
- **It closes a recurring risk rather than a one-off one.** An unresolved plugin id has never failed
  loudly in this system -- it just stops loading, with the roster rendering around the hole -- and this
  is the second time that exact failure mode has bitten from a rename, the first being the team-plugin
  rename in `v4.33.0`. `Get-RetiredRepoNames` and the migration sections in `INSTALL.md` are built to
  keep answering it as the list of retired names grows, not to patch this one instance.
- **Four plugins being uninstallable for a full release, and this repo's own lint gate and CI both
  reporting the manifest clean the entire time, is the sharper risk closed here.** Nobody outside this
  repo could install `dkj-subagents-alpha`, `dkj-subagents-ecomm`, `dkj-subagents-lifehub` or
  `dkj-subagents-shopify` between `v4.33.0` and today, and nothing in this repo's own tooling said so
  until a consumer hit the installer's refusal directly.
- **The smaller fixes are, in aggregate, a register worth trusting again.** The retired-id verdict, the
  unregistered-plugin report, and the remote-runner read all exist because this repo's own bookkeeping
  of who is on what had drifted quietly behind reality more than once, each time discovered from
  outside rather than from the tooling meant to catch it. None of them is dramatic alone; together they
  are the difference between reading what the tooling reports and re-verifying it by hand.

## What was still open at this release

- **Every consumer still has to run its own migration.** Nothing in this release can re-register a
  machine's marketplace or reinstall a plugin on somebody else's behalf. Between this merge and the
  last re-install, any machine or checkout that has not yet been brought over is dark, and that is a
  state only the person at that machine can close.
- **The retired repository names cannot be retired, and that is a standing constraint rather than a
  todo.** `DaveKJohn/claude-code-specialists` and `DKJ-Solutions/claude-code-specialists` now resolve
  only through GitHub's transfer redirect to `DKJ-Solutions/dkj-claude-plugins`, and recreating either
  path would break that redirect permanently, for everyone still relying on it. This is the opposite
  case from the marketplace name above: a repository slug carries a redirect, a marketplace name does
  not, which is exactly why only the marketplace half needed the manual migration this release opens
  with.
- **Not every place that prints a plugin id built from your settings file is hardened against an
  unsafe one yet.** The install-verdict command is; eighteen further sites that interpolate the same
  value are tracked in #1803 and are not part of this release.
