# Release notes v4.13.0 🚀

**Date:** 2026-08-16  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

The changelog entry halves, the changelog reads newest first, and /continue becomes /handover

## For consumers

### Type `/handover` where you used to type `/continue` -- this one you have to act on

The skill that picks work back up after a context clear is now **`/handover`**. Claude Code ships its
own built-in `/continue`, so the two names collided and you could not reliably reach the one you meant
-- on the command whose entire job is to be the first thing you type in a cleared session.

**What to do:** nothing to install and nothing to migrate, but change the word you type. The three
steps are still `/lock` -> `/clear` -> `/handover`, and the file it reads is still `.claude/handover.md`,
which is where the new name comes from. After you update, `/continue` no longer resolves to this skill.

### The branch changelog form asks two questions instead of six

When you start a branch, `new-branch` scaffolds a changelog entry for it. That entry had six sections;
it now has two -- what the change brings to `main` (with its score) and the pull request. The four that
went were each answering something the file already said: the branch id is the timestamp in the entry's
own heading, the branch type is the prefix of the branch that heading names, and what was labelled
"branch title" was always the pull request's title, so it now sits with the rest of the pull request's
facts.

**No action needed.** Entries you have already written keep folding exactly as they did -- every one of
the six sections is still *read*, only four are no longer *asked for* -- and branches you have in flight
right now need no edit. The scaffolder, the templates it regenerates in your repo, and the pages that
describe the shape all arrive in the same update.

### Your changelog reads newest first

`CHANGELOG.md` used to be ordered by reach and score, furthest-reaching change at the top. It is a
record of what landed, so it now reads in the order things landed: every fold inserts at the top.

**No action needed.** Entries already pending in your repo stay where your own folds put them, and
every new one lands above them. Your release documents are unaffected -- they rank themselves from the
scores, which are untouched and still decide both what those documents lead with and which version bump
a release has earned.

### The rest of the chain is written down where a session can read it

If you have ever finished a branch, said "merge it", and watched the assistant be unable to act on your
own approval, this is that. The commands after `new-branch` -- `open-pr`, `ship-pr`,
`fold-changelog-entry`, `cut-release` -- are deliberately hidden from the model, and that hid the
*instruction* rather than the capability: the scripts were always ordinary PowerShell anyone could run,
so the documented route was unavailable at exactly the moment it was needed while the undocumented one
was wide open.

`new-branch`'s own page now lists all four with the exact command form, so the route is readable at the
moment a chain begins. **No permission, gate or approval rule moved** -- the list is a route, never a
licence, and it says so on the page.

### Smaller fixes you may notice

- `INSTALL.md` named four of the workflow's skills as `team-alpha`'s. Corrected, along with the vague
  "several" it used for how many skills are hidden from the model -- it is 14 of 19.
- The entry heading's timestamp no longer carries quotes.

## What it is worth

**The form somebody fills in on every branch got a third shorter, and that is where this release pays.**
Four of the six questions in the changelog entry were asking for facts the file already carried, and the
cost of that was paid once per branch rather than once. Nothing was removed from what the scripts
*accept*, which is the reason it could be done at all without a migration: every consumer's history,
every branch in flight and every already-folded entry keeps working untouched. A smaller form that
breaks nothing is the cheap kind of improvement -- it needs no coordination with anyone who has already
adopted the workflow.

**One collision that cost a session's first move is gone.** `/continue` was unreachable behind a
built-in of the same name, on the command used at the start of a cleared session -- so the failure was
paid at the beginning of every session rather than once. The repair is a rename, and the new name is not
a preference: it is the name of the file the skill reads, so the command and its input now say the same
word. Both pages record why, which is what stops somebody restoring the old name next quarter because it
read more naturally.

**And a reported blocker from a consuming repo was closed without moving a governance boundary.** The
report was right that the owner's explicit "merge it" was unexecutable, and wrong about three of the
facts it counted and about the repair it proposed -- following it would have opened a boundary on a
reason that does not hold. Recounting before repairing is now the fifth finding of that shape in two
days, which is starting to look like a property of how reports are written rather than an accident:
whoever notices a symptom chooses the search, and the search decides the number. The habit of recounting
first is worth more here than any single repair it produced.

**Cost of this release: 20m 38s** from clock start to a published Release with its attachments. The legs,
as measured rather than reconciled to the total: the cut to the pushed tag **6m 15s** (43 test suites green
in 147s inside it), writing this document **2m 40s**, its own gates **2m 50s**, CI and the merge **8m 07s**,
the fold and the publish **46s**. The seconds between them are the gaps where one command finished and the
next was started.

**The head is a minute above its band and the total is three seconds below the previous release's, which is
worth stating together rather than separately.** `v4.12.0` came to 20m 41s with a 4m 57s head; this one paid
an extra minute up front for a refused command and got it back in a shorter tail -- 14m 23s against 15m 44s.
Neither movement is a trend and neither is a repair: one is a property of the harness this release ran in,
the other is a single CI run finishing faster than the last. What the two numbers do support is the older
claim they were taken to test -- that the tail is a property of the procedure rather than a run of
coincidences, and that the procedure did not change between these two releases.

## What was still open at this release

- **The copy attached to the GitHub Release carries the head of the timing only, and stays frozen.** A
  release note cannot time its own publication, so the total above was added afterwards in its own small
  edit. The attachment is deliberately not replaced -- an attachment is what was published at the moment it
  was published, and silently swapping it is the opposite of the record this document is for. This page is
  the current version.
- **The head took about 6m 15s against a 4m 57s -- 5m 36s band across the previous five releases, and
  the extra minute has a named cause rather than a statistical one.** The first, ordinary invocation of
  the cut was refused by the session's own permission classifier, so it was re-run in its
  inspect-before-publish form and the push was issued by hand. Two commands where there is normally one.
  It is a property of the harness the release was run in, not of the procedure, and nothing was skipped
  because of it -- both gates ran in full. Worth a second look only if it happens again.
- **The gate record's saving on a split ship is now measured, twice, and that item leaves this list after
  five releases of carrying it.** It sat here at `v4.12.0` because that release shipped in one motion and
  so never produced the duplicate gate run the record exists to absorb. Two firings have since been
  measured on real pull requests -- roughly 203 seconds of gate replaced by about a sixth of a second.
  Two firings confirm the mechanism and are not a distribution; nobody should read a ratio off them.
- **This release has not been published to the organisation.** Publishing is a decision separate from
  cutting and has not been asked for. Until it is, colleagues installing internally remain on the four
  team plugins at **4.11.0**, now two releases behind. Read at the target rather than carried forward:
  `BWJ-ecommerce/claude-plugins-bwj`, commit `d528567`, 2026-08-15T15:44:13Z, taken from the published
  `plugin.json` files themselves.
- **Two specialists are *degraded* rather than excluded in the Claude App setting.** Two agent
  definitions name a script in one step of one procedure. Excluding them would lose a whole specialist
  over one line; publishing them silently hands a user a step that cannot run. They travel with that step
  named in their own description, which is a mitigation rather than a fix. Unchanged since v4.10.0.
- **A second `Get-JsonField` remains, deliberately.** No live misbehaviour was found; the risk is a
  future caller relying on a `-Default` the second copy does not have. Named and left, per this repo's
  standing rule about risks that have not bitten yet.
- **310 uses of "workshop" as a role word were measured and left standing.** They are not the retired
  framing, and sweeping them is a prose-sensitive rewrite across 61 files that buys consistency at the
  price of worse sentences. Filed with its measurement rather than swept along unasked.
- **Two layers of this repo speak Dutch where no path-scoped rule can reach them** -- the public GitHub
  repository description and the `inbound` label description, both in repository settings rather than in
  the tree. Outward-facing configuration, so they wait on Dave.
