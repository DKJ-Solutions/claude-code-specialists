# Release notes v4.20.0 🚀

**Date:** 2026-08-26
**Type:** Minor
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

## What changed

**Read the first two items before you update.** This release renames a plugin and moves a document
format one heading level; both need one edit from you, and everything else in this release needs
none. If you only have five minutes, do those two and come back later.

### 1. The workflow plugin is now called `contributing-davekjohn` -- act on this

**Breaking change? Yes**, and nothing will tell you: at your next
`claude plugin marketplace update`, the id `workflow-davekjohn@claude-code-specialists` resolves to
nothing, and the session hook that would have complained about your workflow keys is the one this
release retired.

```powershell
claude plugin install contributing-davekjohn@claude-code-specialists --scope project
```

Then change that one id in your `.claude/settings.json`. **That is the whole urgent part.** The name
now says what the plugin does: it carries one owner's contributing rules, not a workflow among
several. `workflow-default` is gone too -- if you had it enabled, it simply stops resolving.

**Everything you already have on disk keeps working.** Your `workflow-davekjohn/` folder is still
read, your branch documents still resolve, your seams still pass the isolation guard, and your own
`CLAUDE.md` in that folder is untouched. Renaming the folder can wait for a quiet moment; seven
document names and both folder names resolve either way, on purpose, so a half-finished branch is
never stranded.

### 2. Your `CHANGELOG.md` moves one heading level down -- act on this

**Breaking change? Yes, on your changelog only.** The pending section is now a real
`## [Unreleased]` heading with `###` entries beneath it, and your branch's development cycle moved
with it: `## Development cycle`, then `### PLAN`, `### CREATE`, `### TEST`, `### DEPLOY`.

**What you will see if you skip this:** a fold that finds no entries, and a release that describes
nothing. That path refuses loudly rather than quietly producing an empty document -- but the refusal
is the only warning you get, so move your entries down a level before your next fold.

**Nothing you have in flight breaks.** Every reader accepts both level pairs, so a branch that was
open when the plugin updates keeps folding exactly as it did.

### 3. Your release documents now live inside the workflow's own folder

**Action: none today, but know where new files land.** The workflow no longer writes into your repo
root. From this release your changelog, the three release-note trees and your release history all
default inside `contributing-davekjohn/`:

| what | where it lands now |
|---|---|
| the changelog | `contributing-davekjohn/CHANGELOG.md` |
| the per-version record | `contributing-davekjohn/releases/changelog/` (previously `releases/development/`) |
| the GitHub Release body | `contributing-davekjohn/releases/github/` |
| this document's tree | `contributing-davekjohn/releases/audience/` |
| your release history | `contributing-davekjohn/releases/history.md` |

**Old files stay where they are; new ones land in the folder.** That duplication is deliberate and
was chosen over a silent redirect. One thing to check by hand: a pending entry still sitting in your
old root `CHANGELOG.md` is **not** picked up automatically.

**You get one migration, not two** -- the move into the folder and the `development` → `changelog`
rename reach you in the same version, so the tree you never saw is the only one that never existed.
The seam **names** did not move on the same day the defaults under them did. And if you prefer a
single tree, repointing the seam at the one you already have still works.

**One seam was renamed** -- `Get-ReleaseDevelopmentNotesRoot` is now `Get-ReleaseChangelogNotesRoot`.
**No action:** the retired name is still read, so a `repo-config.ps1` that defines it keeps
answering. Define both and the current name wins, so a half-finished migration moves rather than
sticking.

### 4. Your branch reaches `origin` on its own now

**Action: none, but this is the most intrusive thing this plugin has shipped** -- the first hook here
that writes to git rather than reporting. `new-branch` pushes at creation by default, and a new
**Stop** hook keeps `development-cycle.md` current on the remote after every turn.

**Why it stopped being opt-in:** parking was available for nineteen days and produced six commits in
the entire history, while the median branch sat invisible on `origin` for 22 minutes and the worst
for six hours. An opt-in backup is a backup nobody takes.

What it will not do: it never opens a PR, it never touches the trunk, it never amends or forces, it
adds one named path and never `git add -A`, and it goes silent the moment a PR is open on the branch.
A turn that changed nothing prints nothing. No `origin`, or a repo still mid-adoption, is not a
failure -- it says so and carries on. `-NoPush` is there for work that must not be visible yet.

**The one thing worth watching:** pushing at creation leaves remote branches behind for work you
later abandon, and `deleteBranchOnMerge` only reaps merged ones. Nothing cleans those up for you.

### 5. A merge is now refused when the DEPLOY section changed after review

**Action: one permission line, if you want the CI half.** The DEPLOY section is fixed at the moment
your PR opens, and `ship-pr` refuses to merge when the document has since diverged from what the PR
published. Two ways out, both named in the refusal: put it back, or republish deliberately with
`open-pr.ps1 -RefreshBody` so the change is reviewed where review happens.

For the same check on a PR merged from the GitHub UI, the branch-entry workflow needs
`pull-requests: read` beside the `contents: read` it has today. Without it the lock reports that it
could not read the body and merges anyway -- so nothing breaks, it simply does not fire.

Your PR bodies also start carrying the `## DEPLOY:` heading verbatim, so a PR body and the changelog
entry it becomes now read as the same document.

### 6. Six failures you no longer have to meet

**Action: none.** All of these arrive with the plugin update.

- **Every new branch was refused by its own CI gate.** The scaffolder wrote a document with four
  orphaned heading markers in it, which the gate reads as branch content in a region that must be
  generic -- so `open-pr` would not push, with no way past it. If you are on 4.19.0, this is the fix
  worth updating for.
- **`-Resolves` together with `-RefreshBody` published a PR that closed nothing.** The refresh
  consumed the closing block, the run warned and exited 0, and the issue stayed open after the merge.
  **Worth checking:** an issue you expected a recent merge to close may still be open.
- **One red advisory check blocked every merge in the repo.** `ship-pr` judged the merge on *any*
  failing check; it now judges on the ones your ruleset actually requires. A failing required check
  still refuses, and an unreadable required list still refuses rather than guessing.
- **`new-branch -Intent` wrote its note where the gate refuses it.** It now opens the `PLAN` phase.
  Holding a branch scaffolded before this? Move that paragraph under `## PLAN` by hand; nothing else
  changes.
- **A repo that states no audience tier got a broken paragraph** in every branch document -- a
  sentence opening mid-clause, referring to a reader whose name had been dropped. The whole paragraph
  is removed now, found by shape, so your own replacement wording still comes back untouched.
- **A blank-only `StepPhases` override emptied the phase arc**, and the scaffolded step then landed
  where the gate refuses it -- every branch blocked, with no way through but deleting what the
  scaffolder had just written. No registered consumer was in that state; the hole is closed anyway.

### 7. Two refusals that are new, and both are yours to overrule

- **A PR title that already carries its branch's type prefix is refused** -- `fix: fix: ...`, which
  happened for real. `-Force` is there, and the check is bounded to *your own* prefixes read from
  *your own* branch table, so a repo whose types are `style/` or `liquid/` is held to its own
  convention.
- **The gate's refusals now quote the heading level they actually read.** Being told to demote a
  `###` to a `###` costs a consumer more than it costs a maintainer here, because you have no repo
  history to fall back on. What the gate accepts is unchanged.

### 8. Documents that now agree with the tree

**Action: none.** The workflow plugin's README lists all **16** skills it ships and stops counting
them -- two had arrived without a row, one of them (`worktree-lane`) invisible everywhere else
because it never appears in a slash list. `INSTALL.md`'s skill-counter warning names examples instead
of totals, after every one of its three figures had gone stale. A new opt-in lint check now holds
that table to the directory beside it, so this is the last time those two drift apart.

The generated developer notes render at your changelog's own heading levels, so an entry copied out
of the record pastes at the level it was written at. And the internal note handed to colleagues now
reads each entry's own declaration -- it could previously have carried a whole release of
repo-internal housekeeping into the one document that exists to stay out of.

## What it is worth

**Two failure modes that cost a person an afternoon each are now impossible.** A branch that cannot
be pushed and a PR that closes nothing both looked like success at the moment they happened: the
first wrote a well-formed document, the second warned and exited 0. Neither is caught by reading; both
were caught by someone hitting them. The repair for each is a guard that fails at build time instead
of at the worst possible moment.

**The backup of work in progress stopped depending on anyone remembering it.** Before this release
the median branch was invisible on `origin` for 22 minutes and the worst for six hours -- a device
failure in that window took the plan, the current phase and the note about where the last session
stopped with it. That is now automatic, and it is worth more than the small `park:` commits it costs.

**The rename is the deliberate cost in this release, and it was priced before it was accepted.** One
install line and one settings line, on a measured population of one consumer. It buys a plugin whose
name states what it is, which is what makes it explicable to the next person who has to adopt it.

**And the release train itself got measurably cheaper.** Superseded CI runs are now cancelled instead
of running to completion beside their replacement -- on a Windows runner that bills double, one PR
was holding three full runs of the same branch at nearly eight minutes each.

**This release cost 7 minutes 38 seconds end to end**, clock started before the cut and stopped when
the Release was published. Three legs: **3m41s** for the gate-and-cut (the lint gate plus 53 test
suites at 182s, three generated documents, five version bumps, the commit and the tag), **3m10s** for
writing this document and running the gates a second time before the notes commit, and **47s** for
the publish and its two attachments. Nothing ran behind: every leg blocked the next one, which is why
the test gate running twice is a third of the total. Compare with the **28m 03s** measured at v4.4.0,
when the note still travelled through its own pull request.

## What was still open at this release

**The issue tracker was empty at the moment this was cut** -- three open issues were closed in the
hour before it, and no new ones were filed.

Two things were deliberately left standing, both recorded rather than repaired:

- **Abandoned branches now accumulate on `origin`.** Pushing at creation is what makes the backup
  work, and nothing reaps a branch that never merged. Watched, not solved.
- **A plugin README that enumerates its skills is only checked where it opts in.** Two of the four
  team plugins enumerate none of theirs, so a general rule would have started life with an eight-item
  exemption list. The explicit sentinel fires on the one table that means it.

Two decisions that belong to a person rather than to the tooling were both taken in the same session
as the cut: the marketplace was published to the business organisation, and the two consumer
checkouts that were several versions behind were updated from their own repos. Neither is part of the
release itself -- a release records a version, a publication changes what colleagues receive -- which
is why they are recorded here as taken rather than assumed.
