# Release notes v4.31.0 🚀

**Date:** 2026-09-06\
**Type:** Minor\
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

Every plugin carries its owner in its name, and the fold survives a queue merge

## What changed

**This release renames every plugin, so it breaks your install the moment you update.** The
migrations are first below, in the order you have to do them. Everything under
[Nothing to do](#nothing-to-do--these-arrive-on-the-update) needs no action from you at all.

### 1. Re-add the four team plugins under their new names — **you must act**

`team-alpha@claude-code-specialists` stops existing, and so do `team-ecomm`, `team-lifehub` and
`team-shopify`. Every plugin this marketplace publishes now carries the owner in its name.

Run this for whichever teams your repo enables:

```text
claude plugin marketplace update claude-code-specialists
claude plugin uninstall team-alpha@claude-code-specialists
claude plugin install   dkj-team-alpha@claude-code-specialists --scope project
```

Then three edits in your own tree, none of which the plugin can make for you:

- **`.claude/settings.json`** — the keys under `enabledPlugins` are the old ids.
- **The orchestrator `@`-import**, normally in `.claude/specialists/SPECIALISTS.md`. It names
  `plugins/teams/team-alpha/personas/01-01-persona.md` literally, because `@`-imports take no
  variables. Re-run `specialists-init` to rewrite it, or edit the one line by hand.
- **Every `@team-alpha:<name>` subagent invocation** in your lenses, skills and docs becomes
  `@dkj-team-alpha:<name>`.

**Get the `@`-import right first, because it fails silently.** Claude Code drops a dead `@`-import
line without an error and the session loses the whole document — so an orchestrator that simply
never loads looks like a model problem rather than a path problem.

The marketplace name is unchanged, so your `extraKnownMarketplaces` block stays as it is. No lens,
manual or specialist id changes: the specialists are the same people in a differently-named box.

### 2. Repoint one line of your own CI — **you must act if you ran `adopt-workflow-folder`**

`plugins/workflows/` is now `plugins/dkj-policy/`. Your `.github/workflows/branch-entry.yml` checks
this repo out at `ref: main` and runs the gate **by path**, so it breaks before you update any
plugin. The skill never overwrites, so the file it wrote once is yours to edit:

```text
- .workflow-scripts/plugins/workflows/dkj-policy/scripts/lint/check-branch-entry.ps1
+ .workflow-scripts/plugins/dkj-policy/scripts/lint/check-branch-entry.ps1
```

One line, one file — and it is the only place your own tree names a shared script by path.

### 3. Two adoption skills became one — **you must act if you invoke them by name**

`adopt-config` and `adopt-workflow-folder` no longer exist. Both are now **`adopt-dkj-policy`**,
which does the work of each. If your own docs or scripts name either of the retired two, point them
at the survivor. Related: `adopt-bwj-asana` is now `adopt-dkj-policy-bwj`, because it covers the
whole plugin rather than just Asana.

### 4. Update promptly if your fold ever runs without `-Branch` — **no edit, but do not defer it**

`fold-changelog-entry.ps1`'s fold-all mode could mistake `CHANGELOG.md`, `CONTRIBUTING.md` or
`README.md` for an unfolded branch dossier — and in one reproduced case it **folded
`dkj-policy/README.md` and deleted the file**, splicing its title into `CHANGELOG.md`. It does not
fail loudly: the run succeeds. Every repo running `dkj-policy` has the layout that makes this
reachable, and the new automatic fold runs with `-Push`. Fixed in this release.

The visible symptom, if this already happened to you: a `dkj-policy/README.md` that is gone, or
already-folded entries reported as *"the same tier declared twice."*

### Nothing to do — these arrive on the update

- **Your branch names are now read as UTF-8.** `new-branch.ps1` strips control and format characters
  out of the remote tip's commit subject — text written by whoever else pushed to that branch. On a
  default Windows console the strip was in your copy of the script and not in effect. No flag, no
  change in use: the line you already see is now the line the script promised.
- **A claim carries straight on into the work.** `claim-issue` used to hand the turn back with
  *"say the word"* after a clean claim. The page, the script and the persona all now say what
  follows, so your session continues in the same turn.
- **You can run a test gate smaller instead of not at all.** `open-pr`, `ship-pr` and `cut-release`
  take **`-MaxParallel <n>`** and pass it to the test gate. Reach for it before `-SkipTests` when a
  gate will not finish on your machine — `-SkipTests` says *this run did not measure*, and a smaller
  run still measures. `0` (the default) behaves exactly as before.
- **`ship-pr` works behind a merge queue.** On a trunk with one it opens the PR, waits for CI,
  enqueues and ends successfully; the queue merges and the fold happens off that push. On a trunk
  without one, nothing changes.
- **`cut-release`'s closing reminder stops printing a command your repo cannot run.** If you adopted
  via `enabledPlugins` rather than an install record, it now names the marketplace refresh — which
  is the whole remedy — instead of an update command that answers *"Plugin is not installed."*
- **Pages you read during adoption are corrected.** `releases/README.md` no longer tells you the
  plugin is called `contributing-davekjohn`; `dkj-policy/scripts/README.md` gained the 21 rows it
  was missing and is now held against the registry by a lint check, so it cannot go short again;
  the plugin table no longer states a session-hook count that had gone stale at two against five.

## What it is worth

**The automation no longer depends on a session being alive to finish its own work.** Two closing
steps — folding the changelog, and verifying that a merged PR really closed the issues it declared —
used to run only from the shipping session, right after its own merge call returned. A merge queue
takes that call away, and a merge from the GitHub UI never had it. Both now run off the push to
`main`, which is the one event that always happens. What that buys is not speed: it is that the
record stops depending on who merged and whether their terminal was still open.

**One silent data-loss path was found and closed before it reached anyone.** The fold could delete a
real `README.md` and exit successfully. It was caught while testing the automation that would have
run it on every push — reproduced, not theorised — and the fix closes the class rather than the
instance: six hand-rolled directory scans that could each have grown the same hole are one shared,
guarded listing now.

**The renames are a one-time cost paid to remove a permanent ambiguity.** Every plugin this
marketplace publishes now says whose it is in its own name. The migration above is real work for
each consuming repo, and it is the last time this particular ambiguity has to be paid for.

**And a gate that would not finish now has an answer that is not "skip it."** On the machine that
reported it, the default test gate was killed twice for running out of memory; a smaller lane count
passed. Before this release the only route past that was the switch that erases the evidence — and
on a release cut, that meant a version could be tagged with a suite red.

### What this release cost

Clock started 16:16:03, before the first command; stopped 16:35:45, when the last asset landed.
**Total, end to end: 19m 42s.** Every leg blocked a person — nothing here ran in the background.

| leg | wall-clock |
|---|---|
| `cut-release.ps1` — lint gate, 71 suites (16 lanes, 369s), notes generated, commit + tag | 9m 16s |
| rewriting the audience document (576 draft lines to 137) **and** re-running the gates from the trunk — 71 suites again, 379s | 9m 17s |
| notes commit, `git push origin main`, `git push origin v4.31.0` | 44s |
| publishing the GitHub Release | 18s |
| uploading the two attachments | 7s |

**Two full suite runs are 12m 28s of the 19m 42s — 63% of the release.** The second one ran because
the checklist has the notes commit pass the gates from the trunk, and what it actually measured was
one edited markdown file. That is the leg to look at if this is ever worth shortening; the tail
after the notes commit came to **1m 09s**, so nothing there is worth optimising.

The cost is per release rather than per change, so releasing half as often removes exactly as much
of it as making it twice as fast — and needs no code.

**A correction worth recording, since this section's whole premise is that the figure was
measured:** the first pass of this table was written before the push and carried a subtotal and two
leg times that were estimates, not readings — including a "total" for events that had not happened
yet. The numbers above are timestamps. The failure mode the two-pass instruction exists to prevent
is exactly the one it walked into, which suggests the instruction needs to say *leave the cell
empty*, not *fill it in later*.

## What was still open at this release

- **Each consuming repo migrates itself.** Nothing in this release can rename ids in somebody else's
  `settings.json` or `@`-import. The connector register still names the retired ids for repos that
  have not migrated, and reports them as `[INFO]` — that is the designed behaviour of a rename, not
  a fault to chase.
- **The automatic fold pushes as a person.** `fold-on-merge.yml` authenticates with a fine-grained
  PAT held by an org owner, because a ruleset bypass has to be an actor and the GitHub Actions app
  cannot be one (a `422` was measured on September 6, 2026). Succession — what happens if that
  owner becomes unreachable before the token's 366-day expiry — is written down; the token itself
  still has a single holder.
- **The default lane formula for the test gate is untouched.** `-MaxParallel` adds a way past a gate
  that will not finish; it is not a new policy. One machine is not a measurement of a formula.
