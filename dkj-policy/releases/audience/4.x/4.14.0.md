# Release notes v4.14.0 🚀

**Date:** 2026-08-19  
**Type:** Minor  
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

The root docs hold without a plugin installed, and the workflow layer sits on top

## For consumers

### If your repo publishes to tier 1, your release note now says what changed -- and the hand step you wrote around it can go

Answer `Get-ReleaseAudienceTier` with `1` and the document `cut-release` drafts for you now opens with a
section listing the changes this release carried, drawn from your own tier-1 entries. Before this update that
section did not exist at all in a tier-1 repo: the draft went straight from the title line to *what it is
worth*, so an outward-facing document could be finished, attached to a GitHub Release and published while
carrying only the two sections a script cannot generate.

**The failure was quiet, which is why it is first on this page.** Nothing errored, no gate objected, and the
draft read as complete -- the visible symptom is simply that there is no heading between the title and
*What it is worth*. If you publish to tier 1 and have released since adopting this workflow, your published
notes are missing that section.

**What to do:** if you wrote a hand step into your own release aftercare to add the heading, **delete that
step rather than filling it in** -- the section now arrives pre-filled, not empty. If you overrode
`SectionConsumers` or `HintConsumers`, nothing breaks: they are renamed to `SectionAudience` and
`HintAudience` and **both old names are still read**, so your heading survives the update untouched. Nothing
in your tree is edited by this release.

### Updating from 4.12.x or earlier: `/continue` is now `/handover`

Skipping straight past v4.13.0 means skipping its one required action. The skill that picks work back up
after a context clear was renamed, because Claude Code ships its own built-in `/continue` and the two names
collided on the command whose entire job is to be the first thing you type in a cleared session.

**What to do:** change the word you type. The chain is still `/lock` -> `/clear` -> `/handover`, and the file
it reads is still `.claude/handover.md`. After you update, `/continue` no longer resolves to this skill.
v4.13.0's own [release note](4.13.0.md) carries the rest of that release and is now complete.

**Coming from 4.13.x?** You have already done this. No action.

### Leave `Get-ReleaseHistoryPath` at its default

The list of every release you have cut belongs at your repo root, where it survives the workflow plugin being
uninstalled. The shipped `adopt-workflow-folder` script, its skill page and the config blueprint used to
advise repointing that seam into the workflow folder; all three now say to leave it alone, so a repo adopting
after this release gets the corrected advice by default.

**What to do:** only if you already repointed it -- **nothing errors either way**, and this is not urgent. But
your history then sits in a folder your own teardown would remove, so moving it back to the default is worth a
minute the next time you are in that file.

### `/handover` now checks whether the cause your lock states is the real cause

The verify step gains a fifth question. The four it already asked all test whether a lock has gone *out of
date*; none of them catches a lock that is current and simply wrong about a mechanism -- a correct report
summarised into something false. That is a failure your own locks can produce, since `/lock` writes its
summary the same way.

The measurement travels with the rule rather than staying in our repo: a lock written **six minutes** before
it was read named its subject correctly, and named as the cause a parameter that only sorts and filters
nothing. It also carried its own certificate -- *"confirmed at the code level before locking"* -- which is
precisely the sentence that would otherwise have prompted a re-read.

**No action needed.** You get the sharper step with this update.

### A freshly adopted workflow folder explains its own layering

`adopt-workflow-folder` now scaffolds a folder page that says how the workflow layer sits on top of your
repo's own operating guide, instead of leaving you to infer it.

**No action needed**, and nothing changes for a repo that has already adopted -- scaffolding is additive by
design, so it writes this once and never again.

### Tessa checks whether a destination can still reach its reader

The technical writer's manual gains a hard rule: picking the right layer for a change is only half of siting
it; the other half is whether that file can still arrive at the reader who needs it. Two destinations look
correct and are not -- a file a plugin scaffolds into your repo is written once, so a repair written there
reaches new adopters only, while `${CLAUDE_PLUGIN_ROOT}` resolves per plugin, to the one shipping the file it
is written in.

**No action needed.** It bites us rather than you: it is the rule that decides whether a fix you need arrives
as a plugin update or never arrives at all.

## What it is worth

**A defect that only appears in somebody else's configuration was found, and the shape of it is worth more
than the fix.** The tier-1 release note was missing its central section for every minor a tier-1 repo has ever
cut, and no gate here could see it: this repo answers tier 2, so every local run, every suite and every CI job
produced a correct document. The test that came closest asserted the *right* behaviour for a tier-2 repo and
was read as universal. The generalisation is now written down -- **a rule stated for one seam value, then read
as though it held for every value** -- and the suites grew scenarios that drive the real script against a
fixture answering tier 1. That is the class of defect a seam buys you along with its flexibility, and it is
invisible from the inside by construction.

**Four reports were repaired this release and three of them were wrong about something before they were
right.** One named a parameter as the cause that only sorts; one proposed an empty heading where the data to
fill it already existed; one counted the root's uses of a name with a tool that counts lines rather than
occurrences. In each case the reported symptom was real and the reasoning was not, and in each case the repair
changed because somebody opened the file before building. This is now a documented habit rather than a run of
luck -- it is written into the shipped `/handover` skill, so it reaches every repo that uses it. **The
organisational value is that a wrong repair costs more than no repair**: it satisfies the report, closes the
issue, and ships a citation for a mechanism nobody has.

**And the repo's own operating guide now holds with nothing installed.** Seven of this release's sixteen
changes do one thing: make the root documentation true on its own, with the plugin layer adding to it rather
than being assumed by it. The root `CLAUDE.md` no longer leans on the specialists, the release history sits at
the root where it survives an uninstall, and the claim that the constitution was *portable* is gone -- what
travels is the shape, not the content. **The practical payoff is that this repo can be handed to somebody who
has installed nothing and still describes how it is run**, which is the only version of that promise worth
making.

**Cost of this release: 26m 40s** from clock start to a published Release with its attachments. The legs, as
measured from timestamps rather than reconciled to the total: the orientation pass that established the state
and the bump **1m 30s**, the cut itself **7m 05s** (43 test suites green in **364s** inside it), writing this
document **6m 01s**, its own gates and the two commits **3m 31s**, CI and the merge **7m 49s**, the fold
**4s**, the publish **40s**. The seconds between them are the gaps where one command finished and the next was
started.

**The head was 8m 35s of that -- 32%, and that is the third release running to land under a third.** `v4.12.0`
came to 24% of 20m 41s and `v4.13.0` to 30% of 20m 38s. Three readings are not a distribution, but they say
the same thing `v4.4.0` did at 35%: most of a release happens after the document that describes it is frozen,
which is why the first pass is written before the tail rather than estimated afterwards.

**This release is six minutes longer than either of the two before it, and the cause is named rather than
inferred.** The tail is where it went -- 18m 05s against roughly 14m 23s at `v4.13.0` -- and two of those legs
are the reason: the test gate inside the cut read **364s** where `v4.13.0`'s read 147s, and CI ran **7m 27s**.
Neither is a change to the procedure, and one refused command is in there too: the first `ship-pr` was stopped
by the step-list gate over a step that named the ship chain itself. The gate was right; the step should not
have been written.

## What was still open at this release

- **The copy attached to the GitHub Release carries the head of the timing only, and stays frozen.** This
  document cannot time its own publication, so the total above was added afterwards in its own small edit. The
  attachment is deliberately not replaced -- an attachment is what was published at the moment it was
  published, and silently swapping it is the opposite of the record this document is for. **This page is the
  current version.**
- **The audience draft silently dropped the tier-2 prose for two entries, found while writing this page.**
  Entries written before the format change of August 16, 2026 head their second section `#### Tier 2`; newer
  ones head it `#### Higher than tier 0?`. The development notes group both shapes correctly, so all eight
  tier-2 entries are in the record -- but the audience draft rendered the two older ones as a heading with an
  empty body, and their scores did not sort. `docs/destination-reach` and `feat/agent-shared-under-teams` are
  written into the consumer section above by hand from `CHANGELOG.md`. Named with its measurement rather than
  repaired mid-release; a repair reaches only the next release either way.
- **The test gate inside the cut reported 364s for 43 suites, against 147s for the same 43 at v4.13.0.** Two
  single readings on different machine states, taken from each cut's own output. Named rather than diagnosed
  -- a stopwatch reading is a count, and one reading is not a distribution.
- **`BRANCH-portable.md` still describes the retired entry shape**, flagged as an observation at
  `docs/entry-shape-repair` and still standing: it calls the entry's first section `Branch title` and still
  refers to a `### Significance` wrapper, neither of which the current template has. It is portable payload
  reaching every consumer and several distinct claims are affected, so rewriting it is its own scoped job.
- **310 uses of "workshop" as a role word remain, deliberately.** They are not the retired framing, and
  sweeping them is a prose-sensitive rewrite across 61 files that buys consistency at the price of worse
  sentences. Filed with its measurement rather than swept along unasked.
- **This release has not been published to the organisation.** Publishing is a decision separate from cutting
  and has not been asked for. Until it is, colleagues installing internally remain on the four team plugins at
  **4.13.0**, one release behind. Read at the target rather than carried forward:
  `BWJ-ecommerce/claude-plugins-bwj`, commit `9ea8dcf`, 2026-08-16T19:40:08Z, taken from the published
  `plugin.json` files themselves -- v4.13.0's note named 4.11.0, which was true when it was written and was
  overtaken by a publication the same evening.
- **Two specialists are *degraded* rather than excluded in the Claude App setting.** Two agent definitions name
  a script in one step of one procedure. Excluding them would lose a whole specialist over one line; publishing
  them silently hands a user a step that cannot run. They travel with that step named in their own description,
  which is a mitigation rather than a fix. Unchanged since v4.10.0.
- **A second `Get-JsonField` remains, deliberately.** No live misbehaviour was found; the risk is a future
  caller relying on a `-Default` the second copy does not have. Named and left, per this repo's standing rule
  about risks that have not bitten yet.
- **Two layers of this repo speak Dutch where no path-scoped rule can reach them** -- the public GitHub
  repository description and the `inbound` label description, both in repository settings rather than in the
  tree. Outward-facing configuration, so they wait on Dave.
