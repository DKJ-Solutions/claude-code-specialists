# Release notes v4.26.0 🚀

**Date:** 2026-08-30\
**Type:** Minor\
**For whom:** consumers of this product, and colleagues in the organisation -- one section each

The gates and their messages name what actually happened instead of an assumed cause

## What changed

### If you move a branch between two machines, `new-branch` now continues it instead of starting a second one

**Action needed if you work from more than one machine.** A branch parked from your laptop lives on
`origin` and not in your desktop's local refs. Until this release `new-branch` looked at local refs only,
so on the second machine it read *"no such branch"* and cut a fresh one at your current base -- same name,
same scaffold, none of your work. It now reads both ref namespaces before it acts, resumes at the remote
tip with tracking, and **says out loud which of the three things it did**: cut, resumed, or found the name
taken (type `-v2` if you meant a new branch).

**Check one thing if you have hit this**: the run did not pass silently, it exited non-zero on a rejected
push -- so what you may have is a local branch sitting at the wrong base beside the real work on `origin`.
Delete the local one and re-run `new-branch`; the remote branch is intact. `worktree-lane` inherited the
same failure and is fixed with it.

The base warning that counts how far behind the trunk you are now waits until after that question, because
on a resume it was measuring the trunk's gap and printing it under your branch's name.

### Do not touch the checkout while a gate is running -- and if you did, the gate now tells you

**Action needed: a habit, not a command.** `open-pr`'s lint and test gates read your working tree for a
minute or more, and that checkout is not private to them. Anything that borrows it in the meantime --
most easily a `prune-merged` run in the session a backgrounded `ship-pr` just handed back to you -- can
turn a healthy suite red. Measured here: one suite of 55 red inside the gate, green on the same commit
seconds later.

Each gate is now asked afterwards whether the tree held still. A red says the result is not trustworthy
and names the usual cause; re-run it. A green is reported and **not** recorded as gate evidence, so the
next run gates for real rather than skipping on a pass nothing judged. Neither is a refusal -- a red still
blocks the push. The workflow page now states plainly that the primary checkout is single-occupancy while
a gate is running.

### A failed park now tells you what git said, not what it guessed

**No action needed.** When a park could not push, the summary line said *"is `origin` configured and
reachable?"* -- written when you had to ask for a park by hand, and left behind when pushing became
automatic on every branch creation and every session stop. The common failure today is a branch that has
moved on the remote, so the line you trust over the raw output was pointing you at your remote
configuration while git's own `! [rejected] ... (non-fast-forward)` sat directly above it.

You now get one of three sentences: the remote is ahead of you (pull or rebase first), the remote could
not be reached, or -- where the shape matches neither -- **no cause at all**, only a pointer to git's own
output. That last one is deliberate: a guess in a summary reads as a finding.

## What it is worth

**The theme of this release is a tool that reports rather than assumes, and its value is measured in
misdirected debugging time.** Every one of the three items above worked correctly at the mechanism level:
the branch really was on the remote, the push really did fail, the suite really did go red. What was wrong
in each case was the one line a person reads instead of the raw output -- and that line sent them to check
their remote configuration, or to hunt a test failure that did not exist, or to conclude that yesterday's
work was gone. A confidently wrong summary costs more than no summary, because it is trusted.

**One of the three was a real risk of lost work, and it is closed.** The cross-device handoff is the
routine this workflow recommends -- park on one machine, resume on the other -- and it was the one path
`new-branch` could not see. Nothing was ever destroyed, but recovering it required a person to distrust a
script documented as idempotent, which is a long way to travel from the symptom.

**Reduced dependence on a developer:** a red suite means something again. This system's own rules tell a
session that a suite red under the gate is reporting a real defect until proven otherwise -- an honest
rule that a false red turns into a trap, and only somebody who knows the gate's internals can tell the two
apart. That judgement is now made by the gate itself.

**What this release cost: 5m 51s end to end**, from the clock start at 14:54:26 to the attachment
landing at 15:00:17.

| leg | time | who waited |
|---|---|---|
| cut: lint gate, 55 suites, generate, commit, tag | 2m 18s | blocked a person |
| the note: writing it, the lint gate again, commit, push, publish, attach | 3m 33s | blocked a person |

**That is a third of the previous release, and the difference is one habit rather than any change to the
tooling.** v4.25.0 came to 15m 44s, of which about four minutes were its own gates re-run one suite at a
time before the note's commit, by hand, instead of through the runner that already existed. Here the cut's
own gate did the suites, and the note's commit re-ran the lint alone -- the check that actually judges a
markdown document. The lesson that release wrote down is the one that paid for this one: reach for the
tool that does it rather than composing an equivalent.

Nothing ran behind us: this repo is its own consumer, so no CI leg blocked the release.

## What was still open at this release

**Three things, all recorded, none blocking.**

- The gate above **detects** a checkout that moved under it; it does not remove the cause. The most
  frequent borrower is `prune-merged`, which fast-forwards the trunk through the working checkout where a
  refspec fetch would not need it at all --
  [#1147](https://github.com/DaveKJohn/claude-code-specialists/issues/1147). Until that lands, the habit
  in the second item above is the remedy.
- The `[RECORD-SHAPE]` roll-up now counts only the plugins a repo's own settings enable, which is the
  predicate the previous release deliberately left alone as unmeasured. It was measured for this one --
  six install shapes against Claude Code 2.1.251 -- and the measurement answered more than was asked: an
  install that cannot write the enable fails outright and leaves no record, so no coverage was traded for
  the quieter count.
- The fourth adoption round had not yet run when this was cut. It is the round that first exercises a
  tier-2 audience note (this document), a major version cut, and a repo with no remote.
